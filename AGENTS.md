# AGENTS.md — termag

## What This Is

A multi-user workspace manager for running AI coding agents in parallel. Each project gets a paired set of tmux sessions — an **agent** pane (Codex, Claude Code, or other agents) and a **ctrl** pane (regular terminal for sudo / interactive auth / things the agent can't run). The web UI renders both terminals side-by-side with xterm.js, shows real-time agent status (working/waiting/idle from Claude hooks + Codex app-server), and exposes per-project usage and a Slack `/t` command surface.

Auth is Google OAuth with an `ALLOWED_USERS` allowlist mapping `email:unixuser`.

## Status

Production-ready. Provider registry covers Codex, Claude, Mistral (vibe), Devin, and pi (pi on the self-hosted model catalog); per-project working-time and human-activity tracking feed a two-tube thermometer UI; project sharing lets owners invite collaborators with terminal access; new projects get seeded `AGENTS.md` and `CLAUDE.md`. The orchestrator can now provision additional EC2 "boxes" on demand (the backend calls the AWS SDK to launch a Packer-baked AMI, surfaced as "a new box…" in the New project dialog) and route projects to a specific `Instance` via `Project.instanceId`. Every project carries a `main` workstream backed by a git worktree, with CRUD routes for additional workstreams. Visit + flow-speed telemetry (`ProjectVisit` for context switches, `WarpSample` for per-minute hyperspace-speed rollups) feeds new sections in the UsageMini overlay.

## Domain Model

- **Project** — an addressable workspace. Has a name, a working directory, an `agent` workflow (the paired tmux sessions), persisted `agentProvider` (string id resolved through the provider registry), and a Slack channel `#proj-<user>-<name>` auto-created on creation (legacy channels are `#proj-<name>`; both route). New projects are seeded with `AGENTS.md` (from the agent-wiki initial template) and a `CLAUDE.md` stub. Projects also carry a `pinned` flag and a `lastActiveAt` timestamp that drive the project list ordering: pinned projects float to the top, then the rest sort by recent activity. Pin/unpin and other per-project actions live in an overflow menu on each project tile. Each project is bound to an `Instance` (box) via `Project.instanceId`; routing decisions key off that field.
- **Paired tmux sessions** — `<unixuser>-<project>-agent` (where the AI runs) and `<unixuser>-<project>-ctrl` (regular shell). tmux turns `.` and `:` in a session name into `_`, so `sessionName()` (backend `services/tmux.ts`, frontend `utils/sessionName.ts`) builds names in that form (`first.last` → `first_last-<project>-agent`) and ownership checks compare against the tmux-safe username (`sessionBelongsToUser`). The web UI streams both via PTY + WebSocket. A third, transient role is `-review`: the **Review** button in the lower-right of the agent pane guesses the PR being worked on (the branch's PR via `gh`, else the PR the agent just opened, else the last PR mentioned in the pane), asks you to confirm or retype it, and starts the chosen reviewer (Devin by default; Claude or Cursor from the dialog's picker, `backend/src/services/reviewers.ts`) with a review prompt in `<unixuser>-<project>-review`; the pane docks under the ctrl terminal (collapsed bar / half-height) and disappears when its session is killed (`backend/src/routes/review.ts`, `services/review.ts`, `frontend/src/components/ReviewButton.tsx` + `ReviewDock.tsx`). Tmux helpers and the agent runtime are workstream-aware: every project gets a `main` workstream, and additional workstreams are realized as git worktrees with their own paired tmux sessions.
- **Workstream** — a named parallel line of work inside a project, backed by a git worktree. Every project has a `main` workstream auto-created on project creation; additional workstreams are managed through `backend/src/routes/workstreams.ts` (orchestrator) and the `git-worktree-add` / `git-worktree-remove` / `git-worktree-move` RPCs in `agent/agent.js` (rename also uses `tmux-rename-session`; the git branch is deliberately not renamed — `services/workstreamRename.ts`). Workstreams live at `<projectDir>/.worktrees/<name>/`. Tmux session naming threads the workstream id through (`<user>-<project>-<workstream>-<role>`, collapsing the workstream segment to keep historical names when it's `main`). Branching off mirrors the project's main-workstream `Workflow` rows onto the new workstream (one per workstream, since the legacy `(projectId, type)` unique was dropped) and launches its tmux sessions so the terminal pane can attach immediately. The UI surfaces a workstream sub-list under projects with >1 workstream and a "Branch off…" overflow action; single-workstream projects render exactly as before.
- **Instance ("box")** — a termag-running host. The orchestrator can provision additional boxes on AWS with the AWS SDK, launching the Packer-baked AMI (`packer/`) from the UI's **New project** dialog ("a new box…" in its box picker, `frontend/src/components/NewProjectForm.tsx`, shared with the `/welcome` wizard; adding a managed box requires a stored GitHub token, `boxGate`); self-managed hosts are registered from the sidebar's Boxes section. `Project.instanceId` and `AgentToken.instanceId` key off the `Instance` model so projects and per-user agent tokens are dual-keyed by host. Provisioning lives in `backend/src/services/boxProvisioner.ts`; orchestration design notes are in `docs/box-provisioning.md`. The owner can **stop and start** an EC2 box from its menu (`POST /api/instances/:id/stop|start`, `services/boxPower.ts`, rules in `boxPowerPolicy.ts`): `ready → stopping → stopped` is settled by a 10 s power sweep from `DescribeInstances`, and `stopped → starting → ready` by the agent's connect, after which `reconstructInstanceSessions` recreates the tmux sessions (Claude relaunches with `claude --continue`). A stopped box costs only its EBS volumes; creating a project, workflow or workstream on it answers 409. A box launched hibernation-capable (`Instance.hibernationConfigured`) can also be **hibernated** (`POST /api/instances/:id/hibernate`): `ready → hibernating → hibernated`, and a start resumes it with its RAM (`docs/box-hibernation.md`). Such a box can also hibernate **on its own** after `Instance.idleHibernateHours` idle (per box, off by default, `PATCH /api/instances/:id/lifecycle`, behind the `box-auto-lifecycle-enabled` flag; activity is human input or an agent `working`, never a reconnect — `services/boxLifecycle.ts`). It can also be **terminated** once it has stayed hibernated `Instance.hibernatedTerminateDays` (same route and flag); the agent's `unsaved-work` scan, taken right before each auto-hibernate, has to come back clean or the box is kept `BOX_UNSAVED_WORK_TERMINATE_DAYS` (90). A box that can't hibernate accepts both settings with a `lifecycle.warning` and is never touched: no stop or terminate fallback.
- **Provider registry** — `backend/src/providers/registry.ts` and `frontend/src/providers/registry.ts` define the set of supported agent providers (codex, claude, mistral/vibe, devin, pi, …) and their metadata: display name, launch command shape, status normalization rules, **tmux poller config** (idle/working detection patterns per provider, since e.g. vibe has a persistent input box that breaks naive polling), **usage scanner source** (Codex JSONL, Claude logs, vibe `~/.vibe/logs/session/meta.json`), and UI affordances. `agentProvider` is a free-form string keyed into the registry rather than a Prisma enum, so adding a provider is a code change in two registry files (no migration). Each user also has a saved `defaultAgentProvider` for the create-project form.
- **Per-user agent process** — `agent/agent.js` runs as the unix user (via systemd user service + lingering). It owns tmux attach, node-pty, filesystem ops, and Codex-bridge lifecycle. The main server at `:3040` is one process; each user has their own agent talking to it via WebSocket with a bearer token. This separation keeps unix permissions clean. The agent now uses heartbeat-driven dead-connection detection and accepts a config path override via `argv[2]`.
- **Status events** — Claude Code hooks (`UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Notification`, `Stop`) and Codex app-server status updates POST to `:3040/termag/api/status`. For providers without a hook surface (vibe), the **tmux poller** in `backend/src/services/tmuxPoller.ts` samples pane content and infers state using provider-specific patterns. Status drives the green/yellow/red indicators, the project-list transition flash (15s, color-coded green/yellow/red by transition type — e.g. idle→working green, working→waiting yellow, anything→idle red), and the "hyperspace" animation that speeds up with activity. The `Notification` hook distinguishes `idle_prompt` (idle) from other notifications (waiting). Status events also bump `Project.lastActiveAt`, which feeds the recent-activity sort.
- **Context-token warnings** — the per-user agent scrapes provider-specific "context remaining" strings out of the agent pane and forwards them through the status pipeline as a separate signal alongside working/waiting/idle. The UI surfaces this on the project tile and inside the terminal chrome so a session that's about to run out of context gets a visible warning before it hard-fails.
- **Rate-limit detection** — same shape as context-token warnings: the per-user agent (`agent/agent.js`) watches the agent pane for provider-specific rate-limit / quota-exhausted messages and forwards a `rateLimited` signal through the status pipeline. The backend persists it on the project's status record and the UI surfaces it on the project tile and in `ProjectControl` so a stuck session is visually distinguishable from a merely-idle one.
- **Working-time tracking** — derived from status transitions: time spent in `working` state is rolled up per-project for the usage dashboard. Provider-specific poller sources ensure correct attribution. Served from `/termag/api/worktime`.
- **User segments (engagement ladder)** — every user holds a daily segment (`New/Power/Active/Passive/Dormant`) in `user_segment_daily`, written by `services/segments/tracker.ts` (daily tick + boot backfill) from work-time/token/visit signals plus creation volumes; the admin **Segments** tab (`/admin/segments`, `pages/admin/AdminSegments.tsx`, `routes/admin/segments.ts`) reads the precomputed rows with 7-day flows (`/api/admin/segments[/users|/rebuild]`). Rules live only in `services/segments/rules.ts`.
- **Human activity tracking** — `backend/src/services/humanActivity.ts` tracks human keystrokes/interactions per project, separate from agent working time. Powers the second tube of the two-tube thermometer in the UI (agent work vs. human work).
- **Project visit telemetry** — `ProjectVisit` records when a user context-switches between projects in the UI. `backend/src/routes/visits.ts` exposes ingest + stats endpoints; the UsageMini overlay renders a visits section derived from them.
- **Warp / flow-speed telemetry** — `WarpSample` stores per-minute rollups of the hyperspace-speed signal. `backend/src/services/warpSampler.ts` produces the samples and `backend/src/routes/warp.ts` exposes a series endpoint feeding flow-speed sections in UsageMini.
- **Project sharing** — owners can invite collaborators by email. Shared users get terminal access to the project's tmux sessions through the same per-user-agent path. Routes in `backend/src/routes/sharing.ts`. **New** shares are behind the boolean feature flag `box-sharing-enabled` (off by default; `services/boxSharingFlag.ts`), evaluated for the person acting: sending an invite and accepting one answer 403 `{ code: 'sharing_disabled' }` while it is off, and the web UI hides the invite form, the Share item (unless the project already has shares) and the accept button. Existing shares are never behind it: terminal and CLI attach, capture/send-keys, review and listing keep working, and revoke, leave and decline stay open. The frontend reads it from `GET /api/flags`.
- **Space** — a named file store shared by people and the boxes they grant, behind the `spaces-enabled` flag (off: every route 404s); adding people also needs `spaces-sharing-enabled` for the owner (off: 403 `sharing_disabled`, so a space has only its owner and their boxes). Bytes go browser/CLI ↔ S3 over presigned URLs, never through the orchestrator; the bucket, presigner role and KMS alias are derived from the orchestrator's account and region (`services/spaces/spaceConfig.ts`), with no env of their own. A box acts with its owner's current role, only while it holds a `SpaceBox` grant, and never manages a space. `termag space …` on the CLI, the `termag-spaces` skill on boxes.
- **Admin surface** — org-wide, read-only view for administrators: `/termag/admin` UI, `/termag/api/admin/*` REST and a Streamable HTTP MCP server at `/termag/mcp/admin`, all behind `requireAdmin` (`middleware/admin.ts`). Admins are `users.role = 'admin'`, seeded at startup from `ADMIN_USERS` or granted from the Settings tab; admin-scoped bearer tokens (`agent_tokens.scope = 'admin'`) serve MCP clients and scripts. Every admin request and tool call lands in `admin_audit_log`. Aggregates and metadata only — never pane content.
- **Agent-to-agent asks** — `termag ask <box>/<project>[@<workstream>]` (CLI only; MetaTerm has no ask tools) runs one Claude Code turn on the target project's box, as the credential-less `termag-subagent` user in a per-thread clone of the committed code (`deploy/termag-subagent-run`, `systemd-run` sandbox, no internet, the box token only as a `LoadCredential`), and hand the reply back once. Commits come back as a git bundle that the **orchestrator** checks and pushes to `termag-<asker>/<thread>`, opening a draft PR with the asker's stored GitHub token (`services/askPublish.ts`). Access is `assertSessionAccess` (owner or share); routes under `/api/cli/v1/ask` (`routes/cliAsk.ts`, `services/askService.ts`); the box needs the `ask-v1` agent capability. The CLI picks the message id, so a retried `POST /ask` replays the same ask; a target that can't take a run is answered `rejected` with a reason and nothing stored; `termag ask --targets` (`GET /ask/targets`) lists what the caller may ask as A2A AgentCards. No run, hop or nesting limits; the hop is recorded. An ask whose work should stay off a busy box gets a box of its own through the CLI (`termag project create <box>/<project> --new-box --from <box>/<project>`, then `termag ask`); that box only gives the ask its own machine, and the run there is the same sandbox. An ask is not a spawn: an ask runs one sandboxed turn on an existing project and hands its reply back (`agent_threads`/`agent_messages`, `/api/cli/v1/ask`), while a spawn starts a new agent in its own workstream or project pane that keeps running and reports back (`agent_spawns`, `/api/spawns`).
- **Status WebSocket** — `/termag/ws/status` pushes status events to anyone subscribed (the UI itself, plus opt-in external consumers). Idle browser WebSockets are kept alive with a server-side heartbeat.

## Architecture

```
Browser ──https──▶ Apache (:443, /termag/*)
                    ├── /termag/ws/*    → ws://localhost:3040/termag/ws/*    (terminal streams + status push)
                    └── /termag/*       → http://localhost:3040/termag/*

Backend (single process, systemd "termag", root or service user, port 3040)
  ├── REST API     /termag/api/* (projects, status, usage, worktime, instances, workstreams, visits, warp, auth)
  ├── WebSocket    /termag/ws/terminal/<sessionId>  PTY stream
  │                /termag/ws/status                fan-out push (+ idle heartbeat)
  │                /termag/ws/agent                 per-user agent connections
  ├── tmux poller  Periodically samples tmux session state as a fallback signal
  ├── boxProvisioner  Launches boxes with the AWS SDK (EC2 + IAM) from the Packer AMI
  ├── Slack Bolt   Socket Mode (no public webhook needed)
  └── Postgres     prisma schema + sessions via connect-pg-simple

Orchestrator + boxes (one orchestrator, N termag-running boxes)
  ├── Instance model in Postgres; Project.instanceId / AgentToken.instanceId route work to a box
  └── New project dialog ("a new box…") → boxProvisioner → AWS SDK → EC2 instance from the Packer AMI,
                          renamed to the owner's unix user during cloud-init

Per-user agent (systemd --user, runs as the unix user)
  ├── WebSocket → backend /termag/ws/agent (bearer token)
  ├── node-pty → tmux attach <session>
  └── Codex bridges (per Codex-backed agent session)

Claude Code hooks (in each user's ~/.claude/settings.json)
  └── curl POST → :3040/termag/api/status   (UserPromptSubmit, Pre/PostToolUse, Notification, Stop)
```

Apache modules required: `ssl`, `proxy`, `proxy_http`, `proxy_wstunnel`, `rewrite`, `headers`.

**Trade-off: single backend + per-user agents vs single multi-user backend** — chose split. The backend can run as root or a service user without inheriting any one user's filesystem permissions; tmux/PTY/filesystem ops happen as the actual user via the agent. Cost: every user must run their own systemd `--user` agent and `loginctl enable-linger`.

**Trade-off: Slack Socket Mode vs HTTPS webhooks** — chose Socket Mode. No public ingress for Slack; reuses the same outbound TCP that the backend already maintains.

**Trade-off: Codex bridge as a managed subprocess vs in-pane only** — chose managed. The agent process owns the bridge lifecycle so termag can normalize Codex's app-server status into the same `working/waiting/idle` shape as Claude Code hooks, without each user wiring it up.

**Trade-off: provider registry as code in two files vs a single shared package** — chose duplicated registries (`backend/src/providers/registry.ts` and `frontend/src/providers/registry.ts`). Adding a provider is a small symmetric edit in both; the alternative (a shared workspace package) buys deduplication at the cost of a build-graph complication this repo otherwise avoids.

**Trade-off: orchestrator-driven box provisioning vs manual `terraform apply`** — chose orchestrator-driven (`boxProvisioner.ts` calls the AWS SDK itself: `DescribeImages`, `CreateSecurityGroup`, `CreateRole` with a permissions boundary, then `RunInstances`). The orchestrator owns the lifecycle so the UI's "Add box" button is the only path users see, and `Instance` rows stay in sync with what actually exists in AWS. Cost: the backend needs credentials for the box account and the IAM grant with its permissions boundary, and termag now owns the EC2, security-group, and IAM lifecycle that Terraform used to own.

## Data & Schema

`backend/prisma/schema.prisma`. Key models (not exhaustive):

| Model | Purpose |
|-------|---------|
| `User` | Google identity + mapped unix user. Holds `defaultAgentProvider` (string), `theme` (JSON — background mode and colour, shape in `src/theme/schema.ts`, `{}` = defaults), agent token records, usage rollups, `role`/`adminSource` (admin authorization), `lastSeenAt` (bumped by the auth gates at most once per 5 min). |
| `Project` | Name, working dir, `agentProvider` (string keyed into the provider registry, no longer an enum), Slack channel id, archived flag, owner, `pinned` flag and `lastActiveAt` timestamp (drive project-list ordering: pinned first, then recent activity), and `instanceId` (which box hosts the project). |
| `Instance` | A termag-running host ("box"). Tracks provisioning state, AWS identifiers, and the owning unix user. It also holds the agent's host sample (`diskUsedPct`, `memUsedPct`, `load1`, `keptCheckouts`, `hostSampledAt`) from its hello and the `host-sample` RPC every five minutes (`services/hostSamples.ts`), shown on Fleet and behind the `box_pressure` signal. `readyAt` holds the first agent connect, so `readyAt - createdAt` is that box's cold-provisioning time. `cleanedUpAt` is set only when a terminated ec2 box's AWS teardown fully finished; the provisioning sweep re-runs teardown for terminated rows without it (`docs/box-provisioning.md`). `parentInstanceId` is the box whose own credentials created this one through the CLI (null otherwise): that box may terminate it (an ask's box). Populated by `boxProvisioner` and the `/termag/api/instances` routes. |
| `Workstream` | A named line of work inside a project, backed by a git worktree. Every project has a `main` workstream auto-created on project creation; additional workstreams are managed through `backend/src/routes/workstreams.ts`. Non-main workstreams carry their own `slackChannelId` (`#proj-<user>-<project>-<workstream>`, auto-created and archived with the workstream); `main` uses `Project.slackChannelId`. |
| `ProjectShare` | Collaborator grants on a project — `(projectId, userId)` with role. Backs the sharing routes; lets a non-owner reach the owner's tmux sessions through their own agent. |
| `ClaudeRunnerSession` | One row per **run** of a Claude Code cloud session on a box (one order each): owner, box, slot, `startedAt`, the end the box reports through `POST /api/claude-runner/event` (`endedAt`, `exitStatus`, `exitReason`), and since the Anthropic `sessionId` that groups runs into sessions, the `clientPlatform` from the box's `started` report, and the owner-only `title` (first prompt's first line, copied to a new run of the same session). It also holds the token usage the session posts about itself (`inputTokens` … `usageAt`, `model`), read by every token report as provider `claude-cloud` through `services/admin/tokenSource.ts`; the usage scanner never sees these sessions. |
| `ClaudeSessionEvent` | Append-only log of what happened to a cloud session, keyed by `sessionId`: every spawn outcome (`queued` with the refusal reason, `placed`, `already-running`, `agent-failed`), the box's `started` and `ended`, the reconciler's `lost`, an `end-requested` from the UI. `detail` never holds an email, a token or prompt text. Swept after 30 days; run rows after 90 (`services/claudeSessions.ts`). |
| `AgentToken` | Bearer token for a per-user agent connection. Issued from the UI sidebar. Carries `instanceId` so a token is scoped to a specific box, plus `scope` (`agent` default, `admin` for the admin surface) and an optional `expiresAt`. `/ws/agent`, the agent-facing REST routes and `/api/cli/v1`'s box credential accept only `agent`; `requireAdmin` accepts only `admin`. The CLI and `termag tui` sign in with `cli_sessions` (`tmcli_`), not this table. |
| `SessionStatus` | Write-through copy of the live in-memory status map (`services/statusPersistence.ts`): one row per `instanceKey+session` — status, meta, open `working` span. Restarts re-read it instead of showing every pill as `not_running`, and re-bank spans whose auto-idle deadline passed while down. Rows are pruned after 24 h untouched; there is no append-only event log (the old `StatusEvent` description was stale — the WebSocket push reads the live map). Status writes also bump `Project.lastActiveAt`. |
| `WorkTimeEntry` | Per-day, per-project, per-provider working-time rollup, banked by in-memory transition timers — agent spans in `services/status.ts` (bank on `working`→other transitions, 5-min auto-idle safety net, restart hydration via `session_statuses`), human typing time in `services/humanActivity.ts` (browser heartbeats while typing, 3-min decay). Upsert-increment keyed `(username, project, provider, date, instanceId)`. Powers `/termag/api/worktime` and the two-tube thermometer. |
| `UsageEvent` | Per-call API usage (tokens, cost) for the dashboard. Provider-specific scanners populate this (Codex JSONL, Claude logs, vibe `~/.vibe/logs/session/meta.json`). |
| `ProjectVisit` | Per-user context-switch log: when the UI focus moves between projects. Feeds the visits section of the UsageMini overlay via `/termag/api/visits`. |
| `WarpSample` | Per-minute rollups of the hyperspace-speed signal. Produced by `warpSampler` and exposed via `/termag/api/warp` for the flow-speed sections of UsageMini. |
| `AgentThread`, `AgentMessage`, `AgentBundle` | Agent-to-agent asks: the thread (origin user, target project + workstream, Claude session id, base commit, repo, branch, PR, hop count), one row per ask (sender, sender box, status, hop, byte counts, publish outcome, whether a poll got the reply; never the reply, and the prompt only in `queuedPrompt` while an ask to the asker's parked box waits for it to connect, at most 15 minutes), and the commits' bundle until published or 1 h old. Reply text is never stored: it reaches the waiting poll through Postgres `NOTIFY` (`services/askReplyBus.ts`) and is dropped if nobody waits. |
| `AdminAuditLog` | Every admin REST request and MCP tool call: actor, token if any, surface, action, args summary, outcome. Never pruned automatically. |

**Schema changes are expand, then contract.** During an overlapping deploy the old and new orchestrator share the database, and the new one syncs with `DB_PUSH_MODE=additive`, which skips drops. So add first (nullable or defaulted; write both shapes, read the new one with a fallback), and drop the old shape only in a later release, by hand. A rename, a type change old code can't read, or a `NOT NULL` column without a default breaks the old process mid-deploy.

**PR pipeline and the running commit.** `GET /api/prs` (`routes/prs.ts`) returns the user's pull requests across the orgs in `GITHUB_REPO_ORGS` (all of GitHub when unset), already in lanes: three parallel GraphQL searches with the stored gh token (`services/prPipelineGithub.ts`; one combined query took ~7 s because `mergeable` is computed on demand), pure lane rules in `services/prPipeline.ts`, fresh for 60 s per user and then served stale while one reload runs (`swrMemo`, ceiling 10 min), `{ connected: false }` with no token. Lanes 1–2 (branches with no PR) come from the `git-branch-state` agent RPC (`agent/git-branch-state.js`, local refs only, no fetch), asked for every live workstream of the user's own projects inside that same load (`services/prBranches.ts`); its `origin` is also what links a PR row to a workstream by (repository, branch). A checkout with no GitHub origin never gets a branch row, and a branch that already had a PR merged (any age, one batched `pullRequests(headRefName:, states: MERGED)` query) is dropped, because a squash merge leaves it "ahead of base" for good. An agent that predates the RPC answers "Unknown command": its workstreams link by branch name only, and the response's `notes` say to restart it. ## Build, Run, Deploy

```bash
# build
cd backend && npm install && npm run build
cd ../frontend && npm install && npm run build

# run main server
sudo systemctl daemon-reload && sudo systemctl enable --now termag

# run per-user agent (as that user, Linux)
mkdir -p ~/.config/systemd/user
cp deploy/termag-agent.service ~/.config/systemd/user/
systemctl --user daemon-reload && systemctl --user enable --now termag-agent
sudo loginctl enable-linger <username>     # so it runs without an active login

# wire Claude Code hooks (per user)
# add the JSON block from deploy/claude-hooks.md to ~/.claude/settings.json

# build a box AMI
# automatic: merging to main bakes within the hour when box.pkr.hcl, setup.sh,
# agent/ or a shipped deploy/ file changed, or the image is over 14 days old
# (publish-ami.yml, `check-box-ami` job).
# on demand: GitHub → Actions → "Publish AMI" → Run workflow → target=box
# (or `both`) + tick `publish`; new boxes then pick up the newest Component=box
# AMI by tag. Without `publish` the result is a Component=box-candidate that
# discovery ignores -- bake a branch, inspect it, promote by retagging.
# local fallback (per-template init — `packer init .` errors on dup vars):
cd packer && packer init box.pkr.hcl && packer build box.pkr.hcl

# provision a box: the UI's New project dialog ("a new box…") is the only path
# the orchestrator knows about. boxProvisioner calls EC2 + IAM directly, so whatever a
# `terraform apply` in terraform/box/ creates has no Instance row behind it.

# run the orchestrator as a container (control plane only; boxes stay EC2)
docker build -t termag-orchestrator .
docker run --rm --env-file backend/.env termag-orchestrator npm --prefix backend run db:push   # schema sync
docker run --rm -p 3040:3040 --env-file backend/.env termag-orchestrator                       # serve
```

**Container deployment** — `Dockerfile` + `docs/container-deploy.md` (runtime contract: `/public/status` health, env, DB, auth modes, agent-endpoint requirements, single-replica constraint, EC2→container cutover runbook).

Apache snippet in `deploy/apache.conf`. See `deploy/setup.md` for the canonical first-time walkthrough (covers both Linux/systemd and macOS/launchd for the per-user agent); `deploy/claude-hooks.md` for the hook config; `docs/box-provisioning.md` for the orchestrator-driven box-provisioning design.

**Suburl apps on the orchestrator** — the orchestrator AMI ships an nginx gateway on :3040 that routes `/termag` to the backend (:3100) and any other path prefix to apps registered under `/srv/termag/apps/<name>/` (an nginx snippet + a systemd unit on the persistent volume, re-registered at every boot by `termag-apps-boot`). Never hand-create ALB target groups or listener rules for an app — see `docs/hosted-apps.md`.

**macOS note** — the per-user agent runs under `launchd` instead of `systemd --user`. There's no linger equivalent; the LaunchAgent plist (`~/Library/LaunchAgents/`) handles auto-start at login. See `deploy/setup.md` for the plist template and `launchctl` commands.

**Pre-commit** — a `gitleaks` hook is configured in `.pre-commit-config.yaml` with rules in `.gitleaks.toml`. Run `pre-commit install` once after cloning so leaked AWS / Slack / OAuth credentials get caught before they land in history.

## Testing

**Changes should ship with tests.** The backend runs [vitest](https://vitest.dev):

```bash
cd backend && npm test                       # vitest run — discovers src/**/*.test.ts
npm test -- src/auth/allowedUsers.test.ts    # one file
```

**No linter or formatter is configured for the TS/JS here** — `npm run build` (`tsc`)
is the only static check on backend/frontend code. For `packer/**`, `terraform/box/**`
and `deploy/**` the checks are `packer validate` and the `deploy/*.test.sh` and `packer/scripts/*.test.sh` scripts.

There's no HTTP/DB integration harness, so prefer **extracting logic into pure,
side-effect-free modules** and unit-testing those — importing a route file like
`routes/projects.ts` directly drags in a module-level `PrismaClient` plus the
tmux/slack/agentRegistry imports. See `routes/bulkPin.ts` (+ `bulkPin.test.ts`)
and `auth/allowedUsers.ts` (+ `allowedUsers.test.ts`) for the pattern: the route
handler stays a thin wrapper, the testable logic lives in its own module. DB- and
side-effect-bound behavior is covered by manual verification until an integration
harness exists. The frontend has no test runner configured yet.

**End-to-end stack** — `make e2e-up` starts Postgres, the backend, the frontend and
two stand-in boxes (real `agent/agent.js`, temp homes, private tmux servers) under
one temp dir; `make e2e-down` removes it and `make e2e-test` scripts the whole
flow. Cursor cloud agents boot with it running. Use it to check UI and box-protocol
changes in a browser before a PR; real AWS is not covered, but box provisioning
(`E2E_EC2_LAUNCH`) and the warm pool (`E2E_WARM_POOL`, `scripts/e2e/warm-pool.test.sh`)

`E2E_TLS`, `E2E_SSHD`, `E2E_EC2_BOXES`, `E2E_EC2_LAUNCH`, `E2E_WARM_POOL`, `E2E_TMUX_FAULTS`) cover
what a feature needs beyond that, and `E2E_FLAGS` sets `TERMAG_FLAGS` for the stack
(`AUTH_MODE=local` only); extend them there rather than keeping one-off overlays.
Guide: [`docs/e2e-stack.md`](docs/e2e-stack.md).

## Observability & Maintenance

- Orchestrator logs can outlive the host: `termag-otelcol.service` ships the termag units' journal over OTLP/HTTP to `OBSERVABILITY_OTLP_ENDPOINT` under the routing key `OBSERVABILITY_PROJECT`. Filter on `service.name = termag-orchestrator` and `host.id` (the instance ID) or `host.image.id` (the AMI).
- `journalctl -u termag -f` — main server.
- `journalctl --user -u termag-agent -f` — per-user agent (run as the user).
- `tail -f /var/log/apache2/error.log` — proxy + WebSocket upgrade errors.
- Status events live in Postgres (`StatusEvent`) — usable for ad-hoc queries about agent activity.
- The agent process must be restarted whenever `agent/agent.js` changes (no hot reload). On a box, the orchestrator does that when it is safe (`deploy/termag-box-update`, started over the agent's `box-update` RPC once the `box-auto-update-enabled` flag is on for the box's owner and the box is behind the current image); a developer's checkout on a branch is left alone.

## Gotchas

1. **Per-user agent must be restarted on `agent/agent.js` changes** — no hot reload. On a box, `termag-box-update.service` (`deploy/termag-box-update --when-enabled`, started by the orchestrator over the agent's `box-update` RPC when the box is behind the current image, never by the box itself) first asks the orchestrator (`GET /api/box-update/policy`, the `box-auto-update-enabled` flag for the box's owner) and does nothing unless it says yes; when it does, it pulls `main`, reconciles and restarts the agent when a tracked `agent/` file or its unit is newer than the running process — but only on a clean `main`, only with `KillMode=process` loaded, and never while a Claude runner session is live; a developer's branch, and a box with `~/.config/termag/no-auto-update`, are left alone. Stage and dev boxes still restart by hand. Forgetting this leaves stale code running and is a common "why isn't my fix taking" debug detour.

2. **`loginctl enable-linger <user>` is mandatory (Linux)** — without it, the per-user agent stops the moment the user logs out, which makes everything in the UI hang the next time termag tries to talk to that user's agent. macOS uses launchd LaunchAgents instead and has no linger equivalent.

3. **`session` table is `connect-pg-simple`'s, but it IS declared in `schema.prisma`** — model `Session`, mapped to `session`, mirroring connect-pg-simple's `table.sql`. It is there purely so schema syncs (`prisma db push`, which drops unknown tables) create and keep it under the migration DB user; on a platform with a separate migration user the server's `application` user may not be allowed to `CREATE TABLE`, so `createTableIfMissing` in `backend/src/index.ts` is only a fallback. The app never touches the table through Prisma: don't add relations to it or query `prisma.session`.

4. **Slack scopes are large** — the bot needs `app_mentions:read`, `chat:write`, `channels:manage`, `channels:read`, `channels:history`, `channels:join`, `commands`, `im:history`, `im:read`, `im:write`, `files:read`, `reactions:read`, `reactions:write`, `users:read`, `users:read.email`, and the `message.channels` + `message.im` events. Re-add any you remove and reinstall the app or `/t create` will silently fail to create channels. Without `channels:history` + `message.channels`, thread replies under Slack collaboration cards in channels never arrive (the card's Reply button still works); every DM to the bot goes to the Claude executor unless `handleCollabThreadMessage` claims it first.

5. **WebSocket upgrade ordering in Apache** — `/termag/ws/*` ProxyPass MUST come before the plain `/termag/*` ProxyPass in the vhost, otherwise socket upgrades fall through to plain HTTP and the terminal never connects.

6. **`ALLOWED_USERS` maps email→unixuser** — both columns matter. A typo in the unixuser half doesn't fail OAuth; it fails later when the per-user agent can't be reached because no such systemd user service is running. Domain-wildcard entries (`*@example.com:default-unixuser`) match any email from that domain to the same unix user — handy, but it means a typo in the wildcard half silently routes everyone to the wrong account.

7. **Project working dirs may be symlinks** — when writing tooling that walks projects, `readlink -f` to get the canonical path before doing anything path-sensitive.

8. **Claude Code hooks fire `curl ... &` (background)** — the `&` is load-bearing. Without it, every tool use blocks on the localhost POST and feels visibly slower. Don't "clean up" the trailing `&` from `deploy/claude-hooks.md`.

9. **Codex bridge subprocess is owned by the per-user agent** — termag's main server doesn't manage it. If a Codex session looks dead, check the agent's logs (`journalctl --user -u termag-agent`), not the main server's.

10. **Provider registry lives in two files and must stay in sync** — `backend/src/providers/registry.ts` and `frontend/src/providers/registry.ts`. Adding a provider on one side only produces a project that the backend will accept but the UI can't render (or vice versa). There's no shared package; the symmetry is by hand. Each entry also carries `selectable`: only `true` entries (claude, cursor, devin, pi) appear in the create-project and default-agent pickers and pass the backend's new-choice validation (`SELECTABLE_PROVIDER_IDS`, `GET /api/providers`); `false` entries (codex, gemini, augment, deepseek, mistral, and the frontend-only `human`) are **hidden, never deleted**, because existing projects and historical worktime/token rows still render through them. `backend/src/providers/registry.test.ts` asserts the two files agree on ids, names, badges and `selectable`.

11. **`agentProvider` is a string, not an enum** — Prisma will happily persist arbitrary garbage. The registry is the validation boundary; route handlers should reject providers not in the registry before writing.

12. **tmux poller patterns are provider-specific** — TUIs with a persistent input box (vibe/Mistral) look "working" to a naive idle/working detector forever. The registry's poller config has to match the actual TUI's render; if a new provider's working-time looks pinned at 100% or 0%, the regex in its registry entry is wrong before anything else.

13. **Working-time attribution is per-provider source** — Codex pulls from JSONL session files, Claude from hook events, vibe from `~/.vibe/logs/session/meta.json`. Mixing sources (e.g. counting a Claude project's hook events as if they were poller-derived) double-counts; each provider entry declares its single source of truth.

14. **Thermometers use an absolute 8h scale, not p50-relative** — when reading the UI, a half-full tube means ~4 hours of work that day, not "average for this project". This was a deliberate switch; don't "fix" it back to relative without thinking about what the tube means at a glance.

15. **Project sharing routes terminal access through the *owner's* per-user agent** — a collaborator's browser hits the backend, but the PTY lives in the owner's tmux. If a shared project's terminal won't connect, the owner's `termag-agent` is the thing to check, not the collaborator's.

16. **Context-token warnings are parsed from agent pane text, not a structured signal** — the per-user agent scans tmux pane content for provider-specific "context left" / token-budget strings and surfaces them via the status pipeline so the UI can flash a warning on the project tile. If a provider changes its wording, the warning silently stops appearing; the parsing lives in `agent/agent.js` and is the place to update.

17. **Rate-limit detection is also pane-text parsing** — same caveat as context warnings. The `rateLimited` flag is inferred from provider-specific quota/rate-limit phrases in the agent pane. If a provider rewords its rate-limit message, the project tile silently stops showing the rate-limit state; update the patterns in `agent/agent.js`.

18. **Slack `/t` executor strips `ANTHROPIC_API_KEY` from the spawned env** — `backend/src/slack/executor.ts` deliberately removes any inherited `ANTHROPIC_API_KEY` before spawning `claude`, so the subprocess uses the user's own auth (Claude Code login / subscription) instead of a stale workspace key. Don't "helpfully" add it back; doing so silently routes Slack-driven sessions onto the wrong account and burns the wrong quota.

19. **Project-list ordering is `pinned DESC, lastActiveAt DESC`** — `lastActiveAt` is bumped on status writes, not on every API touch, so a project you opened in the UI but haven't run the agent in won't float up. If recent-activity sort "isn't working," check that status events are actually arriving (Claude hooks installed, agent up) before suspecting the sort.

20. **Stale `waiting` status is auto-cleared by the per-user agent** — `agent/agent.js` watches for sessions stuck in `waiting` whose pane no longer shows a prompt and demotes them back to `idle`/`working` to match reality. Hooks and bridges aren't perfectly reliable about firing the closing event (notably Claude `Notification` → no follow-up `UserPromptSubmit` if the user dismisses outside the TUI), so the agent is the safety net. If you see a project tile flicker out of `waiting` without an obvious trigger, that's this — don't chase it as a hook bug first.

21. **Agent reconnect reconstructs sessions from the backend's view, not the agent's** — when a per-user agent reconnects (restart, network blip, laptop wake), `backend/src/services/agentRuntime.ts` replays the project/session state down to the agent so existing tmux sessions get reattached without the user re-clicking everything. The backend is authoritative for "what sessions should exist"; the agent is authoritative for "what tmux currently has." If they disagree after a reconnect (ghost sessions, missing reattach), the reconciliation logic in `agentRuntime.ts` is where to look — not the agent's own startup path.

22. **`ensureAgentSessionsAndLaunch` probes before relaunching** — on reconnect / sleep-wake the runtime first probes whether the agent's tmux sessions are still alive and only relaunches the agent process when they're actually gone. If you add a code path that calls into this and it starts double-launching agents, you've skipped the probe; don't.

23. **EC2 security-group descriptions must be ASCII** — `terraform/box` had to swap an em-dash out of an SG description because EC2 rejects non-ASCII characters there. Anything you add to `main.tf` / `variables.tf` describing AWS resources should stay ASCII-only, and so must every description `boxProvisioner` sends with `CreateSecurityGroup` / `AuthorizeSecurityGroupIngress`.

24. **Boxes are provisioned per-Unix-user** — the Packer AMI ships with a `termag` default unix user, and cloud-init renames it to the project owner's username during provisioning. Don't hardcode `termag` as the unix user anywhere on the box; reference `$USER` or the value set by cloud-init.

25. **The box AMI is discovered by tag, not by id** — `boxProvisioner`'s `DescribeImages` call takes the newest self-owned image tagged `App=termag` + `Component=box`; no AMI id is configured anywhere. Rebuilding the AMI with Packer is enough to roll boxes forward, but a stale or missing tag fails the launch with `No box AMI found (tag App=termag, Component=box)`. A user's own boxes can be pointed elsewhere by the `box-image` string feature flag (`services/boxImage.ts`: a pinned `ami-…` or a channel, the newest image tagged `Channel=<name>` by Publish AMI's `channel` input); an unusable value falls back to the published image, and the warm pool always uses the published one (`docs/box-hibernation.md`).

26. **Every project has a `main` workstream by default**. Tmux helpers and the agent runtime thread the workstream id through session naming, but legacy code paths that don't pass one will land on `main`. If you add a new code path that creates project artifacts (worktree, tmux session, status event), pass the workstream id explicitly rather than relying on the implicit `main`. Creating a non-`main` workstream auto-mirrors the project's main `Workflow` rows onto it and launches sessions; failures are returned as a non-fatal `sessionLaunchWarnings` array on the 201 response.

27. **`AUTH_MODE=local` is the only sign-in bypass, and it is loopback-only** — `/auth/login` signs in as the first `ALLOWED_USERS` identity (a `dev@<domain>` identity when there are only domain rules). `authRouter()` throws at startup unless `NODE_ENV` is `development` or `test` and `BIND_HOST` is `127.0.0.1` or `::1`, and `/auth/login` returns 403 unless the caller is on this host (`isSameHostRequest` in `auth/localLogin.ts`: a same-host nginx or Apache makes every socket peer loopback, so the gateway's peer header and forwarding headers are checked too). The old `/auth/dev-login` route, which any non-production server exposed, is gone; don't bring back a bypass that is gated on `NODE_ENV` alone.

28. **`routes/auth.ts` is the source of truth for sign-in modes** — `authMode()` defaults to `google` and only switches to `okta` (ALB header), `oidc` (in-app code flow) or `local` (e2e stack) when `AUTH_MODE` says so explicitly. `.env.example` describes all four, but read the code for behavior and the example for the variable list.

29. **The container has no local tmux — `LOCAL_SESSIONS_ENABLED=false`** — the in-process fallbacks in `services/tmux.ts` (used by `routes/projects.ts` / `services/agentRuntime.ts` only for projects with `instanceId == null`) throw `LocalSessionsDisabledError` there. A "legacy" project can therefore not be created or launched on a containerised orchestrator; pin it to a box. Don't "fix" this by installing tmux in the image — the container also has no engineer home directories or unix users.

30. **`~/.local/bin/xclip` is a termag shim, not X11 xclip** — the per-user agent installs `agent/xclip-shim.sh` there on Linux (idempotent, content-compared, on every startup) so Claude Code's Ctrl+V image paste has something to read on a box with no display. A browser paste sends the PNG over the terminal WebSocket, the agent writes `~/.cache/termag/clipboard.png` and only then types `\x16`. The shim answers exactly two invocations — `-t TARGETS -o` (prints `image/png`) and `-t image/png -o` (streams the file, then deletes it) — ignores a mailbox older than 60s, and fails like an empty clipboard for text and every other target. It shadows a real xclip if one is later apt-installed, since `~/.local/bin` usually precedes `/usr/bin` on `PATH`; rename or remove it if a box ever needs the real thing. `agent/xclip-shim.test.sh` covers the probe/read/staleness contract.

31. **`deploy/` is the source of truth, but only `termag-reconcile` makes it true on a running box** — nothing else installs `deploy/` onto the live paths outside an AMI bake, so a box whose checkout is current can still be *running* artifacts from the image it launched from. This is not hypothetical: a live box had the merged `KillMode=process` fix in `~/src/termag/deploy/termag-agent.service` while `~/.config/systemd/user/termag-agent.service` was the baked copy without it, and a 95-line `~/.local/bin/termag-status` that predated the endpoint-resolution fix — two merged fixes, neither in effect. `termag-reconcile.service` now content-compares and installs on every boot, ordered `Before=termag-agent.service` so the agent starts from the reconciled unit and nothing needs restarting. Between boots, `termag-box-update.service` (installed by the reconciler, so it reaches boxes that predate it; started by the orchestrator over the agent's `box-update` RPC when the box runs an older commit than the current box image, never by the box itself) runs `deploy/termag-box-update --when-enabled`, which does nothing until the orchestrator says the `box-auto-update-enabled` flag is on for the box's owner (`GET /api/box-update/policy`; no answer is a no, so the flag is the fleet-wide kill switch), and otherwise: `git pull --ff-only` on a clean `main`, `termag-reconcile --check` / reconcile / `--check`, `termag-hooks-update` when the owner's `~/.claude/settings.json` hook lines are behind `deploy/claude-settings.json` (reconcile never touches that file), `npm ci` in `agent/` when its lockfile changed, and the agent restart described under the per-user agent restart gotcha — so a box left alone picks a merged `agent/` or `deploy/` change up once the orchestrator asks for it. The one-time catch-up for a box whose agent predates the `box-update` RPC is `git -C ~/src/termag pull --ff-only && ~/src/termag/deploy/termag-box-update` (pull, reconcile, restart the agent when safe), run as the box user with its systemd user bus in scope. There is no SSH to a box, but every provisioned box carries `AmazonSSMManagedInstanceCore` and a live SSM agent, so from an operator session in the termag account the catch-up is one Run Command, which needs neither a key nor the Session Manager plugin: `aws ssm send-command --document-name AWS-RunShellScript --targets Key=tag:App,Values=termag --parameters 'commands=["u=termag; sudo -u $u env XDG_RUNTIME_DIR=/run/user/$(id -u $u) DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/$(id -u $u)/bus bash -lc \"git -C ~/src/termag pull --ff-only && ~/src/termag/deploy/termag-box-update\""]'`, then `aws ssm list-command-invocations --command-id <id> --details` for each box's stdout (one box: `--instance-ids i-…`). It is a one-off for boxes baked before the RPC, not a process: boxes from any later image are reached by the orchestrator's push, and the box reports its outcome (the stale-box update gotcha). The pull itself fails on a box whose git has no credential for its remote; that is what the report's `pull=fetch-failed` says. If you add a box-side artifact to `deploy/`, add it to the table in `deploy/termag-reconcile` too, or it will only ever reach boxes through a bake. `claude-settings.json` is deliberately excluded because owners edit it (its termag hook lines are brought current by `termag-hooks-update`, which `termag-box-update` runs); the reconciler only appends MetaTerm's three read-tool approvals to the installed `~/.claude/settings.json` and sets its own `mcpServers.metaterm` key in `~/.claude.json`, both with `jq`, never rewriting anything else. `termag-reconcile --check` reports drift without changing anything, which is the quickest way to tell whether a box is actually running what you think it is.

32. **First boot rewrites the baked `/home/termag` path from a bake-time index, and the index step must stay the last provisioner** — after step 2 renames the home (`mv`, then `usermod -l -d` to update the record), cloud-init fixes the symlink targets and text files that embed `/home/termag` by reading `/var/lib/termag-bake/home-paths/` and running `/usr/local/sbin/termag-rewrite-home-paths` (`packer/scripts/index-home-paths.sh` and `rewrite-home-paths.sh`). It used to find them at boot with `find -lname` over the whole home and `grep -rIl` over the toolchain dirs; on a box that walk hits a fresh EBS volume restored lazily from the snapshot, so every inode is an S3 round trip, and it took 4.5 minutes before the quick-start bake and 15.5 minutes after — past the orchestrator's 15-minute stuck-provisioning sweep — to rewrite about 200 symlinks and 3 files. Two consequences. Anything a provisioner writes under `/home/termag` *after* `index-home-paths.sh` runs is not rewritten at boot, so a new bake step that installs under the home goes before it in `box.pkr.hcl` (`packer/scripts/home-paths.test.sh` asserts the order). And the text-file scope is still the same six toolchain dirs (`.pyenv .goenv .nvm .local .cargo .config`, `SCAN_DIRS`); a file elsewhere that hardcodes the home, like the tilde-vs-absolute `~/.bazelrc` case above, is not covered — as it never was. The rename in step 2 is `mv` plus `usermod -l -d` **without `-m`** for the same reason: `-m` does the identical rename(2) and then stats every file under the home to re-own it (100,377 `newfstatat` for 100,003 files, measured), which was 4 more minutes on a quick-start box. Do not put `-m` back, and keep `box-ami-ci.yml`'s `sudo-handoff` job on the same sequence.

33. **`termag.service` runs `db:guard` before every start, and it can refuse** — `ExecStartPre` runs `backend/dist/scripts/dbGuard.js` (rules in `config/dbGuard.ts`). With a local database it refuses while `/srv/termag/DATABASE_MOVED_TO_RDS` exists (the RDS cutover wrote it; the container's copy is stale) unless `ALLOW_DOCKER_ROLLBACK` exists too, which `termag-rds-cutover rollback-to-docker` writes after copying Aurora back. On RDS (`PG_IAM_AUTH=true`) it refuses an empty or missing `users` table unless `ALLOW_EMPTY_DATABASE` exists, so an unrestored cluster never comes up as a blank termag that invalidates every box token. A termag that won't start after a database change: read `journalctl -u termag` for `[db:guard] REFUSED` before anything else.

34. **Theme settings are a JSON column validated by a module that exists twice** — `User.theme` is `jsonb` (`{}` = all defaults). `backend/src/theme/schema.ts` and `frontend/src/theme/schema.ts` are the same file kept in sync by hand, like the provider registry: the backend validates writes strictly (`validateTheme`, unknown keys rejected, the client sends the whole object so there is no server-side merge) and normalizes reads (`normalizeTheme`); the frontend normalizes again as a safety net. Adding a theme axis is a key, a default and a validator case in both copies, a CSS-variable mapping in `frontend/src/theme/apply.ts` and a group in `pages/settings/AppearanceSection.tsx` — no migration. The sidebar speed readout is no longer fed by the starfield's draw loop (`hooks/useEasedWarp.ts` steps it on a timer), so don't reintroduce an `onWarpChange` callback on `Hyperspace`: with a solid background or the hyperspace flag off the canvas is unmounted, and under reduced motion it draws one frame, so the readout would stick.

35. **Admin tokens are `agent_tokens` rows with `scope = 'admin'` and must never reach `/ws/agent`** — `registerAgent` replaces the agent for the same user/instance key, so a token that validated there would evict the user's real agent. `/ws/agent` and the gateway ext_authz checks accept only `scope = 'agent'`; `requireAuthOrAgentToken` (the agent-facing REST routes) and `cliBearer`'s `tmag_` path (`/api/cli/v1`) accept only `agent`; `requireAdmin` accepts only `admin` and re-checks that the owner is still an admin on every call. If you add a bearer-accepting route, decide which scope it takes — don't call `validateAgentToken` and ignore `result.token.scope`.

36. **Env-sourced admins are re-checked against `ADMIN_USERS` on every request; granted admins are not** — `isAdminUser` trusts `users.role = 'admin'` only when `adminSource = 'grant'`; a row with `adminSource = 'env'` must still match the live list. So a first-time sign-in on the list is an admin immediately, and removing an email demotes as soon as the process sees the new env (which, on the immutable-AMI orchestrator, means a restart — the startup sync also rewrites the row then). Env-listed admins cannot be demoted from the UI; edit the env. Granting admin to an env-listed user keeps `adminSource = 'env'` so the env stays authoritative for them.

37. **A cloud session's live status is keyed by the runner's tmux session name, not a project** — the session's Claude Code runs termag's status hooks, and the posts carry `<boxUser>-claude-runner-s<slot>-<order>-r`. `services/claudeSessions.ts` hands the frontend that name per run (`current.sessionName`) so it can read the same status map as a project pane. The ownership check in `routes/status.ts` admits those names for an instance-bound token only when they parse as runner sessions of that token's box (`isRunnerSessionOf`); a project pane under the box user's prefix is still refused.

38. **A session checkout's Bazel output base is removed by `termag-claude-runner`, by path hash** — Bazel keys the base on the MD5 of the workspace path under `~/.cache/bazel/_bazel_<user>/`, about 12 GB per checkout of a large Bazel repository, and nothing else ever removes it. The wrapper removes it (detached, after `chmod -R u+w`) when the checkout is released or kept, and sweeps bases whose workspace is gone at start, only when `DO_NOT_BUILD_HERE` names the checkout and `server/server.pid.txt` is dead. The shared `~/.cache/bazel-disk` and `~/.cache/bazel-repo-contents` are deliberately outside that root. Don't move them under it.

39. **The Review pane is a fifth session role, and the role list lives in six places** — `review` sits beside `agent`/`ctrl`/`data`/`data-ctrl` in `services/sessionAccess.ts` (`SESSION_ROLES`), `services/sessionResolver.ts`, `services/tmux.ts` (`sessionName`), the terminal-WS allowlist in `index.ts`, and the frontend `utils/sessionName.ts` + `services/api.ts`. Miss one and the pane either fails `assertSessionAccess` (400) or the browser's attach is refused as a session/project mismatch. The pane rides on the agent workflow: `agentRuntime.stopAgentSessions` kills it with the agent/ctrl pair (archive, workflow delete, workstream remove) and the rename route renames it, so a new teardown path that bypasses `stopAgentSessions` leaves Devin running unseen. Which PR a review pane is looking at is remembered only in backend memory (routes/review.ts and the review sweep); the tmux session is the durable thing, so after a backend restart the sweep's discovery reads the number back from the `@termag-review-pr` option or the launch echo, and a pane older than both ranges shows none. Starting a review uses only RPCs every deployed agent already has (`tmux-has-session/kill/create/send-keys`); the gh-based guess needs the newer `git-pr-info` RPC and falls back to the pane capture and milestone on an older agent — restart the per-user agent to get the branch-based guess. The review pane has no live status for any reviewer (Claude's hooks report on the agent session, not on `-review`), so its state is read off the pane's bottom chrome, per reviewer (`services/reviewers.ts` `classifyReviewerPane`: approval/trust/theme dialog → "needs an answer", spinner or `esc to interrupt` / `ctrl+c to stop` → "reviewing", bare prompt → "ready"); a CLI update that changes its chrome shows up as a wrong dock state. The reviewer rides in the `@termag-review-pr` option as `<pr> <url|-> <reviewer>` (older values decode as Devin) and in the sweep record; with neither, the probe reads it off the pane's foreground command. Claude reviews in `--permission-mode plan`, which refuses every write including `gh pr review`, so posting a Claude review means leaving plan mode in the pane; Cursor runs `--mode plan --auto-review` (plan alone stops on every `gh`). Since the review ring, that state is written ONLY by `services/reviewSweep.ts` (5 s sweep + tmux-list discovery) as `AgentStatus.review` on the AGENT session's status and pushed over /ws/status like `milestone` — never poll GET /review for it; the browser posts `POST /review/seen` when the review terminal takes focus while done, which clears the sidebar's ring. Shared viewers get the review without its URL, same as the milestone. The prompt is written to `~/.termag/review-prompts/<session>.md` on the box (`write-file`, 0600) and handed to Devin with `--prompt-file`, never typed through shell quoting: the dialog's **Edit prompt** lets the user change the body under a fixed, non-editable first line naming the PR and its repository (`reviewPromptHeader`; the repository comes from the PR URL or the workstream's GitHub remote, `services/reviewRepo.ts`, and a bare number in a directory with no GitHub remote is refused, since the reviewer would guess among the box's clones), which is also what `prFromLaunchEcho` reads back from Devin's re-print of the prompt — change that line and PR recovery on older agents breaks — and above a fixed last line (`reviewPromptFooter`) telling the reviewer to end anything it posts to GitHub with "Reviewed by Devin", since it posts with the user's own gh login. The body's default is the first usable template of the repo's `.termag/review-prompt.md`, `~/.config/termag/review-prompt.md`, `~/.termag-review-prompt.md` (the top-level form is the one a script-less dotfiles repo can deliver: those are linked top-level only), else the built-in one. The launch line names the prompt file through `$HOME`, not the backend's absolute path, because `write-file` goes through the agent's `path_remap`. Devin runs in `--permission-mode smart` because its default `auto` stops on the first `gh pr view` for approval; smart auto-runs safe commands **and** workspace edits, so the review staying read-only rests on the prompt's instruction — there is no per-session deny rule in Devin, only `~/.config/devin/config.json` and `.devin/config*.json` in the repo, neither of which termag writes.

40. **An ask run's publish checks bind only runs that behave, because the run holds the box token** — the sandbox (`deploy/termag-subagent-run`) keeps the run off the owner's home, IMDS, sudo, docker and the internet, but the Claude gateway and the GitHub broker share one in-VPC address and both accept the box token the run needs for the model. So a run that deliberately goes around the bundle path could reach the broker with the owner's GitHub access; the orchestrator's checks in `services/askPublish.ts` (protected paths, author = asker, secret scan, no force, draft, branch fixed server-side as `termag-<asker>/<thread>`) hold for everything that comes back through `PUT …/ask/runs/:id/bundle`. A per-run, gateway-only token scope is the fix, deliberately deferred. Don't widen the sandbox's `IPAddressAllow` or add `gh`/`git push` to its allow list without that. The run sees committed code only: a first turn fetches the base (the merge-base with the branch's upstream) over `file://`, so uncommitted edits and untracked files never cross, and an ask about unpushed work answers about the remote's version.

41. **Never build a shell string to type text into tmux — spawn `tmux` with an argv array** (`execFile('tmux', sendKeysArgv(...))`, builders in `agent/tmux-args.js` and `backend/src/services/tmux.ts`). The shell-string version single-quote-escaped the text *and* then ran it through `shellEscape`, so every `'` was typed as the four characters `'\''`: MetaTerm `send_keys`, Slack/Discord `/t` and the agent launch commands all went through it. Two tmux details that the builders encode: `--` must precede the text so a payload starting with `-` isn't parsed as a flag, and `-l` applies to every argument of one invocation, so in literal mode Enter is a separate `send-keys`. `tmux-capture` takes an opt-in `styled` flag (`capture-pane -e`) for callers that need to tell dimmed ghost-text from typed input; the default stays plain because the Slack/Discord formatters expect unstyled text.

42. **A provider that runs on boxes must post its own status, with a registered `source` — the tmux poller only sees the orchestrator's tmux** — `services/tmuxPoller.ts` reads local `capturePaneText`/`isAgentRunning` and never the agent RPCs, so poller providers (cursor, devin) have no live status on a box; and `services/status.ts` books a status whose `source` is unknown as Claude, so a hooks-style provider needs an entry in `statusSources` and must send it. pi is the worked example: its `launchCommand` runs `pi -e` with `deploy/pi-ext/termag-status.ts` (installed by termag-reconcile), a pi extension whose pure reducer (`termag-status-core.ts`, tested from `backend/src/providers/piStatusExtension.test.ts`) turns pi's lifecycle events into `termag-status … --source pi-ext:pi` calls; `termag-status` grew `--source/--reason/--message/--notify`, a `meta` mode and `--print-payload` for exactly this, while a plain `termag-status working` still sends the source-less payload the Claude hooks rely on. Three things that are deliberate: the registry's new `resumeCommand` (`claude --continue`, `pi --continue`) replaced the Claude-only relaunch special case in `agentRuntime.reconstructAgentSessions`; and a failed model request shows up as a `waiting` status with a `rateLimited` badge and a remedy naming the HTTP status. pi runs tools without approval prompts.

43. **`hibernated` is not `stopped`, and hibernation is fixed at launch** — EC2 only takes `HibernationOptions` on `RunInstances`, so `Instance.hibernationConfigured` is written once and every older box keeps plain Stop until it is replaced; the UI only offers Hibernate when it is true. Three things gate it: the `box-hibernation-enabled` feature flag (boolean, default off; an image a user's `box-image` flag chose opts in on its own), an AMI tagged `Hibernation=supported` (packer `var.hibernation`, default off, `scripts/enable-hibernation.sh`), and the type's `HibernationSupported`; the root then grows by the RAM size because hibinit-agent's swap file lives on it. Keep the two power-down statuses apart: a `stopped` box has lost its RAM and is the one a start may replace, a `hibernated` one must only be resumed. A hibernate EC2 refuses falls back to a plain stop with a note on the row, and the power sweep resumes and re-hibernates any box hibernated `BOX_HIBERNATION_REFRESH_DAYS` (55) because EC2 supports at most 60 (`docs/box-hibernation.md`). The flag is read twice (`services/boxHibernationFlag.ts`): the warm pool evaluates it for a fixed `box` context, `termag-warm-pool`, so it follows the fallthrough and feeds the pool spec hash (flipping the fallthrough rolls the pool); a user's box evaluates it for the owner, and an owner whose value differs from the pool's skips the claim and launches fresh, like a `box-image` user.

44. **A stale box is asked to update by the orchestrator, behind `box-auto-update-enabled`, and "current" means the newest box AMI's commit** — `services/boxUpdate.ts` compares each connected owned box's `agentCommit` (the commit the agent process runs, from its hello; read once per process, so a checkout pulled without a restart still reports the old one) with the `TermagSha` tag of the newest published `Component=box` AMI, and sends the agent's `box-update` RPC (which starts `termag-box-update.service`, the same unit the box's six-hourly timer runs) when they differ: a minute after the hello and on a 30-minute sweep, leader work. The AMI tag is the target because `check-box-ami` in `publish-ami.yml` bakes a new box image exactly when `main` changed in a path that executes on a box, so there is no second copy of that path list and no GitHub credential on the orchestrator; the cost is the bake's lag (up to a few hours) and a harmless no-op push after an age-out rebake. One push per (box, target), in memory: a box that refuses the pull (a branch, a dirty tree, `~/.config/termag/no-auto-update`) is not asked again until the target moves. The flag's context is the owner + box multi-context (`boolVariation(key, user, fallback, box)`), so a rollout can start with one box. External boxes and agents without `box-update-v1` are skipped; the flag is read before the AMI, so a fleet with the flag off costs no `DescribeImages`. The push is the orchestrator's half; the box's half is one line back: `termag-box-update` posts `POST /api/box-update/report` at exit (instance token on stdin, a trap after the policy gate, so a policy no and `--check` post nothing), one word for the outcome — `failed` (any step failed, whatever the others did), `updated`, `deferred` (restart put off: a runner, `KillMode`), `skipped` (the pull refused: branch, dirty, detached), `current` — plus one token per step (`pull=pulled:3 reconcile=clean deps=unchanged agent=deferred:runner hooks=updated`, the vocabulary `parseBoxUpdateReport` accepts; `hooks` is optional, older scripts omit it) and the commit before and after. The orchestrator logs it as one `[BOX-UPDATE] <box> (<owner>) reports …` line (shipped to Observability, where the box journal is not) and writes it on the box row (`last_update_*`), so the admin Fleet list shows a *last update* column and the System page counts boxes by the last outcome they reported in the day beside the target (`boxUpdates.boxesByLastOutcome24h`; a row keeps one report, so these are boxes, not runs); Signals raise `box_update_failed` (a `failed` within a week) and `box_update_deferred` (a `deferred` older than a day, unless the connected agent already runs the pulled commit: a reboot restarts the agent without a new report). The agent's hello also carries `agentCommitAt` (`git show -s --format=%cI HEAD`), so Fleet sorts boxes by how old their agent build is against the newest image's bake date, and the detail card says *Nd behind*. A wrapper from before the report posts nothing and the row says *never reported*; a box whose orchestrator predates the route logs `report: not posted … answered 404` and carries on.

45. **Host homes reach a new orchestrator only after the old one terminates, and nothing may touch a host account before that** — the host data volume (`/srv/termag`, `/home` bound from it) is attached after boot by `termag-data-attach.service`, which waits for the volume to be `available` (blue holds it until the ASG terminates it), mounts it, re-adopts the accounts and only then writes `/run/termag/host-storage-ready`. Until then `ensureHostSetup` mints nothing and `hostAgentUnavailableResponse` answers 503, and `deploy/termag-host-setup` exits 3 unless `findmnt` shows `/home` as the volume's bind: an account created on the root disk's `/home` takes a UID a volume home uses and vanishes under the mount. Keep both guards; a new path that creates host accounts or host tokens goes through `ensureHostSetup`. Three things are deliberate. The unit is `Type=simple`, never oneshot: its start job would hold `multi-user.target` and cloud-final, which starts the backend, so green would never serve and blue never release the volume. The script never detaches the volume from another instance, however long it waits; a stuck attach is the runbook's (confirm the holder is gone, snapshot, attach by hand, `systemctl restart termag-data-attach`). Nothing snapshots the volume on a schedule: the runbook takes a manual snapshot before the first handoff deploy and before any manual attach. And there are no fstab entries for the volume, because a boot that bound `/home` before the mount would bind an empty directory. The ASG is pinned to the volume's AZ for the same reason the volume can't follow it.

46. **The daily briefing runs on the owner's box, never on the orchestrator, and is opt-in** — the backend holds no model credential: `services/briefing/runner.ts` asks a `ready` EC2 box whose agent announces both `tmux-create-command-v1` and `briefing-v1` to start a one-shot tmux session, `<boxUser>-briefing-<id>-r` (the `-r` tail keeps it from parsing as a project pane), whose only process is `~/.local/bin/termag-briefing <id>`. The wrapper fetches the prompt from `GET /api/briefings/:id/job`, runs `claude -p` with no built-in tools (`--tools ""`), only its own metaterm MCP server (`--strict-mcp-config`), `--permission-mode dontAsk` and the MetaTerm read tools allowed — `--allowedTools` alone would merge with the owner's settings grants — plus `METATERM_SEND_KEYS=off` and `TMUX`/`TMUX_PANE` unset (so `termag-status` hooks post nothing for it), and posts the result to `POST /api/briefings/:id/result`; both routes answer only the token of the box the run was placed on. It never starts a stopped box or claims a warm one: no box ready means a `skipped` row, which the scheduler retries each tick until the local day ends. The scheduler is leader work and `briefings.scheduleKey` (`<userId>:<local day>`, unique) keeps it to one scheduled run per user per day across overlapping processes; any start holds a per-user advisory lock around its running-run check, so there is one run at a time per user. `User.briefingSchedule` `{}` means off; turning it on needs a timezone. The window is "since the previous done briefing", or the start of the previous local day on a first run or when the previous one ended over four local calendar days ago (`stale`; days, not hours, so a weekend stays whole), and every surface leads with its label. The ledger (`GET /api/briefings/ledger`, MCP `activity_ledger`) answers an index by default and one session in full with `projectId`/`workstream`, both from one build cached for 25 minutes for a briefing run and 5 for an on-demand read (`services/briefing/ledgerCache.ts`), with the run's totals also kept on its row (`rememberLedger`) for a result that lands on another process: a whole ledger runs past Claude Code's MCP output cap on a busy day, and the run has no Read tool for the file it spills to. It reads transcript digests and pane tails from the caller's OWN projects only; the fields it marks untrusted are never stored. A box shows up as "running an older termag" until its agent restarts (`briefing-v1`) and `termag-reconcile` installs the wrapper and the two extra read-tool approvals.

47. **A PR or commit made on a box is marked as termag's, and authorship is never touched** — PR bodies go through `deploy/termag-pr-body` (installed to `~/.local/bin` by termag-reconcile), which wraps the body Cursor-style in `<!-- TERMAG_PR_BODY_BEGIN -->` / `<!-- TERMAG_PR_BODY_END -->` and appends a hidden `<!-- termag: box=<EC2 instance id> project=<name> [ask=<thread>] -->` line and a `<sub>Opened from termag</sub>` footer. The one PR termag opens itself is an ask's draft PR, whose body `services/agentMessages.ts` builds in the same shape and `services/askPublish.ts` sends. The broker only sees requests through Envoy's ext_authz, which cannot rewrite a body, so agents' `gh pr create` reaches the wrapper only through the `termag-pr` skill (`deploy/claude-skills/`, `deploy/pi-skills/`); a provider without skills, or a human typing `gh`, produces an unmarked PR. The skill has the agent write the title and body to files with its file tool and run `deploy/termag-pr-create TITLE_FILE BODY_FILE [flags]`, a fixed argv that hands both to `gh` without a shell ever parsing them: a title or body typed into `--title "..."` or a heredoc is repo-controlled text the agent's Bash tool would execute, and pi runs Bash unprompted. Keep any new example in the skill free of title or body text. Commits get `Generated-by: termag` from `deploy/termag-commit-msg`, the `commit-msg` hook of the box user's git template (`init.templateDir`, in `~/.config/git/config`), which termag-reconcile also copies into existing `~/termag/projects/*` repos that have no `commit-msg` of their own. The project clone (`agent/project-clone.js`) hides the global config from git, so it reads `init.templateDir` itself and passes it as `--template`. It is deliberately not a global `core.hooksPath`: `pre-commit install` refuses to run while one is set. A repository with its own `commit-msg` gets no trailer unless it chains to ours (pre-commit's `commit-msg.legacy` does), an owner's own `init.templateDir` turns the whole thing off, and `git config termag.trailer false` turns it off per repo or globally. No labels are created or added.

48. **An agent spawn's brief is claimed by the first launch, by spawn id or child project id, never by name** — `POST /api/spawns` writes the `agent_spawns` row and the prompt file (`~/.termag/spawn-prompts/<id>.md`, `write-file`) *before* it creates the workstream or project. `ensureAgentSessionsAndLaunch` then asks `claimSpawnLaunch` (`services/agentSpawnStore.ts`) right before typing. The spawn route's own create passes `spawnId` through `createWorkstreamFor` / `createProjectFor`. Every later launch claims an unclaimed `starting` row by the child's project id and workstream: the deferred launch after a box's hello or a clone, and reconnect reconstruction, which claims too, so a first launch that was skipped (pane busy, probe failed) still starts on its brief instead of `resumeCommand`. A failed send hands the claim back (`releaseSpawnLaunch`). The prompted line still goes through `launchCommandFor`, so the `termag-agent-otel` wrapper applies. A claim by id must also match the child project, and the cookie `POST /api/projects` drops a body's `spawnId`, so a stray id can never land a brief in another project. An agent token must name its own `agent` pane (`from.session`), or the depth and per-parent limits have nothing to count. The `agent-spawn-enabled` flag is read for the box the child runs on. Workstream create is `createWorkstreamFor` in `routes/workstreams.ts` (shared by the cookie route and spawns; it repeats the parked/unready checks for callers without the middleware) and takes a `provider` that replaces main's on the new agent workflow. The parent nudge (`services/agentSpawnSweep.ts`, leader work; a report clears `nudgedAt` and the sweep reads only rows where it is null) types a FIXED line, only into an `idle` parent pane (never `waiting`: that is an approval prompt the line would answer), never while the owner typed in that project in the last two minutes, and never the child's report text. `list_spawns` and `report_back` are pre-approved by `termag-reconcile`; `spawn_agent` never is, and pi's registration switches it off (`METATERM_SPAWN_DEFAULT=off`). Spawn limits are tuning parameters: the `agent-spawn-limits` JSON flag (user + target box; malformed keys fall back one by one to `DEFAULT_SPAWN_LIMITS` in `services/spawnLimits.ts`), checked by `admit` in `routes/spawns.ts` after the target box is known. A box over its hot thresholds, judged from its latest host sample (a sample older than 15 min refuses nothing), or at `boxCapacity` (null = no cap, the default), gets 409 `box_busy` / `box_capacity`. Every request and refusal is logged in `spawn_events` with a one-word reason (90-day retention). `host_samples` keeps the 5-minute box history (30 days) with `liveAgents` from `tmux-list`, and cores and memory from `agent/host-sample.js`, so a box's load-per-core check starts only after its agent restarts. A spawn's `endedAt` (the minute sweep) is what "running" counts; an offline or parked box never ends its spawns.

49. **A handoff types only fixed lines, and a restart's relaunch is claimed like a spawn's brief** — the route writes an `agent_handoffs` row; `services/agentHandoffSweep.ts` (leader work, 5 s; rules in `handoffStep`, `services/agentHandoff.ts`) moves it `requested → writing → written → resetting → done`, claiming each step with `updateMany` on the state. It types into the agent pane only when it is `idle` (never `waiting`), and an agent-started handoff also waits out the owner's two-minute typing quiet. What it types is fixed text plus the handoff id: the "write a handoff" request, `/clear` or `/compact <focus>`, and the read-in line naming `~/.termag/handoffs/<id>.md`; the handoff text itself only reaches the next agent through that file (`write-file`, 0600, after `findSecretsInText` and a 32 KB cap). Only an agent the metaterm tools reach can be handed off from (registry `handoffWriter`: Claude and pi), since it must write its handoff; Cursor and Devin can only be restarted into. `clear`/`compact` need the provider's `clearCommand`/`compactCommand` (Claude only today); anything else, or a switch of provider, falls back to `restart`, which is Switch agent's sequence (row, `stopAgentPane`, `markAgentPaneStopped`, `ensureAgentSessionsAndLaunch`). The prompted line comes from the registry's `promptLaunch`, which spawns use too. `ensureAgentSessionsAndLaunch` and reconnect reconstruction call `claimHandoffLaunch` (`services/agentHandoffStore.ts`) after the spawn claim, so a box that drops between the kill and the launch still starts on the handoff instead of `resumeCommand`. Both launch paths take a per-pane lock (`withPaneLock`, held 1 s past a launch that typed), so two launchers reaching one pane at once type once; tests that launch into one pane repeatedly call `setPaneLaunchSettleForTests(0)`. `handoff_written` is always listed but never pre-approved; `handoff` is never pre-approved, and pi's registration switches it off (`METATERM_HANDOFF_DEFAULT=off`).

50. **New projects get a repo and an initial commit automatically, and the helper that does it lives in two files** — a freshly `git init`-ed project has an unborn HEAD, and `git worktree add ... HEAD` refuses to resolve one ("invalid reference: HEAD"), so branching off a new project used to require the user to commit by hand first; a project created with no agent workflow never even reached the `tmux-create` that ran `git init`, so its first branch-off failed with "not a git repository" instead. `ensureProjectRepo` (git init when needed, then the initial commit) runs where the wiki files are seeded — agent `init-wiki` (unless the message says `initRepo: false`, which MetaTerm does), backend `ensureProjectDir` only with `initialCommit: true` — and again as a backstop before `worktree add` when the backend sends `initRepo: true`, so projects created before this get fixed the first time they branch off. **Not in `tmux-create`, and never ahead of a repo clone**: the pane checkout (`buildCloneCommand`) fetches into the init-ed dir and runs `checkout --track origin/<default>`, which fails if a local first commit already owns that branch name. The setup gate (`services/sessionGate.ts`) does NOT cover this: a pane checkout moves `setupStatus` to `none` as soon as it is typed, so workstream create is allowed while the fetch runs. The decision is the backend's, from `repoUrl`: `createWorkstreamFor` sends `initRepo: !project.repoUrl` (and answers 409 `CHECKOUT_NOT_LANDED` instead of git's unborn-HEAD error), and `init-wiki` is only ever sent for a project with no `repoUrl` (Start empty and un-archive clear it). The helper itself has no remote check, on purpose: git state can't tell an in-flight clone from an abandoned one (Start empty after a failed checkout leaves `origin` and no commits), and a remote check left the abandoned one unable to branch off. An older backend sends no `initRepo` to `git-worktree-add`, so the agent skips the backstop. It only commits into a repo whose top level *is* the project dir, so a project dir nested inside an unrelated repo is left alone, and it falls back to a `termag` author identity only when the host has none. The logic is duplicated in `backend/src/services/gitRepo.ts` and `agent/git-repo.js` — same reason as the provider registry: the agent ships standalone with no build step, so keep the two in sync by hand.
