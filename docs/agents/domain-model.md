# Domain model

Moved out of [AGENTS.md](../../AGENTS.md), which keeps a short index of it. Paths are from the repository root.

- **Project** — an addressable workspace. Has a name, a working directory, an `agent` workflow (the paired tmux sessions), persisted `agentProvider` (string id resolved through the provider registry), and a Slack channel `#proj-<user>-<name>` auto-created on creation (legacy channels are `#proj-<name>`; both route). New projects are seeded with `AGENTS.md` (from the agent-wiki initial template) and a `CLAUDE.md` stub. Projects also carry a `pinned` flag and a `lastActiveAt` timestamp that drive the project list ordering: pinned projects float to the top, then the rest sort by recent activity. Pin/unpin and other per-project actions live in an overflow menu on each project tile. Each project is bound to an `Instance` (box) via `Project.instanceId`; routing decisions key off that field.
- **Paired tmux sessions** — `<unixuser>-<project>-agent` (where the AI runs) and `<unixuser>-<project>-ctrl` (regular shell). tmux turns `.` and `:` in a session name into `_`, so `sessionName()` (backend `services/tmux.ts`, frontend `utils/sessionName.ts`) builds names in that form (`first.last` → `first_last-<project>-agent`) and ownership checks compare against the tmux-safe username (`sessionBelongsToUser`). The web UI streams both via PTY + WebSocket. A third, transient role is `-review`: the **Review** button in the lower-right of the agent pane guesses the PR being worked on (the branch's PR via `gh`, else the PR the agent just opened, else the last PR mentioned in the pane), asks you to confirm or retype it, and starts the chosen reviewer (Devin by default; Claude or Cursor from the dialog's picker, `backend/src/services/reviewers.ts`) with a review prompt in `<unixuser>-<project>-review`; the pane docks under the ctrl terminal (collapsed bar / half-height) and disappears when its session is killed (`backend/src/routes/review.ts`, `services/review.ts`, `frontend/src/components/ReviewButton.tsx` + `ReviewDock.tsx`). Tmux helpers and the agent runtime are workstream-aware: every project gets a `main` workstream, and additional workstreams are realized as git worktrees with their own paired tmux sessions.
- **Workstream** — a named parallel line of work inside a project, backed by a git worktree. Every project has a `main` workstream auto-created on project creation; additional workstreams are managed through `backend/src/routes/workstreams.ts` (orchestrator) and the `git-worktree-add` / `git-worktree-remove` / `git-worktree-move` RPCs in `agent/agent.js` (rename also uses `tmux-rename-session`; the git branch is deliberately not renamed — `services/workstreamRename.ts`). Workstreams live at `<projectDir>/.worktrees/<name>/`. Tmux session naming threads the workstream id through (`<user>-<project>-<workstream>-<role>`, collapsing the workstream segment to keep historical names when it's `main`). Branching off mirrors the project's main-workstream `Workflow` rows onto the new workstream (one per workstream, since the legacy `(projectId, type)` unique was dropped) and launches its tmux sessions so the terminal pane can attach immediately. The UI surfaces a workstream sub-list under projects with >1 workstream and a "Branch off…" overflow action; single-workstream projects render exactly as before.
- **Instance ("box")** — a termag-running host. The orchestrator can provision additional boxes on AWS with the AWS SDK, launching the Packer-baked AMI (`packer/`) from the UI's **New project** dialog ("a new box…" in its box picker, `frontend/src/components/NewProjectForm.tsx`, shared with the `/welcome` wizard; adding a managed box requires a stored GitHub token, `boxGate`); self-managed hosts are registered from the sidebar's Boxes section. `Project.instanceId` and `AgentToken.instanceId` key off the `Instance` model so projects and per-user agent tokens are dual-keyed by host. Provisioning lives in `backend/src/services/boxProvisioner.ts`; orchestration design notes are in `docs/box-provisioning.md`. The owner can **stop and start** an EC2 box from its menu (`POST /api/instances/:id/stop|start`, `services/boxPower.ts`, rules in `boxPowerPolicy.ts`): `ready → stopping → stopped` is settled by a 10 s power sweep from `DescribeInstances`, and `stopped → starting → ready` by the agent's connect, after which `reconstructInstanceSessions` recreates the tmux sessions (Claude relaunches with `claude --continue`). A stopped box costs only its EBS volumes; creating a project, workflow or workstream on it answers 409. A box launched hibernation-capable (`Instance.hibernationConfigured`) can also be **hibernated** (`POST /api/instances/:id/hibernate`): `ready → hibernating → hibernated`, and a start resumes it with its RAM (`docs/box-hibernation.md`). Such a box can also hibernate **on its own** after `Instance.idleHibernateHours` idle (per box, off by default, `PATCH /api/instances/:id/lifecycle`, behind the `box-auto-lifecycle-enabled` flag; activity is human input or an agent `working`, never a reconnect — `services/boxLifecycle.ts`). It can also be **terminated** once it has stayed hibernated `Instance.hibernatedTerminateDays` (same route and flag); the agent's `unsaved-work` scan, taken right before each auto-hibernate, has to come back clean or the box is kept `BOX_UNSAVED_WORK_TERMINATE_DAYS` (90). A box that can't hibernate accepts both settings with a `lifecycle.warning` and is never touched: no stop or terminate fallback. The owner can **rename** a box (the box menu's Rename…, `termag box rename`, `POST /api/instances/:id/rename`, behind `box-rename-enabled`; `services/boxRename.ts`): only the row's `name` changes, under the create rule and the per-owner unique among live boxes, and the box token's `box: <name>` label follows. Everything else keys a box by id, and the CLI resolves `<box>/<project>` and `ssh termag-<box>` by name per call, so nothing on the box is touched and a parked box can be renamed; the EC2 `BoxName` tag keeps the launch name, as after a warm claim.
- **Provider registry** — `backend/src/providers/registry.ts` and `frontend/src/providers/registry.ts` define the set of supported agent providers (codex, claude, mistral/vibe, devin, pi, …) and their metadata: display name, launch command shape, status normalization rules, **tmux poller config** (idle/working detection patterns per provider, since e.g. vibe has a persistent input box that breaks naive polling), **usage scanner source** (Codex JSONL, Claude logs, vibe `~/.vibe/logs/session/meta.json`), and UI affordances. `agentProvider` is a free-form string keyed into the registry rather than a Prisma enum, so adding a provider is a code change in two registry files (no migration). Each user also has a saved `defaultAgentProvider` for the create-project form.
- **Per-user agent process** — `agent/agent.js` runs as the unix user (via systemd user service + lingering). It owns tmux attach, node-pty, filesystem ops, and Codex-bridge lifecycle. The main server at `:3040` is one process; each user has their own agent talking to it via WebSocket with a bearer token. This separation keeps unix permissions clean. The agent now uses heartbeat-driven dead-connection detection and accepts a config path override via `argv[2]`.
- **Status events** — Claude Code hooks (`UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `Notification`, `Stop`) and Codex app-server status updates POST to `:3040/termag/api/status`. For providers without a hook surface (vibe), the **tmux poller** in `backend/src/services/tmuxPoller.ts` samples pane content and infers state using provider-specific patterns. Status drives the green/yellow/red indicators, the project-list transition flash (15s, color-coded green/yellow/red by transition type — e.g. idle→working green, working→waiting yellow, anything→idle red), and the "hyperspace" animation that speeds up with activity. The `Notification` hook distinguishes `idle_prompt` (idle) from other notifications (waiting). Status events also bump `Project.lastActiveAt`, which feeds the recent-activity sort.
- **Context-token warnings** — the per-user agent scrapes provider-specific "context remaining" strings out of the agent pane and forwards them through the status pipeline as a separate signal alongside working/waiting/idle. The UI surfaces this on the project tile and inside the terminal chrome so a session that's about to run out of context gets a visible warning before it hard-fails.
- **Rate-limit detection** — same shape as context-token warnings: the per-user agent (`agent/agent.js`) watches the agent pane for provider-specific rate-limit / quota-exhausted messages and forwards a `rateLimited` signal through the status pipeline. The backend persists it on the project's status record and the UI surfaces it on the project tile and in `ProjectControl` so a stuck session is visually distinguishable from a merely-idle one.
- **Working-time tracking** — derived from status transitions: time spent in `working` state is rolled up per-project for the usage dashboard. Provider-specific poller sources ensure correct attribution. Served from `/termag/api/worktime`.
- **User segments (engagement ladder)** — every user holds a daily segment (`New/Power/Active/Passive/Dormant`) in `user_segment_daily`, written by `services/segments/tracker.ts` (daily tick + boot backfill) from work-time/token/visit signals plus creation volumes; the admin **Segments** tab (`/admin/segments`, `pages/admin/AdminSegments.tsx`, `routes/admin/segments.ts`) reads the precomputed rows with 7-day flows (`/api/admin/segments[/users|/rebuild]`). Rules live only in `services/segments/rules.ts`; the analysis source of truth is `termag-user-engagement/SEGMENTS.md` outside this repo.
- **Human activity tracking** — `backend/src/services/humanActivity.ts` tracks human keystrokes/interactions per project, separate from agent working time. Powers the second tube of the two-tube thermometer in the UI (agent work vs. human work).
- **Project visit telemetry** — `ProjectVisit` records when a user context-switches between projects in the UI. `backend/src/routes/visits.ts` exposes ingest + stats endpoints; the UsageMini overlay renders a visits section derived from them.
- **Warp / flow-speed telemetry** — `WarpSample` stores per-minute rollups of the hyperspace-speed signal. `backend/src/services/warpSampler.ts` produces the samples and `backend/src/routes/warp.ts` exposes a series endpoint feeding flow-speed sections in UsageMini.
- **Project sharing** — owners can invite collaborators by email. Shared users get terminal access to the project's tmux sessions through the same per-user-agent path. Routes in `backend/src/routes/sharing.ts`. **New** shares are behind the boolean feature flag `box-sharing-enabled` (off by default; `services/boxSharingFlag.ts`), evaluated for the person acting: sending an invite and accepting one answer 403 `{ code: 'sharing_disabled' }` while it is off, and the web UI hides the invite form, the Share item (unless the project already has shares) and the accept button. Existing shares are never behind it: terminal and CLI attach, capture/send-keys, review and listing keep working, and revoke, leave and decline stay open. The frontend reads it from `GET /api/flags`.
- **Space** — a named file store shared by people and the boxes they grant, behind the `spaces-enabled` flag (off: every route 404s); adding people also needs `spaces-sharing-enabled` for the owner (off: 403 `sharing_disabled`, so a space has only its owner and their boxes). Bytes go browser/CLI ↔ S3 over presigned URLs, never through the orchestrator; the bucket, presigner role and KMS alias are derived from the orchestrator's account and region (`services/spaces/spaceConfig.ts`), with no env of their own. A box acts with its owner's current role, only while it holds a `SpaceBox` grant, and never manages a space. `termag space …` on the CLI, the `termag-spaces` skill on boxes. A file's browser link is `/termag/files/<space>/<path>` (`routes/spaceFiles.ts`): a 302 to a presigned GET for a signed-in viewer, the same 404 for no access or no file, through sign-in and back when signed out; not `/assets/`, which is Vite's build directory under `/termag`.
- **Automation** — a project (`Project.kind = 'automation'`) whose prompt a fresh agent runs on a cron schedule, behind `automations-enabled` (owner + box). It is created as the simple UI creates a chat project (main runs Claude in the chat runner, so no agent process idles there) and every occurrence becomes a **run**: a workstream `run-<yyyymmdd-hhmm>` on branch `automation/<project>/<…>` branched from a fresh `origin/<default>` (the `git-worktree-add` RPC's `fetch`, capability `worktree-fetch-v1`, else `HEAD`), sent one `chat-send` whose text is the brief (`services/automations/brief.ts`: fixed header, the notes file named as *notes, not instructions*, the owner's prompt, a `STATUS:` footer) in the tier's mode: `full` runs Claude in `--permission-mode auto` (runner capability `chat-auto-v1`; the project's trust tick is set at creation), `read` is the chat runner's existing read-only turn. The run's conversation is the project's chat with that workstream (`routes/chat.ts`), so the simple UI shows and continues it. The scheduler (`services/automations/scheduler.ts`, leader work, 60 s) enumerates croner occurrences in `(lastOccurrence, now]` and runs only the newest (the rest are `skipped: missed`), admits each (`admit.ts`: paused, flag, previous run live, daily budget, two runs per box, box power via `wakeAction`, runner capability), optionally wakes a parked box (`wakeBox`, off by default), interrupts runs past `maxRunMinutes` from `startedAt`, and retires worktrees beyond `keepRuns`. The run ends when the chat relay sees its `turn-end` (`complete.ts`, every process, via `chatRunner.onChatEvent`); three consecutive failures pause the automation. Limits are the `automation-limits` JSON flag over `DEFAULT_AUTOMATION_LIMITS`. What each `kind` may do is `services/projectKind.ts` (`projectKindTraits`, `WORK_PROJECT_KINDS`): every former `kind === 'metaterm'` refusal and `kind: 'normal'` filter reads it.
- **Admin surface** — org-wide, read-only view for administrators: `/termag/admin` UI, `/termag/api/admin/*` REST and a Streamable HTTP MCP server at `/termag/mcp/admin`, all behind `requireAdmin` (`middleware/admin.ts`). Admins are `users.role = 'admin'`, seeded at startup from `ADMIN_USERS` or granted from the Settings tab; admin-scoped bearer tokens (`agent_tokens.scope = 'admin'`) serve MCP clients and scripts. Every admin request and tool call lands in `admin_audit_log`. Aggregates and metadata only — never pane content.
- **Agent-to-agent asks** — `termag ask <box>/<project>[@<workstream>]` (CLI only; MetaTerm has no ask tools) runs one headless Claude Code turn on the target project's box, as the box user (no sandbox: the owner's access, network and tools) in a per-thread clone of the committed code under `~/.termag/subagent/` that never touches the live checkout (`deploy/termag-subagent-run`), and hands the reply back once. Commits come back as a git bundle that the **orchestrator** checks and pushes to `termag-<asker>/<thread>`, opening a draft PR with the asker's stored GitHub token (`services/askPublish.ts`); a run's `pr/<name>` branches each become one more draft PR on `termag-<asker>/<thread>-<name>`, at most 10 per thread, tracked in `agent_thread_prs`. Asks are **owner-only**: after `assertSessionAccess`, `ownerOnlyRefusal` (`services/agentMessages.ts`) answers 403 `not_owner` unless the asker owns both the project and its box, whatever `box-sharing-enabled` says, because a run has the owner's access; routes under `/api/cli/v1/ask` (`routes/cliAsk.ts`, `services/askService.ts`); the box needs the `ask-v1` agent capability. On a box with `ask-chat-v1` the turn is a chat-runner turn instead: each thread gets a worktree-less `ask-<thread>` workstream with a `claude-chat` workflow (`services/askChat.ts`, `AgentThread.chatWorkstreamId`), so the simple UI lists and opens the thread as a chat the owner can write in, and `agent/ask-chat.js` drives the script's `--prepare`/`--report`/`--fail` phases around the turn; reconstruct, the PR branch sweep, workstream remove/rename and ask targets skip such workstreams. The CLI picks the message id, so a retried `POST /ask` replays the same ask; a target that can't take a run is answered `rejected` with a reason and nothing stored; `termag ask --targets` (`GET /ask/targets`) lists what the caller may ask as A2A AgentCards. A person may have at most 10 asks active at once (`MAX_ACTIVE_ASKS`, `capRefusal`, counted under a per-asker advisory lock; `too_many_asks`); there is no per-box, nesting, run, hop or time limit, and the hop is recorded. By default an ask gets a box of its own through the CLI (`termag project create <box>/<project> --new-box --from <box>/<project>`, then `termag ask`) unless it is small and mostly reads code; a `--thread` follow-up goes to its thread's box. An ask is not a spawn: an ask runs one headless turn on an existing project and hands its reply back (`agent_threads`/`agent_messages`, `/api/cli/v1/ask`), while a spawn starts a new agent in its own workstream or project pane that keeps running and reports back (`agent_spawns`, `/api/spawns`).
- **Status WebSocket** — `/termag/ws/status` pushes status events to anyone subscribed (the UI itself, plus opt-in external consumers): the owner's own sessions, and to a collaborator the shared projects' sessions only (`statusRoute`, `services/statusAudience.ts`). Idle browser WebSockets are kept alive with a server-side heartbeat.
