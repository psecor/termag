# Observability and maintenance

Moved out of [AGENTS.md](../../AGENTS.md), which keeps a short index of it. Paths are from the repository root.

- Orchestrator logs outlive the host when `termag-otelcol.service` ships them to a telemetry backend (`OBSERVABILITY_OTLP_ENDPOINT`, `OBSERVABILITY_PROJECT`). Filter on `service.name = termag-orchestrator` and `host.id` (the instance ID) or `host.image.id` (the AMI).
- The backend's own OTel metrics and logs (`services/otel.ts`, `orchestratorResource`) carry `service.version` = the full 40-character running commit (`services/termagVersion.ts`, what `GET /api/version` serves; left out when unknown) and `deployment.environment` plus `deployment.environment.name` (`NODE_ENV`: `production` on the host and the container, `development` on stage and e2e). The commit resolves asynchronously, so it is a promised resource attribute and the SDK holds exports until it settles. `OTEL_RESOURCE_ATTRIBUTES` overrides either. The browser's `version` is the 12-character prefix (`BUILD_SHA`), so match on a prefix across the two. The journal records the collector ships carry neither (they are the collector's, not the SDK's).
- `journalctl -u termag -f` — main server.
- `journalctl --user -u termag-agent -f` — per-user agent (run as the user).
- `tail -f /var/log/apache2/error.log` — proxy + WebSocket upgrade errors.
- Status events live in Postgres (`StatusEvent`) — usable for ad-hoc queries about agent activity.
- **Product events** (`backend/src/services/productEvents.ts`, `frontend/src/observability.ts`) are log records in the same project with `event.name` set, plus the `termag.product.events` counter by name; every one carries `context.contextKeys.user` (the user id) and, with a box, `context.contextKeys.box`, so they join browser sessions and agent telemetry on the same keys. Metadata only (enums, ids, counts, seconds; never a prompt, pane text, a brief, an email or a key). The vocabulary, with the `termag.*` attributes each carries: `project.created` {provider, repoSource: empty|github|template, boxKind: box|host, warmClaimed, spawned} · `box.provisioned` {boxKind, warmClaimed, provisioning: orchestrator|manual|external, child, claimMs; a warm claim also the box dimensions} · `box.ready` {provisionSec (row creation to the first agent connect, the write-once `readyAt`: cold provisioning; pool boxes never send it), the box dimensions} · `box.resumed` {from: stop|hibernate, outcome: ready|failed|still-starting, durationSec (start request to this outcome; in-memory clock, so a restart mid-start drops the sample), hourUtc (UTC hour of that request, 0-23), source: user|sweep (sweep is the 60-day refresh; user is every other start), by: owner|automation|cloud|ask|refresh|guest|resize|null (who the start was for), afterAutoPark, parkedMinutes (since the lifecycle sweep parked it, when nobody started it since), downMinutes (since the box went down, `Instance.downSince`: stamped by the power sweep's settle of a stop or hibernate while it is empty; cleared whenever the box is up for use, by the connect that brings it up, a stop or hibernate asked of a ready box, or one that times out back to ready; the 60-day refresh keeps it, through its connect and its re-hibernate of a box nobody used since (`sleepKeepsDownClock`); the refresh's start fills it from `hibernatedAt` for a box hibernated before the column; else since `hibernatedAt` for a hibernated box; null for a box stopped outside termag or before the column), the box dimensions} · `box.pool.claim` {size: small|medium|large|configured, outcome: hit|miss, reason (a miss): size-not-pooled|no-warm-box|every-candidate-failed, via: add-box|claude-runner; in-memory clock, so after a restart `by` and `settleSec` are left out), the box dimensions} (`services/boxPowerEvents.ts`; every stop or hibernate, whoever asked, where `box.parked` is the idle sweep's only) · `agent.session.started` {provider, kind: interactive, resume, spawned, clone} · `agent.session.ended` {provider, kind, lastStatus} · `agent.status.changed` {status, previousStatus, waitingReason, previousStatusSeconds (how long the previous status lasted, from the entry's `statusSince`; via: typed|button; chat: sdk|pane|mobile|new}. Backend events go through the global OTel API, so they are a no-op wherever `services/otel.ts` has nowhere to send (dev, tests, the e2e stack); the browser's go through the Observability plugin's `LDObserve.recordLog` and are a no-op while the plugins are off. The **box dimensions** (`boxEventDimensions`, from the row): `boxKind` (ec2|external), `region`, `imageId` and `imageSource` (the AMI and how it was chosen, `services/boxImage.ts`), `hibernationConfigured`, `fromPool` (claimed from the warm pool), `child` (created by another box); a field the row doesn't have is left out. Not among them: the instance type (a launch may fall back through `BOX_FALLBACK_INSTANCE_TYPES` and the row does not record which type it got) and the agent's commit (it comes in the hello, after the connect `box.ready` and `box.resumed` are timed to; join on `context.contextKeys.box` instead). Add an event to `PRODUCT_EVENTS` and to this list in the same PR. `agent.session.started` is a pane's setup (`ensureAgentSessionsAndLaunch` in `services/agentRuntime.ts`, once it reports `launched`), Codex bridge launches and a chat-runner workstream's pane included, always with `kind: interactive`; it is not a chat session or turn, whose own record is its spans (`termag.session.kind=chat`, below). Not yet wired: pi's resource lacks `termag.project`/`termag.workstream` (Codex's and the chat runner's carry them: the agent telemetry resource gotcha in [gotchas.md](gotchas.md)).
- **Agent telemetry** (OTel from the agents on a box, same project): every resource carries `termag.agent`, `termag.session.kind`, `termag.project`, `termag.workstream`, `termag.box` and the two context keys (the agent telemetry resource gotcha in [gotchas.md](gotchas.md)). A simple-UI chat's Claude turns are `service.name=termag-claude-session` with `termag.session.kind=chat`, its Haiku title and heading calls `termag.session.kind=oneshot` with `termag.oneshot=title|heading`, and Open in full UI's resume `interactive` like any pane; filter on the kind, since a chat turn's `terminal.type` is `non-interactive` like a one-shot's. A `termag ask` thread's turns are `termag.session.kind=ask`, with `termag.ask.thread`, `termag.ask.hop` (the message's turn on the thread; not on a person's turn in its chat) and, as far as known, the asking session's `termag.ask.parent.box`, `termag.ask.parent.project`, `termag.ask.parent.workstream` and `termag.ask.parent.session` (its Claude Code `session.id`), so an ask's spans and events join the conversation that asked on `termag.ask.parent.session = session.id` (the gotcha says where each comes from).
- **How long box operations take in production** comes from those events, not from EC2: a box's role can't call `DescribeInstances`, so an agent on a box can't time a start or stop itself. Search the logs by `event.name`: `box.provisioned` with `warmClaimed=true` for a warm claim (`termag.claimMs`), `box.resumed` for a start (`durationSec`, by `from`), `box.sleep.settled` for a stop or hibernate (`settleSec`), `box.ready` for a cold launch (`provisionSec`), and `"[POOL] warm"*` for pool warm-ups. On 2026-10-28 that was a warm claim in about 45 ms, a stopped box's start a median 15 s, a stop 48 s, and a cold launch 69 to 94 s. Cite the event and the sample size with a number.
- Per-request debug lines (`[STATUS] Push …`, `[STATUS] POST session=…`, `[GH-AUTHZ] … allowed`) print only with `TERMAG_DEBUG=STATUS,GH-AUTHZ` (or `all`) in the backend's environment (`services/debugLog.ts`); the collector's `filter/noise` drops the same lines from any journal, so switching them on does not re-flood the project.
- The agent process must be restarted whenever `agent/agent.js` changes (no hot reload). On a box, the orchestrator does that when it is safe (`deploy/termag-box-update`, started over the agent's `box-update` RPC once the `box-auto-update-enabled` flag is on for the box's owner and the box is behind the current image); a developer's checkout on a branch is left alone.
