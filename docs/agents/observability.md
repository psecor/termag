Moved out of [AGENTS.md](../../AGENTS.md), which keeps a short index of it. Paths are from the repository root.

- Orchestrator logs outlive the host when `termag-otelcol.service` ships them to a telemetry backend (`OBSERVABILITY_OTLP_ENDPOINT`, `OBSERVABILITY_PROJECT`). Filter on `service.name = termag-orchestrator` and `host.id` (the instance ID) or `host.image.id` (the AMI).
- The backend's own OTel metrics and logs (`services/otel.ts`, `orchestratorResource`) carry `service.version` = the full 40-character running commit (`services/termagVersion.ts`, what `GET /api/version` serves; left out when unknown) and `deployment.environment` plus `deployment.environment.name` (`NODE_ENV`: `production` on the host and the container, `development` on stage and e2e). The commit resolves asynchronously, so it is a promised resource attribute and the SDK holds exports until it settles. `OTEL_RESOURCE_ATTRIBUTES` overrides either. The browser's `version` is the 12-character prefix (`BUILD_SHA`), so match on a prefix across the two. The journal records the collector ships carry neither (they are the collector's, not the SDK's).
- `journalctl -u termag -f` — main server.
- `journalctl --user -u termag-agent -f` — per-user agent (run as the user).
- `tail -f /var/log/apache2/error.log` — proxy + WebSocket upgrade errors.
- Status events live in Postgres (`StatusEvent`) — usable for ad-hoc queries about agent activity.

- **How long box operations take in production** comes from those events, not from EC2: a box's role can't call `DescribeInstances`, so an agent on a box can't time a start or stop itself. Search the logs by `event.name`: `box.provisioned` with `warmClaimed=true` for a warm claim (`termag.claimMs`), `box.resumed` for a start (`durationSec`, by `from`), `box.sleep.settled` for a stop or hibernate (`settleSec`), `box.ready` for a cold launch (`provisionSec`), and `"[POOL] warm"*` for pool warm-ups. On 2026-10-28 that was a warm claim in about 45 ms, a stopped box's start a median 15 s, a stop 48 s, and a cold launch 69 to 94 s. Cite the event and the sample size with a number.
- **The box Bazel cache.** The orchestrator logs `[BAZEL-CACHE]` lines (each flag change's or new generation's redelivery, `generation <old> -> <new>`, a failed read of `current-generation`, a malformed `box-bazel-cache-config`), one `[CRED] applied|removed bazel-cache on instance <id> (seq, generation, flush)` per box, and `[BOX] <name>: <instance> launched with private IP <ip>` at each launch, which is how an S3 access-log record's IP maps back to a box. The generation reader is its own trace, `termag.sweep.bazel-cache-generation`, every 5 minutes. On a box, `termag-credentials status` says whether the block is on, off (with the backend's reason) or `NOT WORKING` (and why), and `termag-bazel-cache-canary` measures the shared cache's hit share on a fresh build. The writer instance (no termag tag, so SSM is break glass only) has its journal (`termag-bazel-cache-writer`, `-upload`) and EMF lines in `/var/log/termag-bazel-cache/{metrics,upload}.log`, namespace `TermagBazelCache`, log group `/termag/bazel-cache/writer`. The bucket has S3 request metrics (`FilterId=generations`) and server access logs in `/termag/bazel-cache/s3-access-logs`, which arrive within hours and best-effort. The alarms on these are the deployment's own.
- Per-request debug lines (`[STATUS] Push …`, `[STATUS] POST session=…`, `[GH-AUTHZ] … allowed`) print only with `TERMAG_DEBUG=STATUS,GH-AUTHZ` (or `all`) in the backend's environment (`services/debugLog.ts`); the collector's `filter/noise` drops the same lines from any journal, so switching them on does not re-flood the project.
- The agent process must be restarted whenever `agent/agent.js` changes (no hot reload). On a box, the orchestrator does that when it is safe (`deploy/termag-box-update`, started over the agent's `box-update` RPC once the `box-auto-update-enabled` flag is on for the box's owner and the box is behind the current image); a developer's checkout on a branch is left alone.

## Server traces

The orchestrator's OpenTelemetry traces (`services/tracing.ts`, `services/tracing/`). They go where its logs and metrics go (`otelSetup()`: on the host, the collector's `otlp/termag` receiver and `transform/redact-spans`), as `service.name=termag-orchestrator` with the same resource: `service.version` (the full commit), `deployment.environment`, and through the collector `host.id`, `host.image.id` and the cloud attributes.

- **What's traced.**
  - **Each request that reaches Node**, apart from the health and version probes, static files and the SPA, and preflights (`ignoredRequest`). Each one gives:
    - a SERVER span named `<METHOD> <route template>`, and Express's `request handler - <route>`;
    - Prisma's operations as `prisma:<Model>.<operation>` (`$use` middleware, `tracing/prismaSpans.ts`), without their SQL. In production, Prisma's queries reach `pg` through the driver adapter outside the request's context, and the pg instrumentation records nothing without a parent (the README's "Prisma spans, after the spike");
    - queries made on `pg` directly under a span, such as the session store's (`connect-pg-simple`): `pg.query:<verb> <db>`, with `db.query.text` parameterised, never the values;
    - outbound HTTP (http and undici, named by method) and AWS SDK calls (`EC2.StartInstances`).

    Express routers are recorded but never exported, and middleware isn't recorded at all.
  - **Background work**, each run a trace of its own:
    - `termag.sweep.<name>` for each tick of the loops that run every 30 s or slower (`traceSweep`);
    - `termag.slack.<event|command|action|view>` and `termag.discord.<event>` for each bot listener (`tracing/botSpans.ts`);
    - `termag.box.rpc` for an awaited box agent RPC, under either, with `termag.rpc.method`, `termag.rpc.outcome` and `termag.box`.
  - **Attributes on the server span:**
    - `termag.user`, `termag.project`, `termag.box` and `termag.workstream` (cuids; the last three from the route's parameters);
    - `termag.surface`;
    - `termag.poll` for `?poll=1`;
    - `termag.parent.remote` when the span continued a caller's trace.

    Every exported span carries `termag.sampling.ratio`, the N it was kept at.
  - **Not traced:** WebSocket upgrades and their messages, loops faster than 30 s, pg connects, and dns, net and fs.
- **The environment decides** (`services/tracing/state.ts`), read at start, never per span.
  - `TERMAG_TRACING=on` records; `TERMAG_TRACING=off` registers no tracer at all, wherever it is set. Like the logs and metrics, tracing is off in dev, tests and the e2e stack unless pointed somewhere.
  - `TERMAG_TRACING_RATE` (default 1) is the default rate: 0 to drop, 1 to keep, and N to keep 1 in N. Entries that fail or run slow are kept whatever the rate.
  - There is one decision per entry when it ends (`tracing/buffer.ts`), never one per trace id. In order:
    1. An entry that failed itself is kept: a 5xx, or an exception or error status on the entry span. A child's error that the entry handled doesn't count.
    2. An entry at least 3 s long is kept.
    3. Otherwise the default rate decides.
- **What leaves the process** passes `ScrubbingExporter` (`tracing/scrub.ts`).
  - The server `url.path` becomes the route template. An unrouted path keeps its known leading segments, and the rest becomes `:unrouted`.
  - `url.query` keeps only `poll=1`.
  - An outbound URL keeps its host and a short first path segment; the rest becomes `:path`.
  - Client and peer addresses are removed.
  - An exception's message is a fixed description of its type and code, never its text (`ErrorDescriptionProcessor`).
  - `db.query.text` is cut at 2,048 characters.

  The collector's `transform/redact-spans` repeats the log redaction patterns over every span attribute (the log-shipping gotcha). Attributes on manual spans pass through unchanged, so give them ids and enums only.
- **Rollback:** lower `TERMAG_TRACING_RATE`, or set `TERMAG_TRACING=off` in the backend's `.env` and restart.

### Finding a trace

Search the trace backend the collector sends to. A trace is there only if its entry was kept, so a missing server half usually means it wasn't sampled. An entry that passes 256 spans before it ends is dropped whole, whatever its rate (`termag.tracing.dropped`, `reason=entry-cap`). Check the rate before suspecting propagation.

- **From the browser.** The browser sends `traceparent` on same-origin API calls, apart from the pollers in `NETWORK_URL_BLOCKLIST`. The server continues it when the request carries a credential (a session cookie, the ALB's OIDC header or `Authorization`; `tracing/propagator.ts`), so the server's spans share the browser fetch's trace id.
- **From a log line.** A product event (`event.name` set, `source=backend`) emitted inside a request or a background run carries that span's `trace_id` and `span_id`, so search `trace_id=<id>`. Lines the collector ships from the journal (`console.log`, nginx) carry none, so match those by time, `host.id` and route.
- **Errors by route:** traces with `service_name=termag-orchestrator` and span kind server, grouped by `http.route` and `http.response.status_code`.
- **Background work:**
  - a sweep's ticks: `span_name=/^termag\.sweep\./`;
  - the bots: `span_name=/^termag\.(slack|discord)\./`;
  - failed box RPCs: `span_name=termag.box.rpc termag.rpc.outcome=error`.
