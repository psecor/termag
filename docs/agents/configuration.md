# Configuration

Moved out of [AGENTS.md](../../AGENTS.md), which keeps a short index of it. Paths are from the repository root.

`backend/.env` (gitignored). Key vars (see `.env.example` for the full list):

| Var | Notes |
|-----|-------|
| `DATABASE_URL` | Postgres. Composed from `PG_HOST`/`PG_PORT`/`PG_DATABASE`/`PG_USERNAME`/`PG_PASSWORD`/`PG_SSLMODE` at startup when unset (`config/env.ts`). |
| `PG_IAM_AUTH` | `true` → RDS IAM auth: Prisma runs through a node-postgres pool (`db.ts`, `driverAdapters`) whose password is a fresh IAM token per connection; region from `PG_IAM_REGION`/`AWS_REGION`/the RDS hostname; TLS verified against the baked RDS CA (`PG_SSL_CA_FILE`). Every module imports the shared `prisma` from `db.ts` — never `new PrismaClient()` elsewhere. |
| `DB_PUSH_MODE` | `additive` → `npm run db:push` runs `prisma db push` without `--accept-data-loss`: a change that would drop data-bearing columns or tables is logged and skipped (exit 0), so a rolled-back image can't drop a newer release's data. Unset keeps `--accept-data-loss`. The orchestrator's RDS cloud-init uses `additive` (`config/schemaSync.ts`) |
| `TERMAG_DATA_DIR` | default `/srv/termag`: where `npm run db:guard` looks for its marker files (`DATABASE_MOVED_TO_RDS`, `ALLOW_DOCKER_ROLLBACK`, `ALLOW_EMPTY_DATABASE`) |
| `SESSION_SECRET` | random hex |
| `AUTH_MODE` | `google` (default, in-app Google OAuth), `okta` (identity from the ALB `authenticate-oidc` edge via `x-amzn-oidc-data`), `oidc` (in-app OpenID Connect code flow, `auth/oidc.ts` — for the container behind a non-ALB ingress), or `local` (no identity provider, for the e2e stack only; see `BIND_HOST`). |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | OAuth (required when `AUTH_MODE=google`) |
| `OIDC_ISSUER_URL`, `OIDC_CLIENT_ID`, `OIDC_CLIENT_SECRET`, `OIDC_SCOPE` | required when `AUTH_MODE=oidc`; redirect URI is `<FRONTEND_URL><BASE_PATH>/auth/oidc/callback` |
| `LOCAL_SESSIONS_ENABLED` | default `true`. `false` (baked into the container image) makes the in-process tmux fallbacks for box-less projects throw `LocalSessionsDisabledError` instead of hitting a non-existent tmux. |
| `BOX_PROVISIONER_ROLE_ARN` | optional; box-account role the provisioner assumes for every EC2/IAM call when the orchestrator's identity lives in another account (container). `HOST_SECURITY_GROUP_ID` is optional for the same reason. |
| `ALLOWED_USERS` | comma-separated `email:unixuser` pairs. Supports domain wildcards (e.g. `*@example.com:default-unixuser`). |
| `ADMIN_USERS` | optional; comma-separated emails or `@domain`s who may use the admin surface. Synced into `users.role` at startup (fail-closed when unset). |
| `SLACK_BOT_TOKEN` (`xoxb-`), `SLACK_APP_TOKEN` (`xapp-`), `SLACK_SIGNING_SECRET` | Slack Socket Mode |
| `ALLOWED_SLACK_USERS` | optional; comma-separated Slack user IDs (`U…:unixuser`, unix half ignored) who may use the bot whatever the flag says: `/t` on any project, and the only ones DMs and @mentions answer (they run `claude` as the backend's user). Everyone else needs the `slack-bot-enabled` flag on for their termag user, matched by Slack email, for `/t` on their own or shared projects; it falls back off (`backend/src/slack/access.ts`, deploy/setup.md §7). Unset no longer means "everyone". |
| `CAPTURE_API_SECRET` | shared secret used by external pane-capture relays |
| `ORCHESTRATOR_LEASE` | `true` makes this process take part in overlapping deploys: the newest process holds `orchestrator_leases` and runs the sweeps; the displaced one drains (`/termag/health/serving` 503, new sockets closed 4503, then after `ORCHESTRATOR_DRAIN_GRACE_MS` its agents' sockets and `ORCHESTRATOR_DRAIN_BROWSER_DELAY_MS` later its browsers', all with 4503, which agents and the status socket redial at once). Slack Socket Mode and the Discord gateway connect only on the holder, a draining process stops the host's `claude-runner-orchestrator.service` (sudoers rule `deploy/claude-runner-orchestrator.sudoers`) and its runner spawn hook answers 503, and the new holder re-reads `session_statuses` once the old one has closed its sockets. Unset: always serving, as before. Never set it on a mirror that shares the production database |
| `AGENT_WS_QUERY_TOKEN` | default on. `false` refuses a box agent that sends its token as `/ws/agent?token=` instead of `Authorization: Bearer` (agents before the header did); the admin System page's "agent token in URL" line shows how many still do |
| `BIND_HOST` | interface the backend listens on; unset means all interfaces. `AUTH_MODE=local` refuses to start unless it is `127.0.0.1` or `::1` and `NODE_ENV` is `development` or `test` |
| `AWS_REGION` | region `boxProvisioner`'s EC2 and IAM clients talk to, and the boxes live in. Credentials are never configured by name: the SDK's default chain supplies them from the ambient identity (EC2 instance role, pod identity), optionally chained through `BOX_PROVISIONER_ROLE_ARN` |
| `BOX_RESOURCE_PREFIX`, `BOX_PERMISSIONS_BOUNDARY_ARN`, `BOX_VPC_ID`, `BOX_SUBNET_ID` | required, with `AWS_REGION` and `AGENT_WS_URL`, before a box can launch — `getBoxConfig` returns null without all six and the "Add box" path falls back to handing the user a token |
| `BOX_HIBERNATION_REFRESH_DAYS` | optional; days hibernated before the sweep resumes and re-hibernates a box (default 55, `0` = never). Whether new boxes launch hibernation-capable is the `box-hibernation-enabled` feature flag, not an env var (gotcha on hibernation) |
| `BOX_INSTANCE_TYPE`, `BOX_MANAGED_TAG`, `BOX_ROOT_VOLUME_GB`, `BOX_GIT_TOKEN_SECRET_ARN` | optional; defaults are `t4g.medium` (the AMI is arm64-only), `termag-box`, and `120`. The AMI itself is discovered by tag, not configured |
| `ASK_GITHUB_GIT_URL`, `ASK_GITHUB_API_URL` | optional; where an ask's commits are pushed and its draft PR opened. Defaults `https://github.com` and `https://api.github.com`; the e2e stack points the git one at its GitHub stub |
| `TERMAG_FLAGS` | optional JSON object of flag key to value, e.g. `'{"warm-pool-enabled": true}'`; unset, every flag uses its built-in fallback. Served to the browser at `GET /api/flags`. |
| `OTEL_EXPORTER_OTLP_ENDPOINT`, `OTEL_RESOURCE_ATTRIBUTES`, `OTEL_METRIC_EXPORT_INTERVAL`, `TERMAG_OTEL` | the backend's own OpenTelemetry metrics and logs (spawn and box telemetry, `services/otel.ts`). Unset endpoint: it pushes to `http://127.0.0.1:4318` (`termag-otelcol`'s loopback `otlp/termag` receiver) when `/run/termag-otelcol/destination.yaml` exists, else exports nothing. `TERMAG_OTEL=off` beats both. Interval default 60 s. |
| `PORT` | `3040` |

**PR pipeline and the running commit.** `GET /api/prs` (`routes/prs.ts`) returns the user's pull requests across `example-org` + `example-team`, already in lanes: three parallel GraphQL searches with the stored gh token (`services/prPipelineGithub.ts`; one combined query took ~7 s because `mergeable` is computed on demand), pure lane rules in `services/prPipeline.ts`, fresh for 60 s per user and then served stale while one reload runs (`swrMemo`, ceiling 10 min), `{ connected: false }` with no token. Lanes 1–2 (branches with no PR) come from the `git-branch-state` agent RPC (`agent/git-branch-state.js`, local refs only, no fetch), asked for every live workstream of the user's own projects inside that same load (`services/prBranches.ts`); its `origin` is also what links a PR row to a workstream by (repository, branch). A checkout with no GitHub origin never gets a branch row, and a branch that already had a PR merged (any age, one batched `pullRequests(headRefName:, states: MERGED)` query) is dropped, because a squash merge leaves it "ahead of base" for good. An agent that predates the RPC answers "Unknown command": its workstreams link by branch name only, and the response's `notes` say to restart it. "Deployed" is termag-only and asks GitHub `compare/{running}...{mergeCommit}` (cached forever per pair); a merge touching `agent/` or `deploy/` also needs every connected box's `agentCommit`, and a box GitHub cannot place (a public-mirror clone) is counted as unknown but does not hold a PR back. Both the PR overlay (`components/PrsOverlay.tsx`, `?prs=<view>&pr=<owner/name#n>` over the workspace or the dashboard, opened by the status strip's PRs tile and the dashboard's Attention items; it replaced the dashboard section) and the phone's `/m/prs` (the same `PrDetail` in a full-screen sheet) have Review with Devin (the Review button's `POST /api/projects/:id/review` against the row's `reviewTarget`) and the PR detail (`PrDetail` in `pages/dashboard/PrOverviewDialog.tsx`) over `GET /api/prs/:owner/:repo/:number`, whose review form and, on the user's own PRs, merge panel are termag's GitHub writes: `POST …/review` submits the user's own review and `POST …/merge` merges (pinned to the shown head sha) or toggles auto-merge, `POST …/rerun-failed` re-runs the head commit's failed Actions jobs, `POST …/reviewers` re-requests reviews and `POST …/comment` posts a ping comment the user wrote or approved, all with their token; its Not deployed lane splits "waiting for a bake" from "baked, rolling out" by the newest orchestrator AMI's `TermagSha` and offers Bake & deploy now (`POST /api/prs/bake`, a publish-ami.yml dispatch on main; `services/prDeploy.ts`) (`services/prReview.ts`; never pass GitHub's 401 through, the client reads 401 as signed out). The tile, the phone inbox and the overlay's first view count what needs you (`needsYou` in `utils/prPipeline.ts`). `GET /api/version` (`services/termagVersion.ts`) is what the orchestrator runs, resolved once at startup from `TERMAG_GIT_SHA`, else `git rev-parse HEAD` of its checkout, else `/opt/termag/.termag-baked-sha` (the bake deletes `.git`); an rsync-style hot-patch onto a baked host leaves that file stale, so set `TERMAG_GIT_SHA` when patching that way.

**Phone client as an installed app.** Behind `mobile-installed-app-enabled` (default off, `installedAppMode` in `frontend/src/mobile/redirect.ts`; the flag's value is set there by `MobileRedirectGate` and `MobileApp`, since the opt-out helpers run from click handlers that don't read flags), an app installed on a touch device (`installedOnTouch` in `frontend/src/mobile/redirect.ts`: `display-mode: standalone` or iOS `navigator.standalone`, plus `pointer: coarse`) always redirects `/` to `/m`, whatever `mobile-redirect-enabled` says; its "Full UI" opt-out lives in `sessionStorage`, so it lasts one window. A desktop install keeps the workspace.

**Photo attach.** The phone posts raw `image/png`, scaled to at most 2048 px, to `POST /api/projects/:id/sessions/:role/paste-image?workstream=`. That route is in `routes/sessions.ts` beside send-keys, behind the same `assertSessionAccess`, with a 20 MiB cap and 1 image per 2 s per caller and session. The backend forwards it over the agent's `clipboard-paste-image` RPC, which writes the same `~/.cache/termag/clipboard.png` mailbox as the desktop paste (`agent/clipboard-mailbox.js`, shared by both RPCs) and then sends `C-v` with `tmux send-keys -t =<session>:`. An older agent answers `Unknown command`, which the route maps to 501 "This box needs an update to take images".

**Chat images.** Behind `chat-image-input-enabled` (server-side; the composer reads `imageInput` from `GET …/chat`), a simple-UI chat message carries up to four base64 PNG/JPEG/GIF/WebP images (≤ 3.75 MB each) in `POST …/chat/messages` (22 MB body limit on that path only), checked in `services/chatImages.ts` and again on the box (`agent/chat-images.js`, capability `chat-images-v1`), which keeps them under `~/.termag/chat-images/<chatKey>/` and sends the turn as stream-json image blocks. Events and history leave the box with every base64 image swapped for a `termag` source naming the stored file, which the browser reads through `GET /api/projects/:id/image`.

**Web push.** `frontend/public/sw.js` (scope `/termag/`) handles push and notification clicks only and has **no `fetch` handler, on purpose**: it never serves a stale page, so hot-patches and the stale-chunk reload behave as before. Don't add caching there without reading §5. `routes/push.ts` (`/api/push/config|subscriptions|test`, requireAuth) stores `PushSubscription` rows. `services/pushWaiting.ts` runs from `POST /api/status` on every write: a transition into `waiting` (not from `waiting`, 30 s cooldown per session) pushes once to the session's project owner, resolved with `resolveSessionProject`. It doesn't depend on the hook's `notify` bit or on `notification_targets`, and the orchestrator's in-process tmux poller never pushes, because it writes status without going through the route. The payload is a mutable Declarative Web Push (`web_push: 8030`, `mutable: true`, tag = the status key, `app_badge` at the top level, where WebKit reads it). iOS never runs `notificationclick` for an installed app that is still alive, so on Safari's path the worker shows each notification under a per-push tag (`<status key>#<id>`) and records it in IndexedDB, and the page treats exactly one recorded notification gone from `getNotifications()` as a tap (`mobile/shownNotifications.ts`). The worker skips `setAppBadge` there: in iOS's worker it never settles and iOS drops the notification. The page closes notifications whose session is no longer waiting and sets the app badge (`syncAttention` in `mobile/push.ts`). Push is off unless `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` and `VAPID_SUBJECT` are all set, and then only for users with `mobile-web-push-enabled` (server-side, `services/pushFlag.ts`: config, subscribe, test, sending and the chat mute all check it) (`npm run push:vapid` prints a key pair); the orchestrator needs egress to the push services. With `User.pushMutesChat` and one live subscription, the owner's Slack/Discord "needs input" posts are skipped ("Done" still posts). A simple-UI chat that finishes its turn (`working → idle` on a chat `result`, or a `turn-end` without one and without a signal) pushes through the same subscriptions to its owner and collaborators who set `User.chatTurnNotify` (Settings → Notifications, `pages/settings/NotificationsSection.tsx`), behind `chat-turn-notifications-enabled` (`services/chatTurnPush.ts`, called from the chat relay); the worker skips it for a chat a focused window shows (not on Safari), and an open `/chat` tab without a push subscription shows it with the Notification API instead (`chat/useChatTurnNotifications.ts`).

**Feature flags.** Optional and off-by-default: every flag read names a fallback, so with `TERMAG_FLAGS` unset the app runs on the fallbacks. `backend/src/services/featureFlags.ts` parses `TERMAG_FLAGS` (a JSON object of flag key to value) and answers `boolVariation(key, user, fallback, box?)`, `boolVariationForContext`, `stringVariation` and `jsonVariation`; `routes/featureFlags.ts` serves the values at `GET /api/flags`. The frontend's `contexts/FeatureFlagsProvider.tsx` loads them before rendering, and `useFlag(key, fallback)` in `flags.ts` reads them. Every flag is listed in `backend/src/flags.ts` (kind, fallback, server contexts, whether the browser reads it, lifecycle, the PR that added it); the server's variation helpers take only a listed key of the matching kind, and `backend/src/flags.test.ts` holds the browser's keys and fallbacks to the list. `hyperspace-background-enabled` (boolean, **defaults on**) gates the animated background; it is ANDed with the user's theme (`User.theme`, Settings → Appearance), so the flag can only turn the starfield off. **Telemetry:** a cloud runner session's Claude Code telemetry carries the owner's and the box's ids as `termag.user.id` / `termag.box.id` (`runnerLaunch` hands `--user-key` / `--box-key` to `deploy/termag-claude-runner`). **The other agents** (Codex, Cursor, Devin, pi) export to the same project with the same resource plus `termag.agent=<agent>`: an `agent-telemetry` credential provider (`agentTelemetrySettings`, boxes advertising `agent-telemetry-v1`) records `{endpoint, resourceAttributes}` on the box, `launchCommandFor` types Cursor/Devin/pi launches through `deploy/termag-agent-otel` (which also starts Codex's app server from the status bridge, and drops the shell's `OTEL_EXPORTER_OTLP_*` first, since Rust exporters merge a shell's headers into a configured one), Cursor gets `deploy/termag-cursor-otel-hook` in `~/.cursor/hooks.json`, and pi loads `deploy/pi-ext/termag-otel.ts`. Metadata only; Codex's log exporter stays off because its tool-result logs carry tool arguments and output. termag ships no browser session recorder: `frontend/src/observability.ts` keeps `REPLAY_BLOCK_CLASS` (**give that class to any element that renders a credential**) and a `replaySessionId()` that returns null, so the launch path that files a browser-started session under a recording (`termag.replay.id`, `telemetry-replay-v1`, `services/launchCommand.ts`) stays idle until a deployment adds one.

Per-user agent: `~/.config/termag/agent.config.json` with `server_url` (`ws://localhost:3040/termag/ws/agent`) and `token` (created in the UI sidebar → Agent Tokens). The agent now also accepts a config-path override as `argv[2]` and falls back to the example config if the per-user file is missing.
