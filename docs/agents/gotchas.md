# Gotchas

Moved out of [AGENTS.md](../../AGENTS.md), which keeps a short index of it. Paths are from the repository root.

**How this list is kept.** Each gotcha has a stable slug, the `<a id>` above its heading, and the sections are in alphabetical order by slug. A slug is `<area>-<subject>`, lowercase words joined by hyphens (`box-hibernated-not-stopped`, `status-stale-waiting`), so the sorted list reads grouped by area. There are no numbers: cite a gotcha by its subject ("the gotcha on hibernated boxes") or link its slug (`docs/agents/gotchas.md#box-hibernated-not-stopped`). Numbered, every new gotcha went at the end of this file and of AGENTS.md's index, so any two PRs adding one conflicted there, and a renumber broke every citation by number.

**Adding one.**

1. Pick its slug: an area prefix used below when one fits, or a new one (`agent`, `ami`, `auth`, `box`, `chat`, `deploy`, `o11y`, `project`, `simple-ui`, `space`, `status`, …), then its subject in two to five words. A slug never changes once merged, because links point at it; reword the heading instead, and its index line with it.
2. Insert the section where its slug sorts, not at the end of the file.
3. Insert `- <slug>: <the heading's text>` at the same place in the Gotchas section of AGENTS.md.

`backend/src/docsLists.test.ts` fails when a section has no slug, when the slugs are out of order, or when AGENTS.md's index does not list the same slugs in the same order with the headings' text.

**The agent-wiki sweeper** (CLAUDE.md) rewrites whole sections of AGENTS.md from what its prompt holds: AGENTS.md itself, the git log since the last sweep, and agent-wiki's spec, which describes Gotchas as a numbered list. It never reads this file. So the rule is also written in AGENTS.md's Gotchas section, where the sweeper reads it, and is told to keep a section's existing form. If a sweep renumbers, reorders or rewords the index anyway, the test fails: put the index back from `main` and keep only a gotcha the sweep genuinely added, written into both files by the steps above.

<a id="admin-env-admins"></a>
## Env-sourced admins are re-checked against `ADMIN_USERS` on every request; granted admins are not

`isAdminUser` trusts `users.role = 'admin'` only when `adminSource = 'grant'`; a row with `adminSource = 'env'` must still match the live list. So a first-time sign-in on the list is an admin immediately, and removing an email demotes as soon as the process sees the new env (which, on the immutable-AMI orchestrator, means a restart — the startup sync also rewrites the row then). Env-listed admins cannot be demoted from the UI; edit the env. Granting admin to an env-listed user keeps `adminSource = 'env'` so the env stays authoritative for them.

<a id="admin-tokens"></a>
## Admin tokens are `agent_tokens` rows with `scope = 'admin'` and must never reach `/ws/agent`

`registerAgent` replaces the agent for the same user/instance key, so a token that validated there would evict the user's real agent. `/ws/agent` and the gateway ext_authz checks accept only `scope = 'agent'`; `requireAuthOrAgentToken` (the agent-facing REST routes) and `cliBearer`'s `tmag_` path (`/api/cli/v1`) accept only `agent`; `requireAdmin` accepts only `admin` and re-checks that the owner is still an admin on every call. If you add a bearer-accepting route, decide which scope it takes — don't call `validateAgentToken` and ignore `result.token.scope`.

<a id="agent-bash-tool-shell"></a>
## Claude Code's Bash tool runs bash on a box, not the owner's zsh, and bash reads only `$BASH_ENV`

The box user's login shell is zsh and Claude Code's Bash tool runs `$SHELL`, so until this was set every agent command ran in zsh, and agents write bash. zsh fails it in ways bash does not: an unquoted glob with no match is an error (`grep -r --include=*.ts` → `no matches found`), a word starting with `=` is a command lookup (`echo =====` → `= not found`), an unquoted `$var` does not split. In 14 days of transcripts from four boxes, zsh caused 34 of 155 Bash failures (22%), the largest group with one cause that termag could remove (counts in `team-alpha:termag-ui-runtime/handoffs/agent-pitfalls.md`). `termag-agent.service` sets `CLAUDE_CODE_SHELL=/bin/bash` and `BASH_ENV=%h/.local/share/termag/bash-env`, and `agent/tmux-args.js` puts both on every new tmux session (a server that outlived an agent restart keeps its old environment), so panes, chat and ask turns all get them. The owner's interactive shell stays zsh.

The catch is the environment. A non-interactive zsh reads `/etc/zsh/zshenv` and `~/.zshenv` before every command, and part of a box's environment lives only there: `GH_HOST` (the GitHub broker, written by `termag-credentials` to `~/.zshenv` and `/etc/profile.d/termag-github.sh`), `TERMAG_BOX` and `~/.local/bin` on PATH. A chat or ask turn's `claude` does not have `GH_HOST` in its own environment; it only ever reached the tool shell through `~/.zshenv`. A non-interactive bash reads none of those files, and not `~/.bashrc` either; it reads only `$BASH_ENV`, which is `deploy/termag-bash-env` (installed by `termag-reconcile`). Anything new that a box puts in zshenv for agents has to go in that file too, except PATH: Claude Code sources its shell snapshot after `$BASH_ENV`, and the snapshot ends with `export PATH=<claude's own PATH>`, so PATH has to be right in the environment `claude` starts with (`turnEnv` in `agent/chat-runner.js` adds goenv, pyenv and cargo for chat and ask turns, the way `termag-claude-runner` does for its sessions). The file runs before every Bash tool command and every bash script they start, so it must stay silent, quick and safe under `bash -e`. bash also skips `$BASH_ENV` when its stdin is a socket and `SHLVL` is unset (it takes itself for an sshd command and reads `bash.bashrc` instead); claude's tool shells do not hit that, but a test that runs bash under `env -i` does. An owner who wants zsh back exports `CLAUDE_CODE_SHELL=/bin/zsh` in `~/.zshrc` (panes) or in a drop-in for `termag-agent.service` (chat and asks). A `claude` started from a plain ssh login, outside termag's tmux, still gets zsh. Tested by `deploy/termag-bash-env.test.sh`.

<a id="agent-launch-probes-first"></a>
## `ensureAgentSessionsAndLaunch` probes before relaunching

on reconnect / sleep-wake the runtime first probes whether the agent's tmux sessions are still alive and only relaunches the agent process when they're actually gone. If you add a code path that calls into this and it starts double-launching agents, you've skipped the probe; don't.

<a id="agent-linger"></a>
## `loginctl enable-linger <user>` is mandatory (Linux)

without it, the per-user agent stops the moment the user logs out, which makes everything in the UI hang the next time termag tries to talk to that user's agent. macOS uses launchd LaunchAgents instead and has no linger equivalent.

<a id="agent-reconnect-backend-view"></a>
## Agent reconnect reconstructs sessions from the backend's view, not the agent's

when a per-user agent reconnects (restart, network blip, laptop wake), `backend/src/services/agentRuntime.ts` replays the project/session state down to the agent so existing tmux sessions get reattached without the user re-clicking everything. The backend is authoritative for "what sessions should exist"; the agent is authoritative for "what tmux currently has." If they disagree after a reconnect (ghost sessions, missing reattach), the reconciliation logic in `agentRuntime.ts` is where to look — not the agent's own startup path.

<a id="agent-restart-on-change"></a>
## Per-user agent must be restarted on `agent/agent.js` changes

no hot reload. On a box, `termag-box-update.service` (`deploy/termag-box-update --when-enabled`, started by the orchestrator over the agent's `box-update` RPC when the box is behind the current image, never by the box itself) first asks the orchestrator (`GET /api/box-update/policy`, the `box-auto-update-enabled` flag for the box's owner) and does nothing unless it says yes; when it does, it pulls `main`, reconciles and restarts the agent when a tracked `agent/` file or its unit is newer than the running process — but only on a clean `main`, only with `KillMode=process` loaded, and never while a Claude runner session is live; a developer's branch, and a box with `~/.config/termag/no-auto-update`, are left alone. Stage and dev boxes still restart by hand. Forgetting this leaves stale code running and is a common "why isn't my fix taking" debug detour.

<a id="ami-by-tag"></a>
## The box AMI is discovered by tag, not by id

`boxProvisioner`'s `DescribeImages` call takes the newest self-owned image tagged `App=termag` + `Component=box`; no AMI id is configured anywhere. Rebuilding the AMI with Packer is enough to roll boxes forward, but a stale or missing tag fails the launch with `No box AMI found (tag App=termag, Component=box)`. A user's own boxes can be pointed elsewhere by the `box-image` string feature flag (`services/boxImage.ts`: a pinned `ami-…` or a channel, the newest image tagged `Channel=<name>` by Publish AMI's `channel` input); an unusable value falls back to the published image, and the warm pool always uses the published one (`docs/box-hibernation.md`).

<a id="ami-first-boot-path-index"></a>
## First boot rewrites the baked `/home/termag` path from a bake-time index, and the index step must stay the last provisioner

after step 2 renames the home (`mv`, then `usermod -l -d` to update the record), cloud-init fixes the symlink targets and text files that embed `/home/termag` by reading `/var/lib/termag-bake/home-paths/` and running `/usr/local/sbin/termag-rewrite-home-paths` (`packer/scripts/index-home-paths.sh` and `rewrite-home-paths.sh`). It used to find them at boot with `find -lname` over the whole home and `grep -rIl` over the toolchain dirs; on a box that walk hits a fresh EBS volume restored lazily from the snapshot, so every inode is an S3 round trip, and it took 4.5 minutes before the quick-start bake and 15.5 minutes after — past the orchestrator's 15-minute stuck-provisioning sweep — to rewrite about 200 symlinks and 3 files. Two consequences. Anything a provisioner writes under `/home/termag` *after* `index-home-paths.sh` runs is not rewritten at boot, so a new bake step that installs under the home goes before it in `box.pkr.hcl` (`packer/scripts/home-paths.test.sh` asserts the order). And the text-file scope is still the same six toolchain dirs (`.pyenv .goenv .nvm .local .cargo .config`, `SCAN_DIRS`); a file elsewhere that hardcodes the home, like the tilde-vs-absolute `~/.bazelrc` case above, is not covered — as it never was. The rename in step 2 is `mv` plus `usermod -l -d` **without `-m`** for the same reason: `-m` does the identical rename(2) and then stats every file under the home to re-own it (100,377 `newfstatat` for 100,003 files, measured), which was 4 more minutes on a quick-start box. Do not put `-m` back, and keep `box-ami-ci.yml`'s `sudo-handoff` job on the same sequence. The index runs as the packer user `ubuntu`, which cannot enter the 0750 `/home/termag`, so every probe under the home goes through `$SUDO`, not just `find` and `grep`: a bare `[ -d "$HOME_DIR/$d" ]` skipped every scan dir and the images baked from 2026-09-25 to 2026-11-04 indexed `files=0`, leaving uv tool shebangs and `pyvenv.cfg` on `/home/termag` (`termag-reconcile`'s `reconcile_uv_tool_paths` repairs the uv tools on boxes launched from them; `home-paths.test.sh` bakes a home only `$SUDO` can enter).

<a id="ask-owner-only"></a>
## An ask run has the box owner's full access, which is why asks are owner-only

there is no sandbox: `deploy/termag-subagent-run` runs `claude -p --permission-mode bypassPermissions` as the box user, with the owner's home, network, `gh`, docker and box token. The publish checks in `services/askPublish.ts` (protected paths, which are `.github/workflows/`, `CODEOWNERS` and sudoers files but not the rest of `deploy/`; no merge but a merge of the PR's base branch; author = asker, secret scan, no force, draft, branch fixed server-side as `termag-<asker>/<thread>`, or the head branch of a PR of the asker's that `--update-pr` named and the publish checks on GitHub) bind only what comes back through `PUT …/ask/runs/:id/bundle`; a run could push on its own with the owner's credentials. That is acceptable only because the asker *is* the owner, so never relax `ownerOnlyRefusal` (a share or a flag must not open asks to other people) without bringing an isolation boundary back. The old sandbox (the `termag-subagent` user, `/var/lib/termag-subagent`, `termag-subagent-setup`/`-exec`) is removed from boxes by `termag-reconcile`'s `retire_ask_sandbox`, which deletes the user only when passwordless sudo works and the user runs nothing. The run sees committed code only: a first turn fetches the base (the merge-base with the branch's upstream) over `file://`, so uncommitted edits and untracked files never cross, and an ask about unpushed work answers about the remote's version.

<a id="ask-push-clone-upstream"></a>
## A push-mode ask clone's branch tracks an origin branch, or the thread's chat loses its tools

On a box with `ask-push-v1`, the thread's clone has an `origin`, and that changes how the chat runner sees it. `checkoutOwnTree` (`agent/chat-runner.js`) passes a git checkout with no origin outright, which is why the old shallow clone ran `bypassPermissions`. A checkout *with* an origin must be on a branch whose upstream is a `refs/heads/*` ref of that same repository. A new local branch with no upstream fails that test, and the turn falls back to a read-only mode. So `--prepare` (`checkout_push_branch`) always sets one: the branch's own `origin/<branch>` when GitHub has it, else `origin/<default>`. When GitHub can't be reached during the prepare, so no tracking ref is fetched, it writes `branch.<b>.remote` and `.merge` as config, which is what `readCheckoutFacts` reads. A prepare that can't set either fails rather than hand the turn a clone it would refuse. With `push.default=current`, a plain `git push` still goes to the branch's own name, never to the default branch it tracks. Any new code that creates or switches the thread's branch keeps that upstream. A run that makes its own branch (`git switch -c <branch>-<name> origin/main`) gets one from `origin/main` the same way.

<a id="ask-target-pr-history"></a>
## A thread on another PR fetches that PR's history in full, and its publish orders base-branch commits through GitHub

Publishing to another PR (`docs/agent-messaging.md`: a run's `ask` that builds on one open PR of the asker's, or `termag ask --update-pr <n>`) leaves the box alone: the run's clone is still one commit of the thread's base, and the run is told to fetch the PR's branch into it with `--unshallow`. That flag is load-bearing. Fetched into a shallow clone, the PR's branch brings its whole history, and git cannot see that the PR's fork point is an ancestor of the shallow base, so the runner's `git bundle create ask ^<base>` packs every commit in the repository (1887 for termag in a test) and the publish refuses it. Unshallowed, the bundle holds only the PR's own commits plus the run's. The orchestrator then has to supply what that bundle builds on: `bundlePrerequisites` reads the bundle header and fetches each commit it needs one at a time, `--depth=1`, as it fetches the base. Those commits come in shallow, so git cannot order them either. `merge-base --independent` would keep both an old fork point and a newer merge of main, and the diff from the older one would pull main's own changes into the protected-path and secret scans (a workflow main changed since the fork would refuse the PR). In target mode the merge bases therefore come from GitHub's `compare` (`BaseBranch.independent`), never from git. Fast-forward is checked against the PR's head as GitHub has it now (`resolveTargetPr`), not against the thread's base, which the PR need not descend from. The prerequisites are fetched for every bundle, because which PR a run builds on (`findTargetPr`) is only known once the bundle is in. On an existing PR the checks read only the commits beyond its head on GitHub, plus each merge's combined diff and the PR's net diff less the files it already changed (`prFiles`). The thread's own branch and its `pr/<name>` branches keep the old path.

<a id="auth-allowed-users"></a>
## `ALLOWED_USERS` maps email→unixuser

both columns matter. A typo in the unixuser half doesn't fail OAuth; it fails later when the per-user agent can't be reached because no such systemd user service is running. Domain-wildcard entries (`*@example.com:default-unixuser`) match any email from that domain to the same unix user — handy, but it means a typo in the wildcard half silently routes everyone to the wrong account.

<a id="auth-local-mode"></a>
## `AUTH_MODE=local` is the only sign-in bypass, and it is loopback-only

`/auth/login` signs in as the first `ALLOWED_USERS` identity (a `dev@<domain>` identity when there are only domain rules). `authRouter()` throws at startup unless `NODE_ENV` is `development` or `test` and `BIND_HOST` is `127.0.0.1` or `::1`, and `/auth/login` returns 403 unless the caller is on this host (`isSameHostRequest` in `auth/localLogin.ts`: a same-host nginx or Apache makes every socket peer loopback, so the gateway's peer header and forwarding headers are checked too). The old `/auth/dev-login` route, which any non-production server exposed, is gone; don't bring back a bypass that is gated on `NODE_ENV` alone.

<a id="auth-okta-login-on-gesture"></a>
## A tab never starts the Okta login by itself; only a click or key press does

With `AUTH_MODE=okta` the ALB's `authenticate-oidc` action sends a request with an expired session to Okta and sets an `AWSALBAuthNonce` cookie that lives 15 minutes; the callback (`/oauth2/idpresponse`) answers 401 when that cookie is gone or was overwritten, and reloading that URL never helps (the code is single-use). Two things followed from that. Background requests must not redirect: the listener rule `oidc_deny_background` (example-org/terraform, `projects/termag/.../modules/termag/alb.tf`) gives `/termag/api/*`, `/termag/ws/*`, `/termag/health` and `/termag/auth/me*` a 401 instead, because each redirect overwrote the nonce of the login in progress. And no tab may reload itself into Okta: a probe that finds the session expired only marks the tab signed out (`markEdgeSignedOut` in `contexts/ConnectionContext.tsx`), `ConnectionOverlay` shows "Signed out of termag", and the next `pointerdown` / `keydown` calls `reauthenticate()`. An automatic reload from a probe, a background tab, or a `visibilitychange` (which also fires when a screen wakes at night) parked the Okta page with nobody there, and signing in on it hours later always failed the callback.

<a id="auth-routes-source-of-truth"></a>
## `routes/auth.ts` is the source of truth for sign-in modes

`authMode()` defaults to `google` and only switches to `okta` (ALB header), `oidc` (in-app code flow) or `local` (e2e stack) when `AUTH_MODE` says so explicitly. `.env.example` describes all four, but read the code for behavior and the example for the variable list.

<a id="auth-session-cookie-host-prefix"></a>
## Every cookie termag sets is `__Host-`, and only termag's paths receive the session cookie

In production the session cookie is `__Host-termag.sid`: Secure, `Path=/`, no `Domain` (`backend/src/auth/sessionCookie.ts`). The browser accepts a `__Host-` cookie only from this host itself, so another `example.com` host can't toss a session at termag (fixation, in `google` and `oidc` mode). A new cookie gets the prefix too: `backend/src/auth/sessionCookie.test.ts` lists every file that sets one and fails on a new one. `Path=/` sends it to the hosted apps on the host as well, so nginx forwards `$termag_upstream_cookie` (`deploy/nginx/termag-gateway.conf`, applied by `termag-proxy.conf`): the full `Cookie` header to `/termag`, the header without that pair to every other path (`deploy/termag-gateway-cookies.test.sh`). Off production (plain http: `npm run dev`, the e2e stack, stage) a `__Host-` cookie can't exist, so the cookie stays `termag.sid` on `/termag`, not Secure; scripts and docs for those stacks use that name. The rename signed everyone out once; the old name is never accepted, only expired when a browser still sends it.

<a id="automation-run-is-chat-turn"></a>
## An automation run is a chat-runner turn, and only the relay or the timeout sweep may finish it

the run's workstream carries a `claude-chat` workflow, so its status source is `chat-runner`, `isSdkChat` is true for it, and the simple UI opens it; its row goes `running → done|blocked|needs_input|failed` when `services/automations/complete.ts` sees the turn's `turn-end` through `chatRunner.onChatEvent` (every process relays its own boxes) or when the leader's `timeOutRuns` interrupts it past `maxRunMinutes`, counted from `startedAt` whatever the status says. A frame the relay drops (the project re-pointed to another box, the owner changed) leaves the run `running` until that sweep. The `full` tier sends `permissionMode: 'auto'`; `permissionModeForAgent` downgrades it to `dontAsk` for a box without `chat-auto-v1`, so the scheduler checks the capability first and records `skipped: runner_outdated` rather than running a useless read-only turn. `Project.kind` has three values: a `kind === 'metaterm'` check that means "not a normal project" must go through `projectKindTraits`, and a `kind: 'normal'` Prisma filter through `WORK_PROJECT_KINDS`, or an automation gets Branch off…, rename of its `run-*` workstreams and a main agent, or vanishes from PR pills, the briefing ledger, ask targets and the simple UI. The `automation-run` busy check (`boxLifecycle`) returns only runs inside their limit, so a stuck run never keeps a box awake past it. A `t3` automation (`Automation.kind`) is the exception: its run is one call to a T3 task's webhook on the box, with no turn behind it, so the scheduler finishes its row itself once T3 has the request (`startT3Run` in `services/automations/scheduler.ts`). A run's wake, start and end restart its box's idle clock (`boxActivity.noteAutomationRunActivity`) and the lifecycle sweep never terminates a box that hosts an enabled automation: without both, a box woken for a run read as untouched since its auto-park, went straight back down, and was terminated a day after its first park with the automation archived along with it (babysit-1027, 2026-10-30).

<a id="box-auto-update"></a>
## A stale box is asked to update by the orchestrator, behind `box-auto-update-enabled`, and "current" means the newest box AMI's commit

A box claimed from the warm pool is also brought to the orchestrator's own commit once, before its first launch, without the flag (the gotcha on claimed boxes, `box-claim-update`). `services/boxUpdate.ts` compares each connected owned box's `agentCommit` (the commit the agent process runs, from its hello; read once per process, so a checkout pulled without a restart still reports the old one) with the `TermagSha` tag of the newest published `Component=box` AMI, and sends the agent's `box-update` RPC (which starts `termag-box-update.service`; boxes have no timer for it, so this push is what runs it) when they differ: a minute after the hello and on a 30-minute sweep, leader work. The AMI tag is the target because `check-box-ami` in `publish-ami.yml` bakes a new box image exactly when `main` changed in a path that executes on a box, so there is no second copy of that path list and no GitHub credential on the orchestrator; the cost is the bake's lag (up to a few hours) and a harmless no-op push after an age-out rebake. One push per (box, target), in memory: a box that refuses the pull (a branch, a dirty tree, `~/.config/termag/no-auto-update`) is not asked again until the target moves. The flag's context is the owner + box multi-context (`boolVariation(key, user, fallback, box)`), so a rollout can start with one box. External boxes and agents without `box-update-v1` are skipped; the flag is read before the AMI, so a fleet with the flag off costs no `DescribeImages`. The push is the orchestrator's half; the box's half is one line back: `termag-box-update` posts `POST /api/box-update/report` at exit (instance token on stdin, a trap after the policy gate, so a policy no and `--check` post nothing), one word for the outcome — `failed` (any step failed, whatever the others did), `updated`, `deferred` (restart put off: a runner, `KillMode`), `skipped` (the pull refused: branch, dirty, detached), `current` — plus one token per step (`pull=pulled:3 reconcile=clean deps=unchanged agent=deferred:runner hooks=updated`, the vocabulary `parseBoxUpdateReport` accepts; `hooks` is optional, older scripts omit it) and the commit before and after. The orchestrator logs it as one `[BOX-UPDATE] <box> (<owner>) reports …` line (shipped to Observability, where the box journal is not) and writes it on the box row (`last_update_*`), so the admin Fleet list shows a *last update* column and the System page counts boxes by the last outcome they reported in the day beside the target (`boxUpdates.boxesByLastOutcome24h`; a row keeps one report, so these are boxes, not runs); Signals raise `box_update_failed` (a `failed` within a week) and `box_update_deferred` (a `deferred` older than a day, unless the connected agent already runs the pulled commit: a reboot restarts the agent without a new report). The agent's hello also carries `agentCommitAt` (`git show -s --format=%cI HEAD`), so Fleet sorts boxes by how old their agent build is against the newest image's bake date, and the detail card says *Nd behind*. A wrapper from before the report posts nothing and the row says *never reported*; a box whose orchestrator predates the route logs `report: not posted … answered 404` and carries on.

<a id="box-claim-update"></a>
## A box claimed from the warm pool is updated to the orchestrator's commit before its first launch, and every launch path waits for it

A pool box runs its image's commit, and the stale-box push only fires when a box is behind the newest box image, so a box claimed between a merge and the next bake launched without it (on 2026-10-30 four claimed boxes missed #1099's Fireworks /model menu). `services/claimUpdate.ts` runs from the claim (`warmPoolClaim.ts` `welcomeOwner`): when the box's agent runs another commit than this orchestrator (`termagVersion()`; the orchestrator has no GitHub credential to read `origin/main`, and the box pulls `origin/main` whatever target it is handed) and announces `box-update-v1`, it writes `claimUpdateStatus = 'updating'` on the row before the claim answers, sends `box-update` once the claim's credential delivery has landed, waits for the run's report (`updatePushedAt` cleared by `POST /api/box-update/report`) and, when the report says `agent=restarted` or `reconcile=reconciled`, for a new connection's hello (it closes the socket itself after a reconcile without a restart, since the markers `agent/credentials.js` advertises are read at hello). The whole wait is bounded by `CLAIM_UPDATE_TIMEOUT_MS` (150 s) from the claim, and no update is sent when the delivery left less than `CLAIM_UPDATE_MIN_RUN_MS` of it; a timeout, a failed RPC or a failed run ends it with the reason in a `[CLAIM-UPDATE]` warning and on the row, and the launch goes ahead on the commit the box has. No flag: `GET /api/box-update/policy` says `{enabled: true, reason: 'claim'}` while the row reads `updating` (for at most `CLAIM_UPDATE_POLICY_MS`), whatever `box-auto-update-enabled` says. The hold is in memory in the claiming process (`claimUpdateGate.ts`), which holds the socket every launch goes through, and every path that starts something on a box has to wait on it: `ensureAgentSessionsAndLaunch`, `applySetupEvent`'s `agent-connected` (in the background, so project create answers at once), `dispatchWorkspace`, `chatSendFor`, the chat-resume restore and the cloud runner's placement (`box-wait`, re-offered); an ask waits because the claim's connection is settled (`settleClaimedOwner`) only after the update. The connection is settled only once both the delivery and the update are over: a current box's update ends before its delivery does. A row an orchestrator left `updating` when it stopped reads as over in the UIs after `CLAIM_UPDATE_POLICY_MS` and is marked `timed-out` by the warm-pool tick. A new launch path on a box must wait too, or it can launch on the image's commit or under the update's agent restart. The update counts as the periodic push for the box image's current target (`noteClaimUpdated`), so the hello its restart brings does not run it again. A fresh claim has no live Claude session, so the box-side script never defers the restart for one.

<a id="box-deploy-reconcile"></a>
## `deploy/` is the source of truth, but only `termag-reconcile` makes it true on a running box

nothing else installs `deploy/` onto the live paths outside an AMI bake, so a box whose checkout is current can still be *running* artifacts from the image it launched from. This is not hypothetical: a live box had the merged `KillMode=process` fix in `~/src/termag/deploy/termag-agent.service` while `~/.config/systemd/user/termag-agent.service` was the baked copy without it, and a 95-line `~/.local/bin/termag-status` that predated the endpoint-resolution fix — two merged fixes, neither in effect. `termag-reconcile.service` now content-compares and installs on every boot, ordered `Before=termag-agent.service` so the agent starts from the reconciled unit and nothing needs restarting. Between boots, `termag-box-update.service` (installed by the reconciler, so it reaches boxes that predate it; started by the orchestrator over the agent's `box-update` RPC when the box runs an older commit than the current box image, never by the box itself) runs `deploy/termag-box-update --when-enabled`, which does nothing until the orchestrator says the `box-auto-update-enabled` flag is on for the box's owner (`GET /api/box-update/policy`; no answer is a no, so the flag is the fleet-wide kill switch), and otherwise: `git pull --ff-only` on a clean `main`, `termag-reconcile --check` / reconcile / `--check`, `termag-hooks-update` when the owner's `~/.claude/settings.json` hook lines are behind `deploy/claude-settings.json` (reconcile never touches that file), `npm ci` in `agent/` when its lockfile changed, and the agent restart described under the gotcha on restarting the per-user agent — so a box left alone picks a merged `agent/` or `deploy/` change up once the orchestrator asks for it. The one-time catch-up for a box whose agent predates the `box-update` RPC is `git -C ~/src/termag pull --ff-only && ~/src/termag/deploy/termag-box-update` (pull, reconcile, restart the agent when safe), run as the box user with its systemd user bus in scope. There is no SSH to a box, but every provisioned box carries `AmazonSSMManagedInstanceCore` and a live SSM agent, so from an operator session in the termag account the catch-up is one Run Command, which needs neither a key nor the Session Manager plugin: `aws ssm send-command --document-name AWS-RunShellScript --targets Key=tag:App,Values=termag --parameters 'commands=["u=termag; sudo -u $u env XDG_RUNTIME_DIR=/run/user/$(id -u $u) DBUS_SESSION_BUS_ADDRESS=unix:path=/run/user/$(id -u $u)/bus bash -lc \"git -C ~/src/termag pull --ff-only && ~/src/termag/deploy/termag-box-update\""]'`, then `aws ssm list-command-invocations --command-id <id> --details` for each box's stdout (one box: `--instance-ids i-…`). It is a one-off for boxes baked before the RPC, not a process: boxes from any later image are reached by the orchestrator's push, and the box reports its outcome (the stale-box update gotcha). The pull itself fails on a box whose git has no credential for the mirror; that is what the report's `pull=fetch-failed` says. If you add a box-side artifact to `deploy/`, add it to the table in `deploy/termag-reconcile` too, or it will only ever reach boxes through a bake. `claude-settings.json` is deliberately excluded because owners edit it (its termag hook lines are brought current by `termag-hooks-update`, which `termag-box-update` runs); the reconciler only appends MetaTerm's three read-tool approvals to the installed `~/.claude/settings.json` and sets its own `mcpServers.metaterm` key in `~/.claude.json`, both with `jq`, never rewriting anything else. `termag-reconcile --check` reports drift without changing anything, which is the quickest way to tell whether a box is actually running what you think it is.

<a id="box-dotfiles-private-rerun"></a>
## A private dotfiles repo is cloned by a rerun, never by the claim's own run

The claim path carries no GitHub credential on purpose: a warm box is nobody's until the claim, and `box-claim` is "git identity plus the URL". So `termag-hook-run claim` clones with a neutral global gitconfig, a public repo works, and a private one exits 10, `skipped`/`needs-auth`, with the URL kept in `~/.termag/dotfiles-repo-url`. On a box with the GitHub broker the clone could go through `/etc/gitconfig`'s rewrites, but the orchestrator sends `box-claim` first and delivers credentials only after its ack (`warmPoolClaim.ts`: `configureBox`, then `welcomeOwner`), so the first run always loses that race. Two reruns pick it up: the agent starts `termag-on-claim.service` again after a `credentials-apply` for `github` when the status file says `needs-auth` (`agent/on-claim.js`, `planOnClaimRetry`; it waits for a run in flight, and a delivered connection gets one rerun per 30 minutes, keyed by `onClaimRetryKey` on the broker, the login and the credential's `updatedAt`, so a reconnect's redelivery is the same connection and a token replaced on the Credentials page is a new one), and the owner reruns the hook after `gh auth login` on a box without one. A rerun has no `on-claim.env` (the unit removes it), so the runner takes the owner identity from the global git config the claim set. The two reruns can meet: the runner holds `~/.termag/on-claim.lock` for the whole run, so the second waits and then finds the checkout applied, where each would otherwise remove the other's half-made `~/.dotfiles` as an unfinished clone. The runner exits 0 for a skipped clone too; read `~/.termag/on-claim.status.json`, not its exit code. Making the clone wait for the delivery instead would hold the claim's `ready` on a GitHub round trip the box may never need.

<a id="box-hibernated-not-stopped"></a>
## `hibernated` is not `stopped`, and hibernation is fixed at launch

EC2 only takes `HibernationOptions` on `RunInstances`, so `Instance.hibernationConfigured` is written once and every older box keeps plain Stop until it is replaced. Two things gate it: an AMI tagged `Hibernation=supported` (packer `var.hibernation`, default off, `scripts/enable-hibernation.sh`) and the type's `HibernationSupported`; the root then grows by the RAM size because hibinit-agent's swap file lives on it. Keep the two power-down statuses apart: a `stopped` box has lost its RAM and is the one a start may replace, a `hibernated` one must only be resumed. A hibernate EC2 refuses falls back to a plain stop with a note on the row, and the power sweep resumes any box hibernated `BOX_HIBERNATION_REFRESH_DAYS` (55), because EC2 supports at most 60, and then stops it (`docs/box-hibernation.md`). Nothing hibernates a box any more (auto-park, the refresh and chat archive stop it, and a manual hibernate answers 409 `hibernate_off`), but every launch, the warm pool's included, still asks for hibernation, and a box hibernated before that still resumes. Whether the published image is tagged `Hibernation=supported` feeds the pool spec hash, so a newly tagged image rolls the pool.

<a id="box-per-unix-user"></a>
## Boxes are provisioned per-Unix-user

the Packer AMI ships with a `termag` default unix user, and cloud-init renames it to the project owner's username during provisioning. Don't hardcode `termag` as the unix user anywhere on the box; reference `$USER` or the value set by cloud-init.

<a id="box-quarantine-held-by-status"></a>
## A quarantined box is held by its status: every path that starts, terminates or reconnects a box must refuse `quarantined`

`docs/box-quarantine.md`. An admin's quarantine (`services/boxQuarantine.ts`) revokes the box's tokens, denies its role everything, strips its security group, stops it (the only step that ends connections already open: security groups are stateful), then snapshots its volumes (`Retain=true`, which `prune-snapshots.sh` honours), and then relies on nothing ever moving the row out of `quarantined` but an admin's terminate. Today that holds because `requestPower` refuses it (so every automatic wake does), `terminateBoxRow` refuses it (so the lifecycle sweep, chat delete and the CLI do), the `/ws/agent` handler refuses an agent for it, `CONNECT_TRANSITIONS` keeps it, and the sweeps select other statuses by name. A new path that starts, terminates, retires or re-provisions a box with its own `updateMany` guarded on the status it read would happily move a quarantined row along: check for `QUARANTINED` there too. And never decide from the row an agent's token was validated with: a quarantine can land between that read and what the connection does next, which is why `registerAgent`, credential delivery, `on-warm-start` and `launchBox` all read the status again right before they act. The owner's routes return the row through `ownerBoxView`, which drops the reason, the admin and the step log.

<a id="box-repo-environment-file"></a>
## A box's default size comes from the repository's own `.termag/environment.json`, which is not a space's `.termag/`

There is no map of repositories in termag's code: a repository that needs a bigger box says so in a `.termag/environment.json` committed to it (`{ "resources": … }`, the only key read today, for every box made for it, an ask's too; a multi-repo project takes the largest of its repositories'; other keys are reserved and ignored; docs/box-provisioning.md, "A repository's environment"). Its steps (`setup`, `run`, `ports`, `seed`, `secrets`) are read by the box, from the checkout, never from GitHub, and run in tmux session `termag-env-<key>` once a box made for the project has cloned it: a box whose app didn't come up is `termag-env status` and `~/.termag/env/`, not the orchestrator log. The orchestrator reads it from GitHub, at the default branch's head, with the owner's credential (`services/repoEnvironment.ts`), so a change to it is a PR in that repository, not in termag. It shares only its folder name with a space's `.termag/` memory (`prompt.md`, `memory/`), which lives in a termag space and never sizes anything: don't look for one in the other, and don't put a repository's environment in a space. Nothing in the file can fail a create (a bad value is a warning and the next size in the order), so a box at the "wrong" size usually means a value was ignored: read the create's `warnings`, or the `[BOX] …: …environment.json…` warning in the orchestrator log. A requirements size (`{ "vcpu", "memoryGiB" }`) needs `ec2:GetInstanceTypesFromInstanceRequirements` on the provisioner role, and falls back to the default with a warning without it. A `diskGiB` beside them sets the box's disk (50 to 300 GiB, else 120; docs/box-provisioning.md, "Disk size"), and no disk under the box image's own snapshot (120 GB) can be launched, so 50 to 119 comes up as 120; a box at another disk than the default never comes from the warm pool. A box made from an **environment** (`--environment`, the create dialogs' pickers) reads only that environment's definition (its `resources`, `diskGiB` included): its inline JSON, or a pointer's file read from the **pointer's branch** (not the default), and none of its repositories' own `.termag/environment.json`. When an environment's box is the "wrong" size, look at its definition (its page shows it, and what it resolves to now, with warnings), not at the repositories'.

<a id="box-resize-hibernation-pool"></a>
## A resize stops a hibernated box plainly first, and a resized box may lose hibernation and its pool spec

EC2 can't modify a hibernated instance ("While your instance is hibernated, you can't modify it"), so `services/boxResize.ts` resumes a `hibernated` box, waits for its agent, stops it plainly and only then calls `ModifyInstanceAttribute`: what it held in memory is gone, and it is left `stopped`, like a box that was stopped to begin with. A hibernation-capable box launched with its root grown by its RAM for hibinit-agent's swap file (`planHibernation`), so a resize to a type with more RAM sets `hibernationConfigured` false (`hibernationAfterResize`): otherwise every later hibernate would fall back to a stop with a note. Memory comes from DescribeInstanceTypes, else the type's name; when neither answers, the flag is left as it was, so a failed lookup never drops hibernation. A box claimed from the warm pool keeps `poolSpecHash` until a resize clears it, because its type no longer matches the spec it launched from; an unclaimed pool box is never resized (409 `pool_box`), since a claim matches pool boxes by size and spec hash. While a resize holds the box (its open `resize` row in `box_events`: not finished, under an hour old) every `requestPower` without `forResize` is refused, the sweep's and an ask's included, so nothing starts a box between its stop and its retype; a resize cut off by a restart lets go only when that hour is up.

<a id="box-setup-off-core-only"></a>
## Every `termag-reconcile` item is `core` or `feature`, and a box with termag setup off gets core only

Each row of the artifact table ends in a class, and each step after it is listed with one in `steps()`. A box whose `~/.config/termag/setup` says `off` (cloud-init writes it for a box launched with `Instance.setupEnabled = false`) gets only `core`; anything else counts as `feature`. `deploy/termag-reconcile.test.sh` fails on an unclassified row or step, or a step called outside `steps()`, so a new skill or config merge cannot reach a box with setup off by accident: pick `feature` for whatever writes the owner's agent, shell, git or docker config. The image is still baked with setup on, so first boot runs `termag-reconcile --strip` to remove the feature files that are still termag's unedited copies. The server side reads `Instance.setupEnabled`, never the marker: credential delivery refuses such a box, and Hand off, the orchestrator chat and asks answer 409 `setup_disabled`. A repository's `.termag/environment.json` `"setupEnabled": false` applies only for a caller that states it (the CLI); a box made in the UI has setup on.

<a id="box-sg-ascii"></a>
## EC2 security-group descriptions must be ASCII

`terraform/box` had to swap an em-dash out of an SG description because EC2 rejects non-ASCII characters there. Anything you add to `main.tf` / `variables.tf` describing AWS resources should stay ASCII-only, and so must every description `boxProvisioner` sends with `CreateSecurityGroup` / `AuthorizeSecurityGroupIngress`.

<a id="box-xclip-shim"></a>
## `~/.local/bin/xclip` is a termag shim, not X11 xclip

the per-user agent installs `agent/xclip-shim.sh` there on Linux (idempotent, content-compared, on every startup) so Claude Code's Ctrl+V image paste has something to read on a box with no display. A browser paste sends the PNG over the terminal WebSocket, the agent writes `~/.cache/termag/clipboard.png` and only then types `\x16`. The shim answers exactly two invocations — `-t TARGETS -o` (prints `image/png`) and `-t image/png -o` (streams the file, then deletes it) — ignores a mailbox older than 60s, and fails like an empty clipboard for text and every other target. It shadows a real xclip if one is later apt-installed, since `~/.local/bin` usually precedes `/usr/bin` on `PATH`; rename or remove it if a box ever needs the real thing. `agent/xclip-shim.test.sh` covers the probe/read/staleness contract.

<a id="briefing-on-owner-box"></a>
## The daily briefing runs on the owner's box, never on the orchestrator, and is opt-in

the backend holds no model credential: `services/briefing/runner.ts` asks a `ready` EC2 box whose agent announces both `tmux-create-command-v1` and `briefing-v1` to start a one-shot tmux session, `<boxUser>-briefing-<id>-r` (the `-r` tail keeps it from parsing as a project pane), whose only process is `~/.local/bin/termag-briefing <id>`. The wrapper fetches the prompt from `GET /api/briefings/:id/job`, runs `claude -p` with no built-in tools (`--tools ""`), only its own metaterm MCP server (`--strict-mcp-config`), `--permission-mode dontAsk` and the MetaTerm read tools allowed — `--allowedTools` alone would merge with the owner's settings grants — plus `METATERM_SEND_KEYS=off` and `TMUX`/`TMUX_PANE` unset (so `termag-status` hooks post nothing for it), and posts the result to `POST /api/briefings/:id/result`; both routes answer only the token of the box the run was placed on. It never starts a stopped box or claims a warm one: no box ready means a `skipped` row, which the scheduler retries each tick until the local day ends. The scheduler is leader work and `briefings.scheduleKey` (`<userId>:<local day>`, unique) keeps it to one scheduled run per user per day across overlapping processes; any start holds a per-user advisory lock around its running-run check, so there is one run at a time per user. `User.briefingSchedule` `{}` means off; turning it on needs a timezone. The window is "since the previous done briefing", or the start of the previous local day on a first run or when the previous one ended over four local calendar days ago (`stale`; days, not hours, so a weekend stays whole), and every surface leads with its label. The ledger (`GET /api/briefings/ledger`, MCP `activity_ledger`) answers an index by default and one session in full with `projectId`/`workstream`, both from one build cached for 25 minutes for a briefing run and 5 for an on-demand read (`services/briefing/ledgerCache.ts`), with what the result needs (totals, patterns, charts) also kept on the run's row (`rememberLedger`) for a result that lands on another process: a whole ledger runs past Claude Code's MCP output cap on a busy day, and the run has no Read tool for the file it spills to. The model writes short bullets in three sections (`BriefingContent` version 2: Worked on, Left open, Work better; `content.ts` reads version 1 rows as version 2), and Work better items must name one of the ledger's `patterns` (`services/briefing/patterns.ts`, deterministic, over 14 days) so Done and "Defer a day" (`briefing_dismissals`, keys `pattern:<id>` and `open:<projectId>:<workstream>`) have a stable key; the charts are database-only and stored on the row (`briefings.charts`). It reads transcript digests and pane tails from the caller's OWN projects only; the fields it marks untrusted are never stored. A box shows up as "running an older termag" until its agent restarts (`briefing-v1`) and `termag-reconcile` installs the wrapper and the two extra read-tool approvals.

<a id="browser-pane-guest-chromium"></a>
## The browser pane's guest Chromium runs as `termag-guest`, and its sandbox is root's

`deploy/termag-guest-browser-setup` (run by the bake through `install_guest_browser` in `packer/scripts/box-lib.sh`, and by `termag-reconcile` through `sudo -n` on every boot, so older boxes converge) creates the `termag-guest` system user (home 0700, no shell, never in the box user's group), the root-owned wrapper `/usr/local/libexec/termag-guest-chromium` (which also owns the guest's profiles, in its 0700 home where the box user can't reach: it launches only with a `--user-data-dir` under `~termag-guest/snap/chromium/common/termag-browser-pane/profiles/`, seeds a new one's WebRTC `ip_handling_policy` before Chromium reads it, because the command-line flag does nothing on the snap's Chromium, and lists and deletes them with `--termag-list` / `--termag-forget <name>`), `/etc/sudoers.d/termag-guest-browser`, and the nftables table `inet termag_guest` (`deploy/termag-guest-browser.nft`, loaded by the system unit `termag-guest-browser.service`) that rejects everything `termag-guest` sends except TCP to the agent's pane proxies on `127.0.0.1:47100-47131`. Five things to keep. **The proxy range is reserved** (`net.ipv4.ip_local_reserved_ports`, `/etc/sysctl.d/60-termag-guest-browser.conf`, merged into the live value by the setup): it sits inside the kernel's ephemeral range, and without the reservation any owner service that binds port 0 (Codex's app-server does, with no token on its socket) could be given a port in the one window the guest may reach. **The sudoers entry names the box user by uid** (`#<uid>`, rendered from `@AGENT_UID@` at install): cloud-init renames the box user to its owner's name at launch (`usermod -l`, uid kept), so a name would go stale; unrendered, the line is a comment and grants nothing. **The agent must pass `-C 5`** (`sudo -n -C 5 -u termag-guest /usr/local/libexec/termag-guest-chromium …`): fds 3 and 4 are the DevTools pipe, and `closefrom_override` is set for that one command only; there is deliberately no `--remote-debugging-port` fallback, which any process of the box user could attach to. **`termag-guest` lingers**, because `snap run` places Chromium in a snap scope through the running user's own systemd manager and refuses without one ("… is not a snap cgroup for tag snap.chromium.chromium"); the wrapper sets that user's `XDG_RUNTIME_DIR` and bus. That manager requires the egress unit (`termag-guest-browser-required.conf` under `user@<uid>.service.d`), so no guest Chromium starts without the rule, and lingering is enabled last and never after a failed step. **Reload `termag-guest-browser.service`, never restart it**: a restart takes the guest's user manager, and every live guest browser, with it. `sudo TERMAG_GUEST_BROWSER_REQUIRE_LIVE=1 sh deploy/termag-guest-browser.test.sh` loads the real rules in a network namespace and probes them as the guest's uid and another one.

<a id="chat-live-turn-stdin"></a>
## A live chat turn's stdin closes once, late, and the wrapper says so with `stdin-ended`

A live turn (`agent/chat-turn.js`, `meta.live`) feeds the user's later messages to `claude -p` on stdin, and ending stdin is the only way to let Claude exit, but a closed stdin cannot be reopened. Claude's answer is not the end of its work: a background task that finishes after the `result` sends a `task_notification`, and Claude wakes into a turn of its own (an `init`, more work, maybe more background tasks). Ending stdin at the first `result` with no tasks left made such a turn deaf for as long as it ran, and inbox messages sat there, shown as queued. So the tracker (`createLiveTracker`) counts an `init`, `assistant` or `stream_event` after a `result` as work until the next `result`, holds off up to `WAKE_MS` after a notification for the turn it wakes (a killed task's notification wakes none), and ends stdin only after Claude has looked done for `IDLE_GRACE_MS`. It writes `<turn dir>/stdin-ended` before it does; `chat-runner.js` `readsInput` reads that for `takesLive`, history's `liveInput` and `steerAsk`, so a send after it queues for the next turn, and an ask follow-up is refused `input_closed` (the orchestrator holds it as the next turn), rather than going into an inbox nobody reads. `chat-turn.js` is started from the checkout for every turn, so a pulled change reaches the next turn without an agent restart; the runner side lives in the agent and needs one (gotcha on `agent/agent.js` restarts).

<a id="chat-mermaid-sandboxed-frame"></a>
## A Mermaid diagram is drawn in a sandboxed frame with svg-pan-zoom and Hammer.js, and Mermaid is only ever imported dynamically

Diagrams come from space files and agent output, so neither is trusted. `frontend/src/chat/mermaid.ts` runs Mermaid with `securityLevel: 'strict'` and `htmlLabels: false`, and lists those keys (with the theme's and `look`) in `secure`, so a diagram's own `%%{init}%%` or frontmatter can't turn them back on. The SVG it returns is never put in termag's DOM: `diagramDocument` makes it the `srcdoc` of an iframe with `sandbox="allow-scripts"` and nothing else (an opaque origin: no termag cookies, storage or DOM, no popups, forms or navigation), whose own CSP runs only the one script carrying a fresh nonce: Hammer.js, svg-pan-zoom (the pan and zoom mermaid.live uses, with no visible controls and Hammer.js as its `customEventsHandler`, as in its mobile demo) and `frameScript`, the glue. Never add `allow-same-origin` to that sandbox, `'unsafe-inline'` to its `script-src`, or insert the SVG with `dangerouslySetInnerHTML` or an inline `<svg>`: any of them lets a diagram's markup act as termag. The page and the frame talk only through `postMessage` with `FRAME_MESSAGE`: the frame says when it is active, the page may say `deactivate`, and each side reads only the other's window.

Gestures. A whole file (`mode: 'file'`) is always live: the wheel zooms around the pointer, a drag pans, touch is Hammer's. A diagram in a reply or a Markdown file (`'embed'`) starts as a picture so the page scrolls past it: a plain wheel is stopped in the capture phase before svg-pan-zoom's own listener sees it (Ctrl/⌘ + wheel and a trackpad pinch still zoom), `beforePan` refuses, and Hammer is off with `touch-action: auto`. A click, tap or Enter makes it live; Escape, the frame losing focus, or the page scrolling (`MermaidDiagram.tsx` posts `deactivate`) makes it a picture again. Don't turn the embed's wheel back on unconditionally: the chat transcript would stop scrolling over every diagram. Hammer's pan recognizer is horizontal-only by default; it is set to `DIRECTION_ALL`, and Hammer uses `TouchInput` only, or a mouse drag would pan twice (Hammer's and svg-pan-zoom's).

The frame needs the diagram's size (`sizedSvg`, `frameStyle`; a whole file's frame takes the file pane's height as a flex child), and its text can only use system fonts the page also has, so the font is `--font-ui` (a system stack): Mermaid measures labels in the page, and a web font would make them wider than their boxes. The look is Mermaid's `base` theme with termag's tokens (`mermaidConfig`, `diagramCss`), not a stock theme. Its colours meet WCAG AA on the theme they're drawn in (4.5:1 text, 3:1 outlines and lines): outlines use `diagramColors().graphic`, not `--border` (about 1.4:1 on the canvas), and the pairs are tested in `mermaid.test.tsx`. A `classDef` or `style` that sets a `fill:` with no `color:` gets one added (`readableLabels`, dark or light by the fill), because Mermaid would keep the theme's label colour on any fill. svg-pan-zoom measures the SVG once, when it starts, so the frame starts it only once the SVG itself has a box (on load, a resize or the SVG's ResizeObserver), never by the window's size: a frame the page hides has a 0 × 0 SVG, and so, in Chrome (the sandboxed frame is out of process), does one whose script runs before its document is laid out, with the window already sized. Fitted there its zoom is NaN (`matrix(0,0,0,0,0,0)`) and every refit throws; that left about a third of file-view loads of a board blank. A zoom that comes out unusable or a refit that throws drops svg-pan-zoom back to the plain SVG until the next layout. The frame tells the page `waiting`, `drawn` or `failed`, and `MermaidDiagram` shows the source with an error for a frame that fails or says nothing within `FRAME_START_GRACE_MS` of its load, and for an SVG with no size: a diagram is drawn or explained, never an empty box. Reproduce frame races in Chromium's full browser (`chromium.launch({ channel: 'chromium' })`): Playwright's default headless shell never showed them (0 blank in 30 loads, against 11 in the full browser). Mermaid is about 680 KB before a diagram type's own chunk, so it is imported only with `import('mermaid')` in `mermaid.ts`, Hammer.js's and svg-pan-zoom's source with it (`?raw`), and the components load through `MermaidBlock` (`React.lazy`); `mermaid.test.tsx` fails on a static import anywhere in `src`. Detecting a fence or a `.mmd` path is `mermaidFence.ts`, kept apart so Markdown, the pane chat and the file views don't pull the drawing code in. A fence still streaming (`open` from the parser, or no closing fence in the pane capture) stays code, so a half-written diagram never flashes an error. Mermaid's config is global, so renders are queued one at a time.

Testing, all in jsdom with no browser. `mermaid.render` works there once `SVGElement.prototype.getBBox` and `getComputedTextLength` are stubbed (the `beforeAll` in `MermaidDiagram.test.tsx`): sizes come out wrong, but labels, `aria-roledescription` and sanitization are real. With `htmlLabels: false` each word of a label is its own `tspan`, so match a label by joining them, never with `toContain` on the raw SVG. To prove Mermaid is not loaded, `vi.mock('mermaid', factory)` with a counter in the factory, which runs only when the module is imported (`mermaidLazy.test.tsx`). The frame's own script runs by giving its whole `srcdoc` to `new JSDOM(html, { runScripts: 'dangerously' })`, with the `?raw` libraries mocked to record their calls (`MermaidPanZoom.test.tsx`, `MermaidGestures.test.ts`); jsdom has no types in this repo, so it is imported dynamically.

<a id="chat-open-mode-own-tree"></a>
## A chat turn gets its full tools only on the project's own tree, and a read-only turn tells the model and the person why

A trusted chat asks for `bypassPermissions` (or `auto`), but `settleTurnMode` re-reads the checkout on every turn and drops to the confined `dontAsk` (`--tools Read,Grep,Glob`, an empty `--strict-mcp-config` or, with `chat-confined-mcp-enabled`, only the owner's broker connectors rebuilt by the box under a read-tool allowlist, the scratch config dir) unless `ownTreeRefusal` passes. What it guards is a tree whose startup config came from someone else, a fetched pull request or a fork, loading under bypass: `.claude/` (settings with their `apiKeyHelper`, env, hooks and allow rules), `.mcp.json` and `.pi/`. An upstream on a `refs/heads/*` branch of origin is the usual proof. A branch with no upstream also counts, in the project's main worktree only (never a linked worktree or an ask's thread clone), when git's reflog says it was `Created from` a branch of origin, a local branch that tracks one, or HEAD while on such a branch (`originStartOf`), and nothing under `STARTUP_CONFIG_PATHS` differs from the merge-base with that origin branch, in HEAD, the working tree or as an untracked file. That is the chat's own `git switch -c <b>` off main. Before this, that branch silently confined every later turn and the model reported ToolSearch and MCP as broken (platform-eks-components, 2026-10-29). FETCH_HEAD, a pull ref, a commit id, an expired reflog, or an edited `.mcp.json` still confine. Keep the path list in `STARTUP_CONFIG_PATHS` in step with what Claude Code and pi load at start.

A confined turn is never silent: `readOnlyNotice` goes into the turn's message inside `<termag-box-notice>` (never the system prompt, which must keep its bytes for the prompt cache), naming the reason and `readOnlyFix`'s fix, so the model says why instead of retrying missing tools. turn-start carries `readOnly` and `readOnlyFix`, which the simple UI shows as a LaunchPad warning under the message (`ReadOnlyTurnNotice`). An open-mode repo turn's appended system prompt carries `BRANCH_UPSTREAM_PROMPT` (start branches from origin's branch, push with `-u`). Its condition is the requested mode and the origin, not this turn's outcome, so its bytes don't flip between turns.

<a id="chat-pi-open-tiers-no-classifier"></a>
## pi's open tiers have no classifier, and only `--no-extensions` keeps the owner's MCP servers out

pi never asks before a tool call. A pi turn in `auto` (an automation's full tier) or `bypassPermissions` runs bash, edit and write unprompted: it is bypass in all but name, so the own-tree check (`turnModeFor`) is the only gate, and the read tier is `--tools read,grep,find,ls`, where the other tools do not exist. pi's MCP support is a built-in extension that loads `~/.pi/agent/mcp.json` (on a box, the owner's metaterm server) into every run; there is no MCP flag, but `--no-extensions` turns built-in extensions off while an explicit `-e` (the launcher's telemetry extension) still loads. `piTurnArgs` passes it, with `--no-skills`, for every turn but `bypassPermissions`, matching a Claude turn's empty `--strict-mcp-config` and scratch config dir. `--no-approve` on every turn skips the checkout's `.pi/` settings, extensions and MCP servers.

<a id="chat-pi-process-group-stop"></a>
## A pi chat turn never loads the pi status extension, and is stopped with SIGTERM to its process group

A chat-runner turn on the pi engine (`agent/chat-runner.js` `piTurnArgs`, capability `chat-pi-v1`) runs `termag-pi-headless --headless`, which must not add `termag-status.ts`: the turn's status already comes from the relay as source `chat-runner`, and a second source double-books working time (gotcha [status-working-time-source](#status-working-time-source)). pi runs every bash tool in a session of its own, so SIGINT stops pi and leaves the tool running, orphaned; SIGTERM makes pi kill the tool and record its result. `agent/chat-turn.js` therefore spawns the launcher detached (pi leads its own process group, whatever shell the launcher is) and every stop of a pi turn, from the runner's `armEscalation` or the wrapper's hangup path, is SIGTERM to that group, then SIGKILL. A SIGKILL still orphans a running tool; nothing reaps it yet. A resume after a stop works, but the model may claim the stopped command finished.

<a id="chat-pi-turn-end-settled"></a>
## A pi turn ends on `agent_settled`, and a model error exits 0

`agent/pi-events.js` turns pi's `--mode json` stream into the Claude events the backend reads. The `result` is written at `agent_settled`, never `agent_end` (a retry or compaction may follow it); `agent_end.messages` is only that run's messages, with pi's system prompt as a `role: "system"` message the normaliser drops. pi exits 0 on a model or HTTP error (a bad alias, a broker 403 or 502): the only sign is the last assistant message's `stopReason: "error"`, which becomes `result.is_error` with pi's `errorMessage` as the text. A non-zero exit (the launcher's pre-flight: 75 SSO, 69 broker, 127 missing) has no stream at all and becomes `runner-error` from stderr. Fixtures recorded from pi 1.0.2 on a model broker are in `agent/fixtures/pi/`, and from pi 1.5.0 (the pin since 2026-11-03) in `agent/fixtures/pi/1.5.0/`; a pi bump must re-record and pass `agent/pi-events.test.js`.

<a id="chat-stream-line-timestamps"></a>
## In Claude's stream-json, only `assistant` and `user` lines carry a time

In a chat turn's `~/.termag/chats/turns/<id>/events.jsonl` (checked 2026-10-28), `assistant` and `user` lines have a `timestamp` (ISO, UTC), the same one the transcript entries `historyEntries` passes through have. `stream_event`, `result`, every `system/*` line (init, `hook_*`, `task_started`, `task_notification`) and the runner's own `turn-start` and `turn-end` have none; a turn record's `at` is when the turn ended. So a tool call's start is its `assistant` line's time and its end the `tool_result` user line's. Anything else can only take the newest time seen so far, marked as a guess. Never use the time the browser received a line: a replay from `events.jsonl` delivers them all at once.

<a id="chat-turn-cost-session-total"></a>
## A chat turn's `total_cost_usd` is the session's cost so far, not the turn's

Each chat turn is `claude -p --resume <session>`, and Claude Code carries the session's cost on across resumes, so the `result` event's `total_cost_usd` is everything the session has cost so far (checked on 2.1.310: three resumes of one session reported 0.0310, 0.0337, 0.0364; `duration_ms` is the turn's own). Summing it per turn made a 94-turn chat that cost about $176 show $13,640. A turn's own cost is what the total grew by since the session's last turn (`turnCost`, in `agent/chat-runner.js` and `frontend/src/chat/sdkChat.ts`). A total lower than the one before is a counter that started again, so all of it is the turn's. The runner's turn record (`~/.termag/chats/<chat>.turns.jsonl`) keeps the total as `sessionCostUsd` and the turn's own cost as `costUsd`. Records written before `sessionCostUsd` existed hold the total in `costUsd`, and `parseTurnRecords` prices those again, per `sessionId`, on every read. The browser takes a record or turn-end that carries `sessionCostUsd` as already priced. For an older agent's records and turn-ends, and for the `lastResult` fallback, it takes the growth itself, in order, starting again at a clear. The e2e fake (`scripts/e2e/fakes/claude-stream.mjs`) reports a session total too, kept in `<transcript>.cost`. An automation run's `costUsd` is right as it is: a run is the first turn of a new session, written once. To see it for yourself, resume a session a few times with `claude -p --resume <id> --model haiku < /dev/null` (under a cent; without the `< /dev/null` Claude waits 3 s for stdin and warns).

<a id="cloud-runner-bazel-output-base"></a>
## A session checkout's Bazel output base is removed by `termag-claude-runner`, by path hash

Bazel keys the base on the MD5 of the workspace path under `~/.cache/bazel/_bazel_<user>/`, about 12 GB per checkout of a large Bazel repository, and nothing else ever removes it. The wrapper removes it (detached, after `chmod -R u+w`) when the checkout is released or kept, and sweeps bases whose workspace is gone at start, only when `DO_NOT_BUILD_HERE` names the checkout and `server/server.pid.txt` is dead. The shared `~/.cache/bazel-disk` and `~/.cache/bazel-repo-contents` are deliberately outside that root. Don't move them under it.

<a id="container-no-local-tmux"></a>

<a id="deploy-db-guard"></a>
## `termag.service` runs `db:guard` before every start, and it can refuse

`ExecStartPre` runs `backend/dist/scripts/dbGuard.js` (rules in `config/dbGuard.ts`). With a local database it refuses while `/srv/termag/DATABASE_MOVED_TO_RDS` exists (the RDS cutover wrote it; the container's copy is stale) unless `ALLOW_DOCKER_ROLLBACK` exists too, which `termag-rds-cutover rollback-to-docker` writes after copying Aurora back. On RDS (`PG_IAM_AUTH=true`) it refuses an empty or missing `users` table unless `ALLOW_EMPTY_DATABASE` exists, so an unrestored cluster never comes up as a blank termag that invalidates every box token. A termag that won't start after a database change: read `journalctl -u termag` for `[db:guard] REFUSED` before anything else.

<a id="deploy-host-homes-cutover"></a>
## Host homes reach a new orchestrator only after the old one terminates, and nothing may touch a host account before that

the host data volume (`/srv/termag`, `/home` bound from it) is attached after boot by `termag-data-attach.service`, which waits for the volume to be `available` (blue holds it until the ASG terminates it), mounts it, re-adopts the accounts and only then writes `/run/termag/host-storage-ready`. Until then `ensureHostSetup` mints nothing and `hostAgentUnavailableResponse` answers 503, and `deploy/termag-host-setup` exits 3 unless `findmnt` shows `/home` as the volume's bind: an account created on the root disk's `/home` takes a UID a volume home uses and vanishes under the mount. Keep both guards; a new path that creates host accounts or host tokens goes through `ensureHostSetup`. Three things are deliberate. The unit is `Type=simple`, never oneshot: its start job would hold `multi-user.target` and cloud-final, which starts the backend, so green would never serve and blue never release the volume. The script never detaches the volume from another instance, however long it waits; a stuck attach is the runbook's (confirm the holder is gone, snapshot, attach by hand, `systemctl restart termag-data-attach`). Nothing snapshots the volume on a schedule: the runbook takes a manual snapshot before the first handoff deploy and before any manual attach. And there are no fstab entries for the volume, because a boot that bound `/home` before the mount would bind an empty directory. The ASG is pinned to the volume's AZ for the same reason the volume can't follow it.

<a id="git-marks-prs-and-commits"></a>
## A PR or commit made on a box is marked as termag's, and authorship is never touched

PR bodies go through `deploy/termag-pr-body` (installed to `~/.local/bin` by termag-reconcile), which wraps the body Cursor-style in `<!-- TERMAG_PR_BODY_BEGIN -->` / `<!-- TERMAG_PR_BODY_END -->` and appends a hidden `<!-- termag: box=<EC2 instance id> project=<name> [ask=<thread>] -->` line and a `<sub>Opened from termag</sub>` footer. The one PR termag opens itself is an ask's draft PR, whose body `services/agentMessages.ts` builds in the same shape and `services/askPublish.ts` sends. The broker only sees requests through Envoy's ext_authz, which cannot rewrite a body, so agents' `gh pr create` reaches the wrapper only through the `termag-pr` skill (`deploy/claude-skills/`, `deploy/pi-skills/`); a provider without skills, or a human typing `gh`, produces an unmarked PR. The skill has the agent write the title and body to files with its file tool and run `deploy/termag-pr-create TITLE_FILE BODY_FILE [flags]`, a fixed argv that hands both to `gh` without a shell ever parsing them: a title or body typed into `--title "..."` or a heredoc is repo-controlled text the agent's Bash tool would execute, and pi runs Bash unprompted. Keep any new example in the skill free of title or body text. Commits get `Generated-by: termag` from `deploy/termag-commit-msg`, the `commit-msg` hook of the box user's git template (`init.templateDir`, in `~/.config/git/config`), which termag-reconcile also copies into existing `~/termag/projects/*` repos that have no `commit-msg` of their own. The project clone (`agent/project-clone.js`) hides the global config from git, so it reads `init.templateDir` itself and passes it as `--template`. It is deliberately not a global `core.hooksPath`: `pre-commit install` refuses to run while one is set. A repository with its own `commit-msg` gets no trailer unless it chains to ours (pre-commit's `commit-msg.legacy` does), an owner's own `init.templateDir` turns the whole thing off, and `git config termag.trailer false` turns it off per repo or globally. No labels are created or added.

<a id="github-broker-ghes-meta"></a>
## To `gh`, the GitHub broker is a GitHub Enterprise Server, so the gateway answers its version probe

`gh` treats any host but github.com as GHES. Before some commands it reads `installed_version` from `GET /api/v3/meta` and parses it as semver (gh's `internal/featuredetection`, `resolveEnterpriseVersion`): `gh pr list` with `--author`, `--assignee`, `--label`, `--search` or `--draft` (plain `gh pr list`, and `--state` alone, make no check), `gh issue list` with `--search`, `--label`, `--milestone`, `--type` or `--web`, `gh search issues` and `gh search prs`, and `gh workflow run`. api.github.com's `/meta` has no `installed_version`, so without help each of those exits with `malformed version: `. The gateway's Envoy (the example-org/terraform `claude-gateway/envoy-config` module, `github_meta_lua`) is to add `installed_version` (`github_ghes_version`, 3.21.0, the highest threshold in gh 2.103.2) to a 200 from `GET /api/v3/meta` and leaves the rest of the body, and every other path, as GitHub sent it; `fakes.test.sh` checks it through Envoy and runs those commands with the real `gh`. That change is not live yet (the broker's `/meta` still has no `installed_version`), so until it is, search over REST instead: `gh api -X GET search/issues -f q='repo:<owner>/<repo> is:pr is:open <terms>'`, not `gh pr list --search` or `gh search prs`; `termag-overlap` lists open PRs over REST for the same reason. Page a repository's lists by hand (`repos/<owner>/<repo>/pulls?page=N`): `gh api --paginate` follows GitHub's next-page links, which name `/repositories/<id>/`, and the broker answers those 404. Raise the version when a `gh` release compares against a higher one. Everything else `gh` probes on an Enterprise host already passes through correctly: GraphQL schema introspection reaches github.com's own schema, the `/api/v3/` root answers with its scopes, and `gh` reads no `X-GitHub-Enterprise-Version` header. One thing stays GHES-shaped whatever the broker answers, because `gh` decides it from the hostname: assignees and reviewers go through the legacy user-only API, so a bot such as `@copilot` can't be assigned. `gh` caches a `/meta` answer for 24 hours (`~/.cache/gh`), so a box that cached the bad one keeps failing until it expires or that directory is removed.

<a id="o11y-agent-resource-attributes"></a>
## Every agent telemetry resource carries the same four attributes

`termag.agent`, `termag.session.kind` (`interactive` for a pane on a box, `cloud` for a runner, `chat` for a simple-UI chat turn, `ask` for every turn of a `termag ask` thread's chat, `oneshot` for the chat's Haiku title and heading calls, which also carry `termag.oneshot=title|heading` so they never count as a person's turns), `termag.project` and `termag.workstream`, beside the two context keys. Claude's come from `sessionTelemetrySettings` (agent, kind) and the launch (`launchCommandFor` types `TERMAG_PROJECT=… TERMAG_WORKSTREAM=…` ahead of `termag-credentials telemetry-launch <replay|->`, which adds project and workstream to the resource; the runner sets all four itself, under the reserved `claude:cloud` project). The chat runner's `claude -p` runs are not typed launches either: `chat-send` (and `ask-run`'s chat, and `chat-resume-claim`) carry the project's name as `project` beside the workstream, and `agent/chat-runner.js` `chatTelemetryEnv` runs the same `telemetry-launch -` with `TERMAG_PROJECT`/`TERMAG_WORKSTREAM` plus `TERMAG_SESSION_KIND` (`chat`, or `oneshot` with `TERMAG_ONESHOT`), which replaces the settings' kind, and puts the result in the run's one `--settings` (beside a confined turn's hooks closure and a backend's settings; Claude Code reads only the last `--settings`, and the scratch config dir copies the owner's resource, so it has to go there). An Open in full UI resume is a pane: it gets the pair and names `interactive`. Devin and Cursor get project and workstream the same way through `termag-agent-otel` and `termag-cursor-otel-hook`. Codex's app server is not a typed launch (the box's status bridge starts it), so the pair travels in the `codex-session-start` RPC (`project`, `workstream`) into the bridge's environment (`agent/codex-resource-env.js`), where `termag-agent-otel` reads it; a bad value drops the pair (a bad kind the kind), and any failure of the script leaves the run on the settings' resource, never the launch. pi's extension does not read the pair yet. Environment, not flags, so a box whose scripts predate the pair ignores it rather than fail the launch. Query on `termag.agent`, since Codex replaces `service.name`, and on `termag.session.kind`, not `terminal.type` (a chat turn and a one-shot both say `non-interactive`), to tell a pane from the chat. **An ask's turns also say who asked**: the orchestrator sends `telemetry` (`services/askTelemetry.ts`: the thread, the message's hop, and the thread's parent, which is the session that sent its first ask, so a nested ask's parent is the ask chat that asked) in `ask-run` and in an ask chat's `chat-send` `ask`; `chatTelemetryEnv` hands it to `telemetry-launch` as `TERMAG_ASK_THREAD`, `TERMAG_ASK_HOP` and `TERMAG_ASK_PARENT_{BOX,PROJECT,WORKSTREAM,SESSION}`, which become `termag.ask.thread`, `termag.ask.hop`, `termag.ask.parent.box`, `termag.ask.parent.project`, `termag.ask.parent.workstream` and `termag.ask.parent.session`, with kind `ask`. The parent's project and workstream are only the ones `askParent` checked (`AgentThread.parentProjectId`, named as the project's current name); its session is the CLI's `CLAUDE_CODE_SESSION_ID` (`sender.claudeSession`, kept unchecked as `AgentThread.parentClaudeSession`, since it only places spend under the asker's own session). A person's turn in the thread's chat carries the same parent and no hop, since it is the same Claude session. Each bad value drops only itself (the parent's project and workstream as a pair); a box whose script predates them still sets kind `ask`, which any script takes, and ignores the rest; an older agent sends `chat` and nothing else. The headless ask run (a box without ask-chat-v1) carries none of this. A spend view can roll a thread's spend up under `termag.ask.parent.session`; nothing filters on kind `chat`, so the new kind only adds a row to the by-kind breakdowns. **The kind is in the session's environment too**: every launch that sets `termag.session.kind` also puts `TERMAG_SESSION_KIND=<kind>` in the agent process's own environment, for the tools it runs. `telemetry-launch` reads that same variable, so every launch names its kind explicitly (a pane's `interactive` too, on its `termag-credentials` call: `PANE_KIND_ENV`) and an inherited value never decides a resource; one only reaches `telemetry-launch` when a launch inside a session names none, which then takes the session's kind. **The settings' own kind is `external`** (`termag-credentials apply telemetry` rewrites the delivered `interactive`): it is what a Claude Code session termag did not launch exports with, so every termag launch must name its kind, and `launchCommandFor` sends every Claude command a pane types through `telemetry-launch`, resumes and briefs included. A new launch path that types `claude` without it is counted as `external`. The same launches add the session's work (`termag.repo`, `termag.git.branch`, `termag.git.commit`, `termag.spawn.*`), read from the directory the session starts in: a launch from somewhere other than its checkout names the wrong repository or none, which is why the chat runner passes `TERMAG_WORK_DIR` (`-` for none) rather than leave the runner's own directory to be read.

<a id="o11y-server-tracing"></a>
## Server tracing loads second in `index.ts`, and work outside a request starts its own trace with `rootSpan`

`services/tracing.ts` is imported second in `index.ts`, right after `dotenv/config`, because its instrumentations patch `express`, `pg`, `http`, undici and the AWS SDK as those load. Anything that loads one of them first is silently never traced. So `tracing.ts`, and everything it imports, must load none of them, nor `@slack/bolt` or discord.js (`tracing.test.ts` checks). Keep `services/tracing/` to `@opentelemetry/*` and its own modules. Work that isn't a request (a timer's tick, a Bolt or discord.js listener, a callback queue) runs in whatever context it was created in, which can be an old request's. Its spans would then join that request's trace, or, with no span active, not be recorded at all, since pg, undici and outbound http need a parent. Wrap a new loop's tick in `traceSweep('<name>', tick)` if it runs every 30 s or slower; faster loops stay untraced, because of the volume estimate. Wrap a listener in `rootSpan('termag.<area>.<what>', attrs, fn)` (`services/tracing/spans.ts`). A root named `termag.*` is an entry the trace buffer decides on its own, and any other span with no local parent is dropped as "no entry". Inside one, `withSpan` adds a child, and does nothing where no span is active. An error that the code catches and logs instead of throwing needs `failRoot(err)`, because `keepErrors` keeps an entry only for its own error. These spans' attributes are exported unchanged, so use ids and enums, never a message, a prompt or anything a person typed. What's traced, the two flags and how to find a trace: `docs/agents/observability.md`, "Server traces".

<a id="pane-alt-screen-no-history"></a>
## Agent panes run their TUI on tmux's alternate screen — capture has no history there

pi and Claude Code (and Cursor) draw on the alternate screen, so while the TUI runs, the pane's tmux history is **zero** (`tmux display-message -p '#{alternate_on} #{history_size}'` reads `1 0`): `capture-pane -S -N` returns only the visible pane, whatever `lines=` asked for. The phone's transcript depth on an agent tab is therefore the TUI's screen height, not the capture depth — raising `lines` changes nothing for a live TUI, and the desktop's deeper history is xterm.js accumulating the PTY stream client-side, which a reloading phone page cannot keep. The pane's past comes from `agent/pane-history.js` instead (`tmux pipe-pane` → `~/.cache/termag/pane-history/<session>.log`, served by `GET …/sessions/:role/history` for the phone's "Load earlier"), and for Claude and pi, phase 3's transcript JSONL is the quality fix — the pane stream is also full of repaint frames. A pane whose TUI has exited is back on the main screen, where history accumulates again.

<a id="preview-host-never-termag"></a>
## A preview host's request never reaches termag: its dispatch is the first middleware and never calls `next()`

Preview links serve someone's dev server at `<name>.<PREVIEW_LINKS_DOMAIN>` through this same backend. `previewHost.dispatch` (`backend/src/services/previewHost.ts`) is the first `app.use` in `index.ts`, and the upgrade handler's first statement is `previewHost.dispatchUpgrade`: nginx's preview server block sets `X-Termag-Preview-Host` (and `termag-proxy.conf` clears it on every other upstream), and a request carrying it, or any `Host` in the preview domain, is answered there and never handed on, so a preview's `/termag/api/...` or `/termag/ws/terminal` is the app's path, never termag's (SR3). Mount nothing ahead of it: CORS would stamp termag's `Access-Control-Allow-Origin` on an app's answer, `express.json()` would eat a POST body before the relay pipes it, and the session, the surface and the ALB bridge have no business on a host Okta doesn't front (#167 hit both, #314). `backend/src/indexPreviewDispatch.test.ts` pins the order and `previewHost.test.ts` mounts a sentinel after the dispatch that no preview-host request may reach. A new upgrade path goes after that check too. Identity on a preview host is the `__Host-termag-preview` session alone: nothing there reads `x-amzn-oidc-*` (SR17).

<a id="project-initial-commit"></a>
## New projects get a repo and an initial commit automatically, and the helper that does it lives in two files

a freshly `git init`-ed project has an unborn HEAD, and `git worktree add ... HEAD` refuses to resolve one ("invalid reference: HEAD"), so branching off a new project used to require the user to commit by hand first; a project created with no agent workflow never even reached the `tmux-create` that ran `git init`, so its first branch-off failed with "not a git repository" instead. `ensureProjectRepo` (git init when needed, then the initial commit) runs where the wiki files are seeded — agent `init-wiki` (unless the message says `initRepo: false`, which MetaTerm does), backend `ensureProjectDir` only with `initialCommit: true` — and again as a backstop before `worktree add` when the backend sends `initRepo: true`, so projects created before this get fixed the first time they branch off. **Not in `tmux-create`, and never ahead of a repo clone**: the pane checkout (`buildCloneCommand`) fetches into the init-ed dir and runs `checkout --track origin/<default>`, which fails if a local first commit already owns that branch name. The setup gate (`services/sessionGate.ts`) does NOT cover this: a pane checkout moves `setupStatus` to `none` as soon as it is typed, so workstream create is allowed while the fetch runs. The decision is the backend's, from `repoUrl`: `createWorkstreamFor` sends `initRepo: !project.repoUrl` (and answers 409 `CHECKOUT_NOT_LANDED` instead of git's unborn-HEAD error), and `init-wiki` is only ever sent for a project with no `repoUrl` (Start empty and un-archive clear it). The helper itself has no remote check, on purpose: git state can't tell an in-flight clone from an abandoned one (Start empty after a failed checkout leaves `origin` and no commits), and a remote check left the abandoned one unable to branch off. An older backend sends no `initRepo` to `git-worktree-add`, so the agent skips the backstop. It only commits into a repo whose top level *is* the project dir, so a project dir nested inside an unrelated repo is left alone, and it falls back to a `termag` author identity only when the host has none. The logic is duplicated in `backend/src/services/gitRepo.ts` and `agent/git-repo.js` — same reason as the provider registry: the agent ships standalone with no build step, so keep the two in sync by hand.

<a id="project-list-order"></a>
## Project-list ordering is `pinned DESC, lastActiveAt DESC`

`lastActiveAt` is bumped on status writes, not on every API touch, so a project you opened in the UI but haven't run the agent in won't float up. If recent-activity sort "isn't working," check that status events are actually arriving (Claude hooks installed, agent up) before suspecting the sort.

<a id="project-multi-repo-not-git"></a>
## A multi-repo project's directory is not a git repository

With `Project.layout = 'workspace'` (behind `multi-repo-projects-enabled`) the project directory, and each `.worktrees/<ws>/` under it, is a plain folder holding one checkout or worktree per `ProjectRepo`, and `repoUrl` is null. Code that runs git at `projectDirFor(project)` (a branch-state read, a worktree add, a PR checkout) gets "not a git repository" there, so branch on `isWorkspace(project)` (`services/projectRepos.ts`) first: workstream create and remove do, the PR lanes, the Review pane, a spawn's retire check and a share preview's checkout lookup read each repository's worktree under the root instead (one PR per repository), a PR checkout puts the PR in its repository's worktree at `.worktrees/<ws>/<repo>` (git-worktree-add-pr with `worktreePath`, agent capability `worktree-pr-path-v1`), the chat runner's own-tree check reads the repositories under a root that is no checkout, so a chat there runs read-only while one of them is a PR's or a fork's (`memberRefusal`, `agent/chat-runner.js`), asks run in the one repository the target names (`box/project:repo`, a bare one refused with 409), project and workstream rename move the folder and then `git worktree repair` in each repository's checkout against its worktrees, never at the root (behind the agent's `workspace-rename-v1`), and Start empty refuses with 409. The single-repository setup machine (`services/projectClone.ts` `applyNow`) ignores a workspace row: with `repoUrl` null it would read as an empty project and launch sessions before the marker exists. `tmux-create` skips its `git init` for such a folder because of the `.termag-workspace` marker (`agent/workspace.js`); without it the first session would turn the folder into a repository. A repository added to a ready project has its `ProjectRepo` row while it is still cloning, and the project stays `ready`, so code that reads a workspace's repositories on the box filters to `setupStatus: 'ready'` (the PR lanes, Review, asks and spawn retire do).

<a id="project-sharing-owner-agent"></a>
## Project sharing routes terminal access through the *owner's* per-user agent

a collaborator's browser hits the backend, but the PTY lives in the owner's tmux. If a shared project's terminal won't connect, the owner's `termag-agent` is the thing to check, not the collaborator's.

<a id="provider-registry-two-files"></a>
## Provider registry lives in two files and must stay in sync

`backend/src/providers/registry.ts` and `frontend/src/providers/registry.ts`. Adding a provider on one side only produces a project that the backend will accept but the UI can't render (or vice versa). There's no shared package; the symmetry is by hand. Each entry also carries `selectable`: only `true` entries (claude, cursor, devin, pi) appear in the create-project and default-agent pickers and pass the backend's new-choice validation (`SELECTABLE_PROVIDER_IDS`, `GET /api/providers`); `false` entries (codex, gemini, augment, deepseek, mistral, and the frontend-only `human`) are **hidden, never deleted**, because existing projects and historical worktime/token rows still render through them. Entries with `chatRunner: true` (`claude-chat`, `pi-chat`) are the headless chat-runner twins of a user-facing provider: unselectable, status source `chat-runner`, and each names its `chatEngine` (`claude` or `pi`); a user-facing entry's `automationChatProvider` is the twin its automations run as (`automationProviders()`). Test "is it a chat" with `isChatRunnerProvider` (both files), never `=== CHAT_PROVIDER_ID`, or a pi chat renders as a pane. `backend/src/providers/registry.test.ts` asserts the two files agree on ids, names, badges, colours (`color` for dark and `lightColor` for light, both copied by hand), `selectable`, `chatRunner`, `chatEngine` and `automationChatProvider`.

<a id="provider-string-not-enum"></a>
## `agentProvider` is a string, not an enum

Prisma will happily persist arbitrary garbage. The registry is the validation boundary; route handlers should reject providers not in the registry before writing.

<a id="push-endpoint-url"></a>
## A push subscription's endpoint is a URL the server POSTs to

`isAllowedPushEndpoint` (`services/webPush.ts`) is an SSRF guard: https only, no userinfo, port 443 only, no IP literals, known push hosts only. The WHATWG parser and the legacy `url.parse` must also agree, because web-push sends with the latter. Don't loosen it to "any https"; stored rows are re-checked before every send.

<a id="push-vapid-subject"></a>
## `VAPID_SUBJECT` must be a public contact, or Apple refuses every push

Apple's push service answers 403 `BadJwtToken` for a subject like `mailto:e2e@termag.local`, and FCM accepts it, so only iPhone and Mac users lose push. `vapidSubjectProblem` (`services/webPush.ts`) turns push off for a private-use domain at config time, with one `[PUSH]` error line. Use `mailto:` on a real domain or an `https:` URL.

<a id="simple-ui-launchpad-controls"></a>
## New simple-UI controls are LaunchPad's, and monospace is for code

New UI in the simple UI uses LaunchPad (`@launchpad-ui/components`, which is built on React Aria). Its controls then behave and read alike, and they bring the keyboard, focus and screen-reader handling termag would otherwise rebuild by hand. Hand-roll a control only when LaunchPad has none, and say why in a comment. Three things make a component work here.

- **Its CSS is cut down at build time.** LaunchPad ships one stylesheet that starts with a page base: rules on `html`, `body`, `*`, `:root`, `[data-theme]` and headings, which would restyle all of termag. `frontend/vite.config.ts` therefore serves that import through `launchpadComponentsCss` (`src/launchpad/launchpadCss.ts`). It keeps every rule whose selectors all name a component's hashed class (`.DpiyKW_slider`, or `._1iK3oq_popover` for a hash that would start with a digit) and drops everything else. Any component is styled with nothing to register; the whole set is about 80 KB, 9 KB gzipped. A release that changes the class scheme fails the build (`launchpadCss.test.ts` reads the installed stylesheet).
- **Its colours are termag's.** Never import `@launchpad-ui/tokens/themes.css`: a person's termag theme must still apply. Map the `--lp-color-*` tokens the component reads to termag's variables (`--bg-*`, `--text-*`, `--accent`). For new UI, put the `lp-theme` class (`LP_THEME`, `src/launchpad/theme.ts`) on its container and on each of its overlays; `launchpad/theme.css` is the one shared map, of colours and of the type tokens' font family, and `theme.test.ts` holds it to the installed packages. Older controls map their own few tokens, as `.chat-effort` does for the Slider in `pages/chat/chat.css`. `@launchpad-ui/tokens/index.css` (sizes, spacing, type) and `fonts.css` (Inter's `@font-face`) are safe to import. The chrome refresh's LaunchPad palette is termag's variables set to LaunchPad's values inside its scope (`pages/chat/chrome.css`), not `themes.css`.
- **Its icons need the sprite.** `Icon` from `@launchpad-ui/icons` draws `<use href="#lp-icon-…">`, so the package's `sprite.svg` has to be in the document once: call `ensureLaunchPadSprite()` (`src/launchpad/sprite.ts`) where the icons are first needed. Render them at 20 px (`size="medium"`); they are drawn on a 20 px grid and blur when scaled down.

Type: text is in `var(--font-ui)` (`App.css`), and `var(--font-mono)` is only for code, paths, commands, keys and terminal output. The full UI's body is still monospace. A page that moves to the UI font keeps mono for its inline code, as Settings does (`.settings-page` in `App.css`).

<a id="simple-ui-side-panel-ctrl-shell"></a>
## The simple UI's side panel attaches the ctrl shell, never the agent pane, and shares its tmux window

the side panel (`pages/chat/SidePanel.tsx`, `chat/sidePanel.ts`) mounts the workspace's own `Terminal` on the workstream's `-ctrl` session (`utils/sessionName.ts`, owner's unix user for a shared project) and the workspace's `BrowserPane`. Do not point it at `-agent`: the pane chat (`ChatView`) reads that pane's text as the conversation and types into it, and for an SDK chat the agent is the chat runner's, with the pane held only while the user has opened it in the terminal (`chat/terminalHold.ts`); a second writer in either breaks the chat. Neither tab mounts while the session is set up or has no agent workflow, the same `hasAgent && !cloneHeld` branch the workspace's ctrl column (terminal and browser dock) sits in (`sidePanelBody`). Only the shown tab is mounted, so the terminal socket exists only while the Terminal tab is visible and the browser parks on the box (60 s) when the panel shuts or switches tab, exactly as when the workspace dock collapses. The ctrl window is set to `window-size latest` (older sessions: `largest`), so with the same session also open in the workspace the surface not used last shows the other's window clipped or padded; that is tmux, not a fit bug. The panel's remembered browser URL is the dock's (`useRememberedBrowserUrl`, keyed per project and workstream), so either surface reopens on the other's page. Its shortcut is Ctrl+Alt+B (⌘⌥B), caught in the capture phase so it works inside xterm; plain Ctrl+B is tmux's prefix and must never be bound here. As a phone's overlay its Terminal has a key bar (`pages/chat/TerminalKeyBar.tsx`) whose keys are raw bytes down the same terminal WebSocket as typing, through the Terminal's `onReady` handle; never route them through send-keys, which the phone client's key bar uses for tmux key names.

<a id="slack-scopes"></a>
## Slack scopes are large

the bot needs `app_mentions:read`, `assistant:write`, `chat:write`, `chat:write.public`, `channels:manage`, `channels:read`, `channels:history`, `channels:join`, `commands`, `files:read`, `files:write`, `groups:history`, `groups:read`, `groups:write`, `im:history`, `im:read`, `im:write`, `reactions:read`, `reactions:write`, `users:read`, `users:read.email`, and the `message.channels`, `message.groups` and `message.im` events, plus the channel events space links depend on (`member_joined_channel`, `member_left_channel`, `channel_left`, `group_left`, `channel_archive`, `group_archive`, `channel_unarchive`, `group_unarchive`, `channel_rename`, `group_rename`, `channel_shared`; `deploy/slack-app-manifest.yaml` is the list). Without the `groups:*` scopes a private channel can't be linked to a space or created as one, and without the channel events a link outlives its archive or rename until the daily reconcile (§4.7). Re-add any you remove and reinstall the app or `/t create` will silently fail to create channels. Without `channels:history` + `message.channels`, thread replies under Slack collaboration cards in channels never arrive (the card's Reply button still works); every DM to the bot goes to the Claude executor unless `handleCollabThreadMessage` claims it first.

<a id="slack-t-strips-api-key"></a>
## Slack `/t` executor strips `ANTHROPIC_API_KEY` from the spawned env

`backend/src/slack/executor.ts` deliberately removes any inherited `ANTHROPIC_API_KEY` before spawning `claude`, so the subprocess uses the user's own auth (Claude Code login / subscription) instead of a stale workspace key. Don't "helpfully" add it back; doing so silently routes Slack-driven sessions onto the wrong account and burns the wrong quota.

<a id="space-memory-frozen-prompt"></a>
## A chat session's space memory is frozen into its system prompt at the session's first turn; changes come as a notice in the message

`agent/space-memory.js` appends a space's `.termag/` index to a chat-runner session's system prompt (`--append-system-prompt`), copied into `~/.termag/chats/<chat>.space-memory/` at the session's first turn. A space's skills are never loaded (no `--plugin-dir`; skills live in the repo's `.claude/skills/`). Every later `claude -p … --resume` turn of that session passes exactly those bytes, whatever the space now holds. A memory change arrives as a one-line `<space-memory-notice>` at the start of the turn's own message, once per change. Never "refresh" the appended prompt mid-session: anything ahead of the conversation that changes makes the whole context miss the prompt cache, on every turn after. The notice is stripped from history, live events and the running turn's replay (`outboundEvent`), the turn cut, titles and the orchestrator's stored view (`stripNotice`, `withoutSpaceMemoryNotice`); a new code path that reads a user message from the transcript or the event stream must strip it too, or the person sees it as their own words. `owner.json` ties the frozen copy to a Claude session id: a turn with no session id (a first turn, Clear) starts over, and a session that began without memory never gains a system prompt, only a notice. Chat turns carry `TERMAG_SPACE_MEMORY_MANAGED=1`, so the box's Claude Code hooks (`termag space memory context --hook`, which serve interactive panes) stay quiet in them. Details: `docs/space-memory.md`.

<a id="spawn-brief-claim"></a>
## An agent spawn's brief is claimed by the first launch, by spawn id or child project id, never by name

`POST /api/spawns` writes the `agent_spawns` row and the prompt file (`~/.termag/spawn-prompts/<id>.md`, `write-file`) *before* it creates the workstream or project. `ensureAgentSessionsAndLaunch` then asks `claimSpawnLaunch` (`services/agentSpawnStore.ts`) right before typing. The spawn route's own create passes `spawnId` through `createWorkstreamFor` / `createProjectFor`. Every later launch claims an unclaimed `starting` row by the child's project id and workstream: the deferred launch after a box's hello or a clone, and reconnect reconstruction, which claims too, so a first launch that was skipped (pane busy, probe failed) still starts on its brief instead of `resumeCommand`. A failed send hands the claim back (`releaseSpawnLaunch`). The prompted line still goes through `launchCommandFor`, so the `termag-agent-otel` wrapper applies. A claim by id must also match the child project, and the cookie `POST /api/projects` drops a body's `spawnId`, so a stray id can never land a brief in another project. An agent token must name its own `agent` pane (`from.session`), or the depth and per-parent limits have nothing to count. Workstream create is `createWorkstreamFor` in `routes/workstreams.ts` (shared by the cookie route and spawns; it repeats the parked/unready checks for callers without the middleware) and takes a `provider` that replaces main's on the new agent workflow. The parent nudge (`services/agentSpawnSweep.ts`, leader work; a report clears `nudgedAt` and the sweep reads only rows where it is null) types a FIXED line, only into an `idle` parent pane (never `waiting`: that is an approval prompt the line would answer), never while the owner typed in that project in the last two minutes, and never the child's report text. `list_spawns` and `report_back` are pre-approved by `termag-reconcile`; `spawn_agent` never is, and pi's registration switches it off (`METATERM_SPAWN_DEFAULT=off`). Spawn limits are tuning parameters: the `agent-spawn-limits` JSON flag (user + target box; malformed keys fall back one by one to `DEFAULT_SPAWN_LIMITS` in `services/spawnLimits.ts`), checked by `admit` in `routes/spawns.ts` after the target box is known. A box over its hot thresholds, judged from its latest host sample (a sample older than 15 min refuses nothing), or at `boxCapacity` (null = no cap, the default), gets 409 `box_busy` / `box_capacity`. Every request and refusal is logged in `spawn_events` with a one-word reason (90-day retention). `host_samples` keeps the 5-minute box history (30 days) with `liveAgents` from `tmux-list`, and cores and memory from `agent/host-sample.js`, so a box's load-per-core check starts only after its agent restarts. A spawn's `endedAt` (the minute sweep) is what "running" counts; an offline or parked box never ends its spawns. Finished spawns are parked and retired: the lifecycle sweep (`services/spawnLifecycleSweep.ts`, behind `spawn-lifecycle-enabled`) parks a `done` child idle past `agent-spawn-limits.parkIdleMinutes` (`stopAgentPane`; `parkedAt`). A parked spawn is not running: it is out of the running, gauge and host-sample counts, the end sweep leaves it, and reconnect reconstruction does not relaunch its pane. The sweep retires a parked *delegate* through `removeWorkstreamFor` (never `force`, so git's own refusals stand) only when `retireCheck` on its `git-branch-state` says nothing would be lost: clean, and nothing beyond base or pushed with no unpushed commits. A local-only project (no `origin`) has no origin base: the RPC then counts against `agent_spawns.baseSha` (the commit the child was spawned from, passed as `base`) and nothing else, never a local branch, and only an empty checkout counted that way (`baseLocal: 'spawn-base'`) retires. Otherwise `keptReason` holds why. `dismiss_spawn` (parent only, MetaTerm) and the dashboard's Park / Retire / Resume act at once with the same check. A spawn whose parent went away is adopted by the orphan sweep (`services/spawnOrphanSweep.ts`, same flag): the nearest living ancestor, else `users.spawnOrphanHome`, else `orphanedAt`. The *effective* parent is `foster*` when set, else `parent*`: the nudge, `dismiss_spawn`'s parent check, `list_spawns` and the report note all use it, and a new reader of parent fields must too. Orphans nobody adopted are never nudged. The network view (`/spawns/:rootId`, `GET /api/spawns/trees/:rootId`) replays from `spawn_events` of kind `status`: `setStatus` and the auto-idle timer call a transition callback (`setStatusTransitionCallback` in `services/status.ts`) that only the spawn sweep's process registers, and `services/spawnStatusLog.ts` logs only sessions in its watched set. The spawn route adds a child when its row is written (`watchSpawnedSession`), and the sweep rebuilds the set each pass as a backstop; never rely on that refresh to start a child's history, since one pass of the sweep can take minutes on a large fleet. Status events are not OTel signals.

<a id="spawn-handoff-fixed-lines"></a>
## A handoff types only fixed lines, and a restart's relaunch is claimed like a spawn's brief

the route writes an `agent_handoffs` row; `services/agentHandoffSweep.ts` (leader work, 5 s; rules in `handoffStep`, `services/agentHandoff.ts`) moves it `requested → writing → written → resetting → done`, claiming each step with `updateMany` on the state. It types into the agent pane only when it is `idle` (never `waiting`), and an agent-started handoff also waits out the owner's two-minute typing quiet. What it types is fixed text plus the handoff id: the "write a handoff" request, `/clear` or `/compact <focus>`, and the read-in line naming `~/.termag/handoffs/<id>.md`; the handoff text itself only reaches the next agent through that file (`write-file`, 0600, after `findSecretsInText` and a 32 KB cap). Only an agent the metaterm tools reach can be handed off from (registry `handoffWriter`: Claude and pi), since it must write its handoff; Cursor and Devin can only be restarted into. `clear`/`compact` need the provider's `clearCommand`/`compactCommand` (Claude only today); anything else, or a switch of provider, falls back to `restart`, which is Switch agent's sequence (row, `stopAgentPane`, `markAgentPaneStopped`, `ensureAgentSessionsAndLaunch`). The prompted line comes from the registry's `promptLaunch`, which spawns use too. `ensureAgentSessionsAndLaunch` and reconnect reconstruction call `claimHandoffLaunch` (`services/agentHandoffStore.ts`) after the spawn claim, so a box that drops between the kill and the launch still starts on the handoff instead of `resumeCommand`. Both launch paths take a per-pane lock (`withPaneLock`, held 1 s past a launch that typed), so two launchers reaching one pane at once type once; tests that launch into one pane repeatedly call `setPaneLaunchSettleForTests(0)`. `handoff_written` is always listed but never pre-approved; `handoff` is never pre-approved, and pi's registration switches it off (`METATERM_HANDOFF_DEFAULT=off`).

<a id="status-claude-hooks-background"></a>
## Claude Code hooks fire `curl ... &` (background)

the `&` is load-bearing. Without it, every tool use blocks on the localhost POST and feels visibly slower. Don't "clean up" the trailing `&` from `deploy/claude-hooks.md`.

<a id="status-cloud-session-key"></a>
## A cloud session's live status is keyed by the runner's tmux session name, not a project

the session's Claude Code runs termag's status hooks, and the posts carry `<boxUser>-claude-runner-s<slot>-<order>-r`. `services/claudeSessions.ts` hands the frontend that name per run (`current.sessionName`) so it can read the same status map as a project pane. The ownership check in `routes/status.ts` admits those names for an instance-bound token only when they parse as runner sessions of that token's box (`isRunnerSessionOf`); a project pane under the box user's prefix is still refused.

<a id="status-codex-bridge"></a>
## Codex bridge subprocess is owned by the per-user agent

termag's main server doesn't manage it. If a Codex session looks dead, check the agent's logs (`journalctl --user -u termag-agent`), not the main server's.

<a id="status-context-warnings-pane-text"></a>
## Context-token warnings are parsed from agent pane text, not a structured signal

the per-user agent scans tmux pane content for provider-specific "context left" / token-budget strings and surfaces them via the status pipeline so the UI can flash a warning on the project tile. If a provider changes its wording, the warning silently stops appearing; the parsing lives in `agent/agent.js` and is the place to update.

<a id="status-desktop-thread-checkout"></a>
## A desktop thread's status is filed by its checkout, not its tmux pane

t3's Claude on a box runs the box user's hooks inside the t3 server's tmux session `termag-t3`, which no project owns. `deploy/termag-status` sees `TERMAG_T3` (set by `agent/t3-bridge.js`) or that pane and posts under the `-agent` session whose start directory holds `CLAUDE_PROJECT_DIR` (a `.worktrees/<name>` path only under that workstream's session), else under `termag-t3` (box activity only; a box token may write it), with `source: t3:claude` (booked as Claude; the frontend's `runningProviderForSource` ignores it, as it runs beside the pane) and the hook's `session_id` as `threadId`; outside tmux it posts nothing. Threads and the pane sharing a session settle in `services/sessionTurns.ts`: working while any works, else waiting while any waits; pushes follow the post.

<a id="status-provider-posts-own"></a>
## A provider that runs on boxes must post its own status, with a registered `source` — the tmux poller only sees the orchestrator's tmux

`services/tmuxPoller.ts` reads local `capturePaneText`/`isAgentRunning` and never the agent RPCs, so poller providers (cursor) have no live status on a box (Devin now posts its own: `deploy/devin-hooks.json`, merged by termag-reconcile into the `hooks` key of `~/.config/devin/config.json`, sends `--source devin-hooks`, and `termag-status` drops source-less posts when `DEVIN_PROJECT_DIR` is set, because Devin also imports the Claude hooks); and `services/status.ts` books a status whose `source` is unknown as Claude, so a hooks-style provider needs an entry in `statusSources` and must send it. pi is the worked example: its `launchCommand` runs `pi -e` with `deploy/pi-ext/termag-status.ts` (installed by termag-reconcile), a pi extension whose pure reducer (`termag-status-core.ts`, tested from `backend/src/providers/piStatusExtension.test.ts`) turns pi's lifecycle events into `termag-status … --source pi-ext:pi` calls; `termag-status` grew `--source/--reason/--message/--notify`, a `meta` mode and `--print-payload` for exactly this, while a plain `termag-status working` still sends the source-less payload the Claude hooks rely on. Three things that are deliberate: the registry's new `resumeCommand` (`claude --continue`, `pi --continue`) replaced the Claude-only relaunch special case in `agentRuntime.reconstructAgentSessions`; and a failed model request shows up as a `waiting` status with a `rateLimited` badge and a remedy naming the HTTP status. pi runs tools without approval prompts.

<a id="status-rate-limit-pane-text"></a>
## Rate-limit detection is also pane-text parsing

same caveat as context warnings. The `rateLimited` flag is inferred from provider-specific quota/rate-limit phrases in the agent pane. If a provider rewords its rate-limit message, the project tile silently stops showing the rate-limit state; update the patterns in `agent/agent.js`.

<a id="status-stale-waiting"></a>
## Stale `waiting` status is auto-cleared by the per-user agent

`agent/agent.js` watches for sessions stuck in `waiting` whose pane no longer shows a prompt and demotes them back to `idle`/`working` to match reality. Hooks and bridges aren't perfectly reliable about firing the closing event (notably Claude `Notification` → no follow-up `UserPromptSubmit` if the user dismisses outside the TUI), so the agent is the safety net. If you see a project tile flicker out of `waiting` without an obvious trigger, that's this — don't chase it as a hook bug first.

<a id="status-tmux-poller-patterns"></a>
## tmux poller patterns are provider-specific

TUIs with a persistent input box (vibe/Mistral) look "working" to a naive idle/working detector forever. The registry's poller config has to match the actual TUI's render; if a new provider's working-time looks pinned at 100% or 0%, the regex in its registry entry is wrong before anything else.

<a id="status-working-time-source"></a>
## Working-time attribution is per-provider source

Codex pulls from JSONL session files, Claude from hook events, vibe from `~/.vibe/logs/session/meta.json`. Mixing sources (e.g. counting a Claude project's hook events as if they were poller-derived) double-counts; each provider entry declares its single source of truth.

<a id="test-fake-timers-fake-intl"></a>
## `vi.useFakeTimers()` fakes `Intl` too, so a timezone spy does nothing under it

Vitest 4's fake timers (@sinonjs/fake-timers) replace `Intl` along with `Date` and the timers. With them installed, `vi.spyOn(Intl.DateTimeFormat.prototype, 'resolvedOptions').mockReturnValue({ timeZone: 'America/Los_Angeles' })` has no effect and the code under test sees the machine's zone (UTC on boxes and in CI), while the same spy works in a test with no fake timers. When a test needs a fake clock and a chosen zone, fake only what it needs, `vi.useFakeTimers({ toFake: ['setTimeout', 'clearTimeout', 'setInterval', 'clearInterval', 'Date'] })`, then spy. Better, give a formatter a `timeZone` argument and test it without mocks.

<a id="test-root-only-cases"></a>
## A test case that needs a file you don't own runs only as root

A check such as `[ -O f ]` needs a file owned by someone else, and a test can't make one without root. On the boxes `unshare -rm` fails (`write failed /proc/self/uid_map`), `fs.protected_hardlinks` blocks a hard link to a root-owned file, and a symlink is not the same case because `-O` follows it; `sudo -n` works. Guard the case with `[ "$(id -u)" = 0 ]` and print a `skip:` line otherwise, rather than adding a test-only environment variable to the production script. Then run the whole test once as `sudo -n env -i PATH=/usr/bin:/bin HOME=<scratch> sh <test>`, with the fix and with it removed, so you have seen the case pass and fail (`deploy/termag-status.test.sh`'s `.termag-e2e` owner check is the example).

<a id="tmux-argv-not-shell-string"></a>
## Never build a shell string to type text into tmux — spawn `tmux` with an argv array

(`execFile('tmux', sendKeysArgv(...))`, builders in `agent/tmux-args.js` and `backend/src/services/tmux.ts`). The shell-string version single-quote-escaped the text *and* then ran it through `shellEscape`, so every `'` was typed as the four characters `'\''`: MetaTerm `send_keys`, Slack/Discord `/t` and the agent launch commands all went through it. Two tmux details that the builders encode: `--` must precede the text so a payload starting with `-` isn't parsed as a flag, and `-l` applies to every argument of one invocation, so in literal mode Enter is a separate `send-keys`. `tmux-capture` takes an opt-in `styled` flag (`capture-pane -e`) for callers that need to tell dimmed ghost-text from typed input; the default stays plain because the Slack/Discord formatters expect unstyled text.

<a id="ui-daily-theme-days"></a>
## A day's theme is CSS and code from an agent: its sprite runs only in the sandboxed frame, and a person reviews each day

Each directory under `frontend/src/theme/daily/` is one day, written by the theme-of-the-day skill from research on the web, and its `sprite.js` is code. It runs only in the frame `DailyDecor.tsx` makes from `spriteFrame.ts`: `sandbox="allow-scripts"` alone (an opaque origin) and a CSP of `default-src 'none'` plus its nonce, so it can't reach termag's DOM, cookies, storage or API, the network, or `eval`. A denylist can't do that job (`'con' + 'structor'` passes any), so `lint.ts` (run over every day by `lint.test.ts`) is a tripwire on top: it keeps a day's CSS under its own `html[data-daily-theme="<date>"]` scope, off the engine's frame and away from fetches, fonts and `!important`, and a sprite plain JavaScript with one `export default` and no imports. Never add `allow-same-origin` to the frame, a `connect-src` or `'unsafe-eval'` to its CSP, or import any day file as a module: the registry reads `meta.json` (parsed and checked by `meta.ts` before use), `theme.css` and `sprite.js` as text, and `lint.test.ts` holds it to that, because a day's module would run as termag. The CSS is not sandboxed, so each day's PR is reviewed by a person with its screenshots and never auto-merged. Keep the engine's guarantees in the engine: the frame's `pointer-events: none` and opacity cap are inline in `DailyDecor.tsx`, which a day's CSS can't override without `!important`, so never let `lint.ts` allow `!important` or a selector on `.daily-theme-decor`. The flag gates `?dailyTheme=` previews too, so it stays the kill switch. A day is Pacific (`date.ts`), and reaches people only once merged and deployed. Add a day's file kind or a sprite capability in `lint.ts`, `types.ts`, the skill and `docs/daily-theme.md` together.

<a id="ui-theme-settings-two-modules"></a>
## Theme settings are a JSON column validated by a module that exists twice

`User.theme` is `jsonb` (`{}` = all defaults). `backend/src/theme/schema.ts` and `frontend/src/theme/schema.ts` are the same file kept in sync by hand, like the provider registry: the backend validates writes strictly (`validateTheme`, unknown keys rejected) and normalizes reads (`normalizeTheme`); the frontend normalizes again as a safety net. The client sends the whole object, but `PUT /auth/me/preferences` fills each absent optional key (`OPTIONAL_THEME_KEYS`) from the stored theme (`mergeStoredThemeKeys`) so a tab loaded before a key existed cannot reset it; the flip side is that the client must send a key explicitly to set it back to its default (Settings' Reset sends `palette: 'dark'`). Never bump `THEME_VERSION` for a new axis: the validator rejects any other version, so every stale tab could no longer save; add an optional key instead. Adding a theme axis is an optional key, a default and a validator case in both copies, a CSS-variable mapping in `frontend/src/theme/apply.ts` and a group in `pages/settings/AppearanceSection.tsx` — no migration. The palette is `html[data-palette="light"]` (absent = dark), set by `apply.ts` with `color-scheme` and the `theme-color` meta; never `data-theme`, which LaunchPad's page-base CSS targets. Its light values are one `html[data-palette="light"]` block in `App.css` that sets every colour `:root` sets to a literal; a translucent tint is `rgba(var(--x-rgb), a)`, a shadow `rgba(var(--shadow-rgb), calc(a * var(--shadow-strength)))`, and a colour with no palette token gets a named token in both blocks. `theme/paletteCss.test.ts` fails on a token left dark, a triplet that drifts from its hex, an AA pair that fails in either palette, or a new literal colour in `App.css`. Charts follow the palette two ways: a fixed series hue is an App.css token (`--series-*`, `HUE` in `pages/dashboard/chartPalette.ts`, the tooltip band `CURSOR`), which flips with no re-render; a provider's colour is JS, so read it with `providerColor(p, usePalette())` (`theme/usePalette.ts` observes `data-palette`), never `p.color` directly, which is the dark pair. `wash()` is a `color-mix`, so it takes a `var()`; `opaque()` only strips a registry `rgba`. The same test pins every series token, provider pair and the series `PALETTE` (`theme/seriesPalette.ts`) at 3:1 on the chart surfaces.Two palettes live outside that block: the chrome refresh sets its own LaunchPad greys inside `.chat-root[data-chrome='refresh']` and their light copies under `html[data-palette='light']` in `pages/chat/chrome.css` (`chromePaletteCss.test.ts` holds the pair), and a box colour (`utils/boxColor.ts`) is only a hue, drawn at `--box-saturation` / `--box-lightness`, so never return a full `hsl()` from JS again. `apply.ts` caches it in localStorage (`termag.palette`) and `frontend/index.html`'s inline script sets it before first paint, so the two must agree on the key; `ThemeProvider` applies nothing while `/auth/me` is loading, or the defaults would flash dark and overwrite the cache. The terminal is dark in both palettes: `components/terminalTheme.ts` reads its colours on the container, which carries `.terminal-island`, and App.css's dark `:root` rule also matches `html[data-palette="light"] .terminal-island`, so in light the terminal gets the whole dark set back (keep that selector list; `paletteCss.test.ts` holds it), opaque there and see-through only in dark; `--terminal-*` tokens have no light value. The starfield is dark-only (`apply.ts` `showStarfield`), and the backdrop behind the workspace is the palette's `BASE_BACKGROUND_COLORS` unless the user saved a solid colour, which applies as it is in either palette. The sidebar speed readout is no longer fed by the starfield's draw loop (`hooks/useEasedWarp.ts` steps it on a timer), so don't reintroduce an `onWarpChange` callback on `Hyperspace`: with a solid background or the kill-switch flag the canvas is unmounted, and under reduced motion it draws one frame, so the readout would stick.

<a id="ui-thermometer-scale"></a>
## Thermometers use an absolute 8h scale, not p50-relative

when reading the UI, a half-full tube means ~4 hours of work that day, not "average for this project". This was a deliberate switch; don't "fix" it back to relative without thinking about what the tube means at a glance.

<a id="ui-whats-new-entries"></a>
## A change people will notice adds or edits its What's new entry, in the PR that makes it live

What's new is kept current by the agents that ship changes: nothing sweeps the merged PRs for it afterwards. For each PR, ask whether someone using termag or lab will notice the change once this PR deploys. If so, add an entry in `frontend/src/whatsNew/entries/`, or edit the one that already covers the feature (an edit keeps its id, so it doesn't show as new again). If not, leave What's new alone; most PRs need nothing. Entries are bundled with the frontend and go live with the deploy that ships them, so an entry belongs in the PR that makes the change usable: not in a step of a stack, not in box-side work before boxes run it, and naming in `flag` every flag the change needs, even one that is on for everyone, until that flag is deleted from the code. Say what you did in a `What's new:` line in the PR description, next to `Flag:`. `frontend/src/whatsNew/whatsNew.test.ts` holds every entry to the format and the copy rules, and the doc's table says when to add, edit or leave one.

<a id="ui-zoom-lock"></a>
## The viewport zoom lock is the workspace's, not the phone's

`index.html` keeps `maximum-scale=1, user-scalable=no` for the terminals and chrome, which block touch zoom on purpose (`App.css`). `/m` lifts it while mounted (`useZoomableViewport` in `MobileApp.tsx`), and its inputs stay at 16 px so iOS does not zoom on focus.

<a id="workstream-main"></a>
## Every project has a `main` workstream by default

Tmux helpers and the agent runtime thread the workstream id through session naming, but legacy code paths that don't pass one will land on `main`. If you add a new code path that creates project artifacts (worktree, tmux session, status event), pass the workstream id explicitly rather than relying on the implicit `main`. Creating a non-`main` workstream auto-mirrors the project's main `Workflow` rows onto it and launches sessions; failures are returned as a non-fatal `sessionLaunchWarnings` array on the 201 response.

<a id="workstream-review-pane-role"></a>
## The Review pane is a fifth session role, and the role list lives in five places

`review` sits beside `agent`/`ctrl`/`data`/`data-ctrl` in `services/sessionAccess.ts` (`SESSION_ROLES`, which the terminal socket's `terminalSessionAccess` also reads), `services/sessionResolver.ts`, `services/tmux.ts` (`sessionName`), and the frontend `utils/sessionName.ts` + `services/api.ts`. Miss one and the pane either fails `assertSessionAccess` (400) or the browser's attach is refused as a session/project mismatch. A workstream has up to eight review panes: slot 1 is the role's own name, slots 2..8 are `<it>-<n>` (`tmux.reviewSessionName`/`reviewSessionNames`, mirrored in the frontend), and every list of legal names (`legalSessions`, `terminalSessionAccess`, the resolver, both renames, the session list, teardown) carries all eight. Every review RPC names its pane with the exact target `=<name>:` (`tmux.exactPaneTarget`): a bare `…-review` prefix-matches `…-review-2` once its own pane is gone, so a stop or teardown would kill the wrong one. The agent passes the string to `-t` as given, so this needs no agent change; send-keys and set-option refuse the bare `=<name>` form. The pane rides on the agent workflow: `agentRuntime.stopAgentSessions` kills it with the agent/ctrl pair (archive, workflow delete, workstream remove) and the rename route renames it, so a new teardown path that bypasses `stopAgentSessions` leaves Devin running unseen. Which PR a review pane is looking at is remembered only in backend memory (routes/review.ts and the review sweep); the tmux session is the durable thing, so after a backend restart the sweep's discovery reads the number back from the `@termag-review-pr` option or the launch echo, and a pane older than both ranges shows none. Starting a review uses only RPCs every deployed agent already has (`tmux-has-session/kill/create/send-keys`); the gh-based guess needs the newer `git-pr-info` RPC and falls back to the pane capture and milestone on an older agent — restart the per-user agent to get the branch-based guess. The review pane has no live status for any reviewer (Claude's hooks report on the agent session, not on `-review`), so its state is read off the pane's bottom chrome, per reviewer (`services/reviewers.ts` `classifyReviewerPane`: approval/trust/theme dialog → "needs an answer", spinner or `esc to interrupt` / `ctrl+c to stop` → "reviewing", bare prompt → "ready"); a CLI update that changes its chrome shows up as a wrong dock state. The reviewer rides in the `@termag-review-pr` option as `<pr> <url|-> <reviewer>` (older values decode as Devin) and in the sweep record; with neither, the probe reads it off the pane's foreground command. Claude reviews in `--permission-mode plan`, which refuses every write including `gh pr review`, so posting a Claude review means leaving plan mode in the pane; Cursor runs `--mode plan --auto-review` (plan alone stops on every `gh`). Since the review ring, that state is written ONLY by `services/reviewSweep.ts` (5 s sweep + tmux-list discovery) as `AgentStatus.reviews` (every pane) and `AgentStatus.review` (slot 1's) on the AGENT session's status and pushed over /ws/status like `milestone` — never poll GET /review for it; the browser posts `POST /review/seen` when the review terminal takes focus while done, which clears the sidebar's ring. Shared viewers get the review without its URL, same as the milestone. The prompt is written to `~/.termag/review-prompts/<session>.md` on the box (`write-file`, 0600) and handed to Devin with `--prompt-file`, never typed through shell quoting: the dialog's **Edit prompt** lets the user change the body under a fixed, non-editable first line naming the PR and its repository (`reviewPromptHeader`; the repository comes from the PR URL or the workstream's GitHub remote, `services/reviewRepo.ts`, and a bare number in a directory with no GitHub remote is refused, since the reviewer would guess among the box's clones), which is also what `prFromLaunchEcho` reads back from Devin's re-print of the prompt — change that line and PR recovery on older agents breaks — and above a fixed last line (`reviewPromptFooter`) telling the reviewer to end anything it posts to GitHub with "Reviewed by Devin", since it posts with the user's own gh login. The body's default is the first usable template of the repo's `.termag/review-prompt.md`, `~/.config/termag/review-prompt.md`, `~/.termag-review-prompt.md` (the top-level form is the one a script-less dotfiles repo can deliver: those are linked top-level only), else the built-in one. The launch line names the prompt file through `$HOME`, not the backend's absolute path, because `write-file` goes through the agent's `path_remap`. Devin runs in `--permission-mode smart` because its default `auto` stops on the first `gh pr view` for approval; smart auto-runs safe commands **and** workspace edits, so the review staying read-only rests on the prompt's instruction — there is no per-session deny rule in Devin, only `~/.config/devin/config.json` and `.devin/config*.json` in the repo, neither of which termag writes.

<a id="worktime-day-is-the-persons"></a>
## A working-time day is the person's own, in the zone their clients last sent

`work_time_entries.date` is the person's local day in `User.timeZone`, the zone termag's web UI and the desktop send as `tz` when they read working time (`services/userTimeZone.ts`); a span across their midnight is split between the two days (`services/worktimeDays.ts`). So read "today" as the day `/api/worktime` answers (`today`), not this machine's or UTC's: summing the local and UTC keys, as the thermometers once did, also counts the edge of the neighbouring day. Rows banked before a zone was recorded, and those of anyone no client has reported for, are the orchestrator's day. Banking runs synchronously on hook and heartbeat events, so it reads the zone from memory (`timeZoneFor`, loaded at start), never from the database.
