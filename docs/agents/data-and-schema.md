# Data and schema

Moved out of [AGENTS.md](../../AGENTS.md), which keeps a short index of it. Paths are from the repository root.

`backend/prisma/schema.prisma`. Key models (not exhaustive):

| Model | Purpose |
|-------|---------|
| `User` | Google identity + mapped unix user. Holds `defaultAgentProvider` (string), `theme` (JSON — background mode and colour, shape in `src/theme/schema.ts`, `{}` = defaults), agent token records, usage rollups, `role`/`adminSource` (admin authorization), `lastSeenAt` (bumped by the auth gates at most once per 5 min). |
| `Project` | Name, working dir, `agentProvider` (string keyed into the provider registry, no longer an enum), Slack channel id, archived flag, owner, `pinned` flag and `lastActiveAt` timestamp (drive project-list ordering: pinned first, then recent activity), and `instanceId` (which box hosts the project). |
| `Instance` | A termag-running host ("box"). Tracks provisioning state, AWS identifiers, and the owning unix user. The agent's host sample (`diskUsedPct`, `memUsedPct`, `load1`, `keptCheckouts`, `hostSampledAt`) from its hello and the `host-sample` RPC every five minutes (`services/hostSamples.ts`), shown on Fleet and behind the `box_pressure` signal. `readyAt` holds the first agent connect, so `readyAt - createdAt` is that box's cold-provisioning time. `downSince` is when the box went down: the power sweep's settle of a stop or hibernate stamps it while it is empty, and anything that leaves the box up for use clears it (the connect that brings it up, a stop or hibernate asked of a ready box, one that times out back to ready), except the 60-day refresh's connect and its re-hibernate of an untouched box (`sleepKeepsDownClock`); read by `box.resumed`'s `downMinutes`. `cleanedUpAt` is set only when a terminated ec2 box's AWS teardown fully finished; the provisioning sweep re-runs teardown for terminated rows without it (`docs/box-provisioning.md`). `parentInstanceId` is the box whose own credentials created this one through the CLI (null otherwise): that box may terminate it. Populated by `boxProvisioner` and the `/termag/api/instances` routes. |
| `Workstream` | A named line of work inside a project, backed by a git worktree. Every project has a `main` workstream auto-created on project creation; additional workstreams are managed through `backend/src/routes/workstreams.ts`. Non-main workstreams carry their own `slackChannelId` (`#proj-<user>-<project>-<workstream>`, auto-created and archived with the workstream); `main` uses `Project.slackChannelId`. Archiving a project deletes every workflow but keeps the workstream rows; un-archiving it on the same box gives each live workstream whose checkout still has a commit its agent back, resumed (`services/workstreamAgent.ts`), and a workstream left without one offers **Start agent…** (the switch-agent route). `sessionTitle` is Claude's own title for the workstream's chat session, written by the chat relay from a turn-end and led with in the simple UI's sidebar (`simple-ui-session-titles-enabled`). |
| `Automation` | One per project of kind `automation` (`projectId` unique): cron `schedule` + `timezone`, `prompt`, `tier` (`full`/`read`), `enabled`, `prOnChange`, `wakeBox`, `maxRunMinutes`, `keepRuns`, `spaceName` + `spaceFolder` (the space and its folder the automation lives in, stored once; `mirrorGrantBoxId` the box grant it added), `pausedReason` + `consecutiveFailures`, and the scheduler's cursors `nextRunAt` / `lastOccurrence`. |
| `AutomationRun` | One occurrence: `trigger` (`schedule`/`manual`), `scheduledFor` (the minute), `state` (`pending`/`running`/`done`/`blocked`/`needs_input`/`failed`/`skipped`) with a one-word `reason`, the run's `workstreamId` (half of its chat key; set null when the worktree goes, `retiredAt`), `chatSessionId`, `summary`, `branch`, `prUrl`, cost and tokens, and `spaceSyncError` (why the space step was skipped or failed). Unique on `(automationId, scheduledFor, trigger)` so two orchestrator processes start one run per occurrence. |
| `ProjectShare` | Collaborator grants on a project — `(projectId, userId)` with role. Backs the sharing routes; lets a non-owner reach the owner's tmux sessions through their own agent. |
| `ClaudeRunnerSession` | One row per **run** of a Claude Code cloud session on a box (one order each): owner, box, slot, `startedAt`, the end the box reports through `POST /api/claude-runner/event` (`endedAt`, `exitStatus`, `exitReason`), and since the Anthropic `sessionId` that groups runs into sessions, the `clientPlatform` from the box's `started` report, and the owner-only `title` (first prompt's first line, copied to a new run of the same session). It also holds the token usage the session posts about itself (`inputTokens` … `usageAt`, `model`), read by every token report as provider `claude-cloud` through `services/admin/tokenSource.ts`; the usage scanner never sees these sessions. |
| `ClaudeSessionEvent` | Append-only log of what happened to a cloud session, keyed by `sessionId`: every spawn outcome (`queued` with the refusal reason, `placed`, `already-running`, `agent-failed`), the box's `started` and `ended`, the reconciler's `lost`, an `end-requested` from the UI. `detail` never holds an email, a token or prompt text. Swept after 30 days; run rows after 90 (`services/claudeSessions.ts`). |
| `AgentToken` | Bearer token for a per-user agent connection. Issued from the UI sidebar. Carries `instanceId` so a token is scoped to a specific box, plus `scope` (`agent` default, `admin` for the admin surface) and an optional `expiresAt`. `/ws/agent`, the agent-facing REST routes and `/api/cli/v1`'s box credential accept only `agent`; `requireAdmin` accepts only `admin`. The CLI and `termag tui` sign in with `cli_sessions` (`tmcli_`), not this table. |
| `ChatActiveTarget` | What a Slack or Discord user's `/t` drives outside a project channel (`/t switch`, `/t attach`, the Home tab's Attach), keyed `(platform, chatUserId)` — the chat id, not a termag user, since the bot's operators may have none. Write-through copy of the map in `backend/src/slack/activeTargets.ts`; each chat bot reads it back when it connects on the lease holder, keeping whichever of row and memory is newer, and retrying every 30 s after a failed load. A first `/t`'s fallback project is a guess: kept in memory only, never written, replaced by any row. Cascades with its project; archived projects' rows are skipped on load. |
| `SlackAgentThread` | A Slack agent session's thread (`backend/src/slack/agentSession.ts`), keyed `(channelId, threadTs)`: the Claude session a reply there resumes and its working directory, the channel thread's owner (the one person it answers), and `resetAt` when "new session" cleared it. Write-through copy of `agentSession`'s maps (`agentStore.ts`), loaded before the bot connects, keeping whatever memory set since; rows untouched for 14 days are skipped and pruned. Owner and session share a row so a restart brings them back together. |
| `SlackAgentDmLast` | The newest Claude session in each Slack DM, keyed `channelId`, which a new thread there picks up for 30 minutes. Same write-through and load as `SlackAgentThread`. |
| `SessionStatus` | Write-through copy of the live in-memory status map (`services/statusPersistence.ts`): one row per `instanceKey+session` — status, meta, open `working` span. Restarts re-read it instead of showing every pill as `not_running`, and re-bank spans whose auto-idle deadline passed while down. Rows are pruned after 24 h untouched; there is no append-only event log (the old `StatusEvent` description was stale — the WebSocket push reads the live map). Status writes also bump `Project.lastActiveAt`. |
| `WorkTimeEntry` | Per-day, per-project, per-provider working-time rollup, banked by in-memory transition timers — agent spans in `services/status.ts` (bank on `working`→other transitions, 5-min auto-idle safety net, restart hydration via `session_statuses`), human typing time in `services/humanActivity.ts` (browser heartbeats while typing, 3-min decay). Upsert-increment keyed `(username, project, provider, date, instanceId)`. Powers `/termag/api/worktime` and the two-tube thermometer. |
| `UsageEvent` | Per-call API usage (tokens, cost) for the dashboard. Provider-specific scanners populate this (Codex JSONL, Claude logs, vibe `~/.vibe/logs/session/meta.json`). |
| `ProjectVisit` | Per-user context-switch log: when the UI focus moves between projects. Feeds the visits section of the UsageMini overlay via `/termag/api/visits`. |
| `WarpSample` | Per-minute rollups of the hyperspace-speed signal. Produced by `warpSampler` and exposed via `/termag/api/warp` for the flow-speed sections of UsageMini. |
| `AgentThread`, `AgentThreadPr`, `AgentMessage`, `AskReply`, `AgentBundle` | Agent-to-agent asks: the thread (origin user, target project + workstream, Claude session id, base commit, repo, branch, PR, hop count), one row per PR the thread opened (`AgentThreadPr`: key, branch, number, URL), one row per ask (sender, sender box, status, hop, byte counts, publish outcome, whether anything has read the reply; the prompt only in `queuedPrompt` while an ask to the asker's parked box waits for it to connect, at most 15 minutes, or an ask to a project still cloning waits for the clone, at most 30), its final reply (`AskReply`, `ask_replies`: written in the transaction that finishes the message, sealed with the chat transcript store's key and bound to the message id, at most 1 MiB, read only by the sender, deleted by the ask sweep after 14 days; `services/askReplyStore.ts`), and the commits' bundle until published or 1 h old. A waiting poll gets the reply through Postgres `NOTIFY` (`services/askReplyBus.ts`); a deployment with no transcript key stores none, and there a reply nobody waits for is dropped. |
| `AdminAuditLog` | Every admin REST request and MCP tool call: actor, token if any, surface, action, args summary, outcome. Never pruned automatically. |
| `Team`, `TeamMembership` | PR analytics teams: a named roster of GitHub logins, sourced from the org-tree, with effective-dated membership intervals (`start`/`end`/`openStart`, `source` `synced`|`manual`; a manual row wins over a synced one). A parent team's roster is the de-duped union of its descendants'. `PrAnalyticsSettings.seededTeams` marks the seed rosters created once. |
| `ProjectSpace` | Where a project is listed among spaces, kept when its box terminates. Recorded from `SpaceBox` grants, inherited ones included, by `addGrant` and by the spaces sweep before it prunes terminated boxes' grants. Each listing names the box it was made for (`instanceId`) and counts only while the project is still on it. Listing only: `SpaceBox` stays the access. |
| `ChatTranscript`, `ChatTranscriptChunk` | The orchestrator's copy of each chat-runner chat's Claude Code session: one `ChatTranscript` per (project, workstream, session) with `current` marking the live one, and per-turn chunks keyed by byte offset holding the gzipped raw JSONL and the view entries, sealed under `CHAT_TRANSCRIPT_KMS_KEY_ID` with the chat and offset in the encryption context. `gitState` is the checkout's state at the session's last turn end, unsealed and with no file names. |
| `ChatResume` | A chat continued on a new box after its box was terminated: the session, the old and new box, the old box's last git state, when the session reached the new box (`restoredAt`) and when its first turn there was told (`noticeSentAt`), plus the project's other workstreams named as lost (`lostWorkstreams`). |
| `ChatHeldMessage` | A message sent to a chat whose box is gone or down (`services/chatHeld.ts`): held until the chat can take it, then sent as its sender, oldest first; `claimedAt` for the one process sending it, `error` for one the chat refused. |
| `ChatContinueLock` | One continue onto a new box under way per project (`services/chatContinueLock.ts`): one row, taken by a conditional upsert, deleted when the continue ends; stale after five minutes. |
| `BugReport` | A termag bug an agent or person filed with `termag bug report`: reporter (user, credential kind, box, project, workstream, ask thread), agent and model, title, Markdown body, severity, area, context (CLI version, the box agent's commit and capabilities, the command and its error output), the secret kinds redacted on filing. Only `status`, `duplicateOfId`, `linkUrl` and `triagedAt` change, from `/admin/bugs`, each change a `BugReportEvent`. No foreign key to the reporter or the box, like `admin_audit_log`. |
| `SoftwareUpdateRun` | One update of a tool on a box (`software_update_runs`): `component` (a string the registry in `services/toolUpdate/components.ts` validates, not an enum, so a new tool needs no migration; `claude`, `codex`, `cursor`, `devin`, `pi`, `gh`, `aws` and `node`), `hostKey` (`host_software`'s key: the instance id, or `orchestrator` for the orchestrator host's own Claude Code runs, which have no `instanceId` and are read from the root recipe's records by `services/toolUpdate/orchestrator.ts`; a boot run's id there is `boot<kernel boot id>`), `trigger` (`manual`/`boot`/`guard`/`floor`/`resume`/`nightly`), `restart`, `status` (`requested`/`running`/`done`/`failed`/`refused`/`expired`), `outcome`, `target`, versions before and after, `detail` (≤ 2000), the session counts (`sessions` JSON) and `requestedAt`/`startedAt`/`finishedAt`. Rules in `services/toolUpdate/run.ts`, reads and writes in `services/toolUpdate/runs.ts`. At most one `requested`/`running` run per `(hostKey, component)`: `claimRun` checks and inserts under `pg_advisory_xact_lock` on `tool-update:<hostKey>:<component>`, not a partial unique index, which `prisma db push` can neither express nor keep; a run the fleet pacer still holds counts as in flight whatever its age. No foreign keys, like `host_software`. |
| `session` | `connect-pg-simple`'s session store. Declared in `schema.prisma` as model `Session` (`@@map("session")`) ONLY so `prisma db push` creates/keeps it under the migration DB user; the app never reads or writes it through Prisma. |

`prisma migrate dev` is fine here (this is an interactive box); on non-interactive deploy targets prefer `db push`.

**What runs is `db push`, not the migrations.** Deploys and the e2e stack sync the schema with `prisma db push` (`src/scripts/dbPush.ts`, through `config/schemaSync.ts`); the migration files are a record. `prisma migrate deploy` on an empty database fails early in the history (at `20260528000000_add_instance_model`), so it can't check a migration. Check a schema change instead with `npx prisma db push --skip-generate` against an empty database, then `npx prisma migrate diff --from-url <that url> --to-schema-datamodel prisma/schema.prisma`, which should say "No difference detected". A column on a table that an unmerged PR creates goes into that PR's own migration, and can be `NOT NULL` because no deployed process knows the table yet; on an existing table it is nullable or defaulted (below). Raw SQL in a store gets a `*.integration.test.ts` (`services/prReviewGroups.integration.test.ts`), run against a throwaway Postgres: `docker run -d -p 127.0.0.1:55499:5432 -e POSTGRES_PASSWORD=pw postgres:16` and `TERMAG_TEST_PG_URL=postgresql://postgres:pw@127.0.0.1:55499/postgres`. `db.integration.test.ts` fails against that password-auth server, since it needs trust auth for the users it creates.

**Schema changes are expand, then contract.** During an overlapping deploy the old and new orchestrator share the database, and the new one syncs with `DB_PUSH_MODE=additive`, which skips drops. So add first (nullable or defaulted; write both shapes, read the new one with a fallback), and drop the old shape only in a later release, by hand. A rename, a type change old code can't read, or a `NOT NULL` column without a default breaks the old process mid-deploy.
